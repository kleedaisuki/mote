# Mote.Engine invariants

The engine owns **one file at a time** and has no dependency on format policies, UI frameworks, reflection, or source generators. `Document` is the mutable lifetime boundary; each `TextSnapshot` is immutable and remains readable after later edits or document disposal. Public offsets are UTF-16 code-unit offsets so they can be passed directly to .NET and native text controls. Edits may not bisect a surrogate pair or insert ill-formed UTF-16; CR and LF are ordinary editable code units.

Filesystem failures during Save keep their original exception type, message, HResult, and stack. For content-free diagnosis, `Exception.Data["Mote.Engine.SavePhase"]` names the bounded operation that failed: `TargetCheck`, `TempWriteAndHash`, `FinalTargetCheck`, `Move`, `Replace`, `Cleanup`, or `SavedStamp`. This annotation is not a retry signal: notably, a `Replace` failure may leave the original target intact while the document remains dirty, and the caller must not infer that every filesystem/provider failure is transient. A cleanup failure never supersedes the primary exception: its bounded HResult is attached as `Mote.Engine.SaveCleanupHResult` and as secondary evidence. No file path, text, or fingerprint is added to the annotation; the UI may choose to record the phase and HResult only in opt-in diagnostics. Cancellation is not phase-annotated. `SaveFailureInfo.FromException` exposes local path-bearing observed target/stage outcomes without wrapping the exception; it must not be serialized into telemetry. Missing, unreadable, externally changed, and installed-new target states are distinct; dirty state alone does not prove old bytes survived. See the [recovery contract](../../docs/save-failure-recovery.md) for staging ownership, quotas, explicit export/discard, partial failure and remaining concurrency boundaries.

The buffer is a persistent AVL rope of at most 16 Ki UTF-16-code-unit leaf strings. Branches cache code-unit length, height, logical line-break count, and CR/LF boundary flags. Splitting and joining reuse unaffected subtrees. This avoids the O(file size) copy that `string.Remove().Insert()` would impose on every keystroke. A `GetText()` call *does* materialize the full file; viewport and large-file consumers should use `GetText(start, length)`, `GetLine(line)`, or `GetChunks()` instead. The line index treats CR, LF, and CRLF as one break each, including when CRLF straddles leaves. Original separators and BOM are never normalized.

`Document.Apply`, `Undo`, and `Redo` publish `Changed` only after committing a new snapshot. Commits enqueue events under the document lock; one drainer invokes handlers outside the lock in version order, even with concurrent callers or reentrant handlers. The event contains the prior and next snapshots plus a UTF-16 replacement expressed in prior-snapshot coordinates; a handler may nevertheless observe a newer current `Snapshot`. Undo history retains **before/after rope roots and lengths**, not copied inserted/deleted strings. The newest oversized action is guaranteed undoable **immediately after it commits**; the nominal 32 MiB soft budget applies to other retained edits, and the 512-entry cap still applies. Subsequent ordinary edits can evict that oversized action once the contiguous later suffix exceeds the soft budget or entry cap; a second oversized action can also evict it. History remains a contiguous linear suffix—there is no hidden jump over discarded edits. Thus a latest large paste/delete is undoable without an extra full-string copy at rest, but history depth is bounded. Legacy `Changed.Change.InsertText` still requires a temporary contiguous string on Undo/Redo for large replacements. State identifiers make undoing to the last successful save clean again. A blank untitled `new Document()` is clean until its first real edit; an unsaved document constructed with nonempty text is dirty. The per-document analysis cache is invalidated on every committed edit; callers must compare snapshot versions before presenting analysis computed concurrently with edits.

Open reads into chunks rather than one whole-file string. A known UTF-8, UTF-16, or UTF-32 BOM selects strict decoding; BOM-less input is strict UTF-8. Unsupported legacy encodings fail instead of silently corrupting text. Raw bytes are SHA-256-hashed during this same read, including any BOM. Save writes a captured snapshot through an exclusively created fixed recovery sidecar in the target directory and replaces the target only after a successful flush. An existing current target is replaced with .NET `File.Replace` (which attempts to merge target metadata); a new target uses `File.Move`. A different existing Save As path is **never** silently replaced: default `SaveAsync(path)` fails, while an explicitly confirmed overwrite requires `FileOverwriteToken.CaptureAsync(path)` followed by `SaveOverAsync(token)`. A concurrent edit stays dirty. For any replacement, file length and last-modified timestamp act as a cheap prefilter, and the target's SHA-256 hash is compared with the opened/saved/approved fingerprint immediately before replacement. This catches same-size, restored-timestamp external edits, failing with `IOException` rather than overwriting them. The saved temp file is currently read once more to establish its fingerprint for the next save; this extra I/O is measurable on very large files and can later be folded into the write stream. A filesystem race still exists between final verification and replacement because .NET exposes no portable compare-and-swap file replace; platform/filesystem-specific crash durability and metadata preservation are not guaranteed. The UI should expose failures and offer an explicit recovery path (reload, save as, or compare), not silently retry over the target. See the [.NET `File.Replace` contract](https://learn.microsoft.com/en-us/dotnet/api/system.io.file.replace?view=net-10.0).

The rope's balanced-tree structure follows the production lesson behind [VS Code's piece-tree buffer](https://code.visualstudio.com/blogs/2018/03/23/text-buffer-reimplementation): line arrays and whole-string replacement are poor foundations for large-file editing. Mote uses immutable nodes because snapshot retention and background semantic analysis are first-class; it is not a claim that this structure is universally faster than a mutable piece tree. Measure representative open, viewport, head/tail edit, and save workloads before tuning chunk size or allocator behavior.

## Copy-free range iteration

`TextSnapshot.GetChunks(start, length)` yields nonempty `ReadOnlyMemory<char>` slices
of existing immutable leaf strings in source order. It validates the UTF-16 range
immediately, including zero-length ranges at the end offset. A zero-length range
yields no slices. Like `GetText(start, length)`, reads may split a surrogate pair or
CRLF; streaming consumers must carry decoder or line-ending state between slices.
The existing parameterless `GetChunks()` contract is unchanged.

The range iterator seeks by cached subtree lengths, skipping the preceding leaves,
then visits intersecting leaves with an explicit pending-subtree stack. For n
leaves and k returned slices, traversal is O(log n + k), stack space is O(log n),
and no source text is copied. The sequence captures its snapshot, not the mutable
document; deferred enumeration and yielded memories survive later edits and
document disposal. `EngineRangeChunksTests` verifies exact nested/edited-rope
ranges, backing-string identity, boundary pairs, eager invalid-range rejection,
and retained versions, with 150 deterministic additional random ranges.

## Recovery lifecycle

`Document.GetSaveRecoveryPath(target)` identifies one fixed same-directory slot per normalized target name. An existing slot is neither adopted nor deleted. A commit error retains an owned stage even if the target disappeared (the documented Windows 1176/no-backup outcome); `PendingSaveRecovery` records its attempted version, not subsequent edits. Another Save cannot allocate a second stage until that recovery is explicitly resolved. `ExportSaveRecoveryAsync(newPath)` refuses the recorded attempted Save/Save As target even if it is now missing, creates a distinct new file without overwrite, verifies exact snapshot bytes, then removes the owned stage; it does not change saved state or FilePath. `DiscardSaveRecoveryAsync` removes only verified owned bytes or acknowledges a confirmed Missing slot; unknown/changed/incomplete bytes require manual handling. Dispose leaves bytes intact for recovery after restart. This same-directory content sidecar is a deliberate exception to the configured `~/.mote` data home: moving a possibly unique replacement across volumes/permissions on failure would introduce another unsafe destructive step. No automatic expiry, retry, in-place overwrite, crash-durability or metadata/ACL guarantee is added.

Failure-only outcome collection is best effort for all non-OutOfMemoryException inspection errors, including security/provider failures. Unknown is not Missing. Pending ownership is established before optional evidence, and unavailable exception Data cannot replace the original failure: local `SaveFailureInfo.FromException` returns null, while enabled telemetry degrades phase to unknown and keeps the original HResult. Catastrophic resource exhaustion is not a promised recovery boundary.
