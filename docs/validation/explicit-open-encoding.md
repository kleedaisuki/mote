# Explicit document encoding validation

## Contract and independent oracle

The engine's explicit-open route must preserve the existing automatic route: BOM detection, otherwise strict UTF-8. A user-selected codec is not permission to replace undecodable bytes, guess another codec, or discard a conflicting known BOM. Successful legacy open must permit exact byte round-trip; unsuccessful save must preserve the original, dirty snapshot and recovery options.

`tests/Mote.Tests/DocumentExplicitEncodingTests.cs` owns independent portable checks. Its Chinese fixtures are literal bytes, not generated by the codec under test:

| Codec | `中文` + CRLF, hexadecimal |
| --- | --- |
| UTF-8 | `E4B8ADE696870D0A` |
| UTF-16 LE / BE | `2D4E87650D000A00` / `4E2D6587000D000A` |
| UTF-32 LE / BE | `2D4E0000876500000D0000000A000000` / `00004E2D000065870000000D0000000A` |
| GBK / GB18030 | `D6D0CEC40D0A` |
| Big5 | `A4A4A4E50D0A` |

The GB18030 astral fixture `9439FC36` represents U+1F600. The literal bytes were independently cross-checked with local Python standard-library codecs; production expectations do not invoke Python or generate bytes with `Document.Encoding`.

Checks cover BOM-less input and empty files for all eight choices; matching and conflicting Unicode BOMs; unchanged automatic BOM detection; malformed Unicode and truncated legacy sequences; default UTF-8 refusal of GBK input; source-byte preservation; supported legacy edits, save/undo/redo state and version; unrepresentable emoji saves with original protection and staging cleanup; external byte changes with unchanged size and restored timestamp; read boundaries, invalid enum and pre-cancellation.

## Defensive round-trip rejection: negative fixture search

On Windows with .NET SDK 10.0.400, a separate console probe used `CodePagesEncodingProvider.Instance.GetEncoding(codePage, EncoderFallback.ExceptionFallback, DecoderFallback.ExceptionFallback)` directly, without global provider registration or production engine calls. It enumerated all 65,536 two-byte strings, decoded each valid input, re-encoded the text and compared exact bytes:

| Code page | Valid decoded two-byte strings | Re-encoding mismatches |
| --- | ---: | ---: |
| 936 | 40,840 | 0 |
| 54936 | 40,324 | 0 |
| 950 | 36,610 | 0 |

The independent probe also enumerated all 1,587,600 GB18030 four-byte patterns with positions in `81..FE`, `30..39`, `81..FE`, `30..39`. It found 1,087,996 valid decoded strings and **zero** re-encoding mismatches. Invalid decoder and encoder inputs were counted outside the valid set, not repaired or retried. Artifacts are `.temp/encoding-independent-scan/{Probe.csproj,Program.cs,results.txt,four-byte-results.txt}`. Exact command: `dotnet run --project .temp/encoding-independent-scan/Probe.csproj -c Release` (the two-byte and four-byte implementations ran separately). To reproduce the two-byte scan, enumerate `n = 0..65535` and use `[(byte)(n >> 8), (byte)n]`; for each code page, count successful `GetString` followed by `GetBytes`, and compare exact arrays. The four-byte scan uses the Cartesian product of the ranges above. Do not substitute global `Encoding.GetEncoding` registration or a production wrapper.

Consequently, no fabricated duplicate-mapping fixture is asserted to trigger `DocumentEncodingRoundTripException`. This defensive negative branch remains unexercised by a real-provider fixture; exhaustive fixed-width scans are not a proof over arbitrary streams or future provider versions. The positive byte comparisons and strict rejection checks still exercise the ordinary contract.

## Native-controller portable orchestration

`tests/Mote.Tests/NativeExplicitEncodingControllerTests.cs` drives the actual `NativeEditorController` through an independently implemented minimal `INativeEditorShell` and optional `INativeOpenEncodingShell`. No shared fake was changed and no production seam was added. Modal callbacks dispatch actual New, ordinary Open, edits or disposal, and background completions are delivered through the fake's owned concurrent queue. The postconditions concern installed text, document stamps/titles, dirty state, undo results, exact saved bytes, chooser/discard/picker call counts and collected errors, not presumed implementation fields.

The 13 new cases establish:

- A default strict UTF-8 failure offers the chooser exactly once; deliberate GBK selection opens fixed Chinese bytes and a supported edit saves fixed GBK bytes.
- Canceling the offered chooser or selecting invalid UTF-8 does not replace the previous document, alter its version/title, clear dirty state or discard undo history. Explicit decode failure does not offer the chooser again.
- The explicit command can interpret BOM-less `41004200` as UTF-16 LE (`AB`) even though these bytes are also legal UTF-8; it is not restricted to default decode failures.
- A nonfatal chooser exception is contained and preserves current text.
- New, later ordinary Open or disposal dispatched within the explicit chooser prevents the original choice from replacing the current document. Disposal removes the optional command subscription; invoking it afterward does not call the chooser.
- Edits after initial Open admission, both before the fallback chooser and within it, require a fresh discard confirmation. Rejecting that final confirmation preserves the newer edit and its undo chain; initial approval is not reused.
- An in-flight actual Save request or a fake native pending-input veto prevents the explicit command from entering its file picker or chooser.
- A shell without the optional capability retains the established generic strict-decode error behavior.

These cases do not prove all arbitrary reentrant callback sequences or platform menu/shortcut wiring.
