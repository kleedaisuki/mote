# One logical Windows UIA editor with a focused RichEdit input island

Status: **focused design and reversible experiment, not an accepted tree**, 2026-09-29. This document addresses only the duplicate-document tree of the opt-in Windows continuous canvas. Whole-source ranges, request budgets, and incomplete TextPattern methods remain in [accessibility-provider-design.md](accessibility-provider-design.md); IME ownership remains in [input-island-design.md](input-island-design.md). No Narrator/NVDA or real CJK-composition pass follows from the tree proposal.

## Observed failure, not an inferred one

The canvas HWND is a child of the main window; the visible `RICHEDIT50W` input HWND is a child of the canvas and receives actual Win32 keyboard focus for editing and IME. The canvas `WM_GETOBJECT` path returns the engine-backed `IRawElementProviderSimple`/TextPattern; the input HWND's existing subclass forwards `WM_GETOBJECT` to RichEdit unchanged. An external WindowsDesktop UIA client queried a published win-x64 Native AOT binary on Windows 10.0.26200.0. In `.cache/ax-uia-external/invalid-operation.txt`, `AutomationElement.FromHandle(input)` is `Document / RichEdit Control` with 16 UTF-16 units; the canvas's first RawView and ContentView child is the same `Document`, while the canvas itself exposes the source-backed Document/TextPattern and its offscreen tail. `HasKeyboardFocus` and `GetFocusedElement` identify **RichEdit**, not canvas. A separate ControlView query also found the child Document. This is two semantic documents in all three views, with focus on the bounded one. There is no speech evidence yet.

The target is **one source-backed Document in ControlView and ContentView, and one focused semantic editor**. RawView may retain an implementation-only HWND proxy, but that proxy must not identify itself as a second Document or leak a page-local TextPattern. Physical Win32 focus must remain on RichEdit; keyboard input, clipboard, TSF/IMM composition, candidate placement and undo/save behavior must not change. UIA focus, selection, visible ranges, and text events must describe the canonical source. If a screen reader cannot announce composition after the RichEdit node is demoted, this design is not accepted merely because the tree looks tidy.

## What the platform contract actually permits

Microsoft defines RawView as the full provider tree, ControlView as nodes with `IsControlElement=true`, and ContentView as the subset also marked `IsContentElement=true` ([UIA tree overview](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-treeoverview)). A custom HWND provider can use its [host provider](https://learn.microsoft.com/en-us/windows/win32/api/uiautomationcore/nf-uiautomationcore-irawelementprovidersimple-get_hostrawelementprovider) for default HWND properties. Complex controls instead need an `IRawElementProviderFragmentRoot` with navigable fragment nodes, hit-testing and focus; [`IRawElementProviderHwndOverride::GetOverrideProviderForHwnd`](https://learn.microsoft.com/en-us/windows/win32/api/uiautomationcore/nf-uiautomationcore-irawelementproviderhwndoverride-getoverrideproviderforhwnd) may **reposition/override a window-backed child provider inside that fragment**. Microsoft's [server-side provider guide](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-serversideprovider) demonstrates this for rebar bands containing HWND controls. It does **not** promise that returning `null`, setting one filter property, or swallowing a child's `WM_GETOBJECT` will make a standard RichEdit provider disappear. The returned override must belong to the fragment; its parent/child navigation, host HWND and runtime identity must be coherent. The [fragment-root `GetFocus` contract](https://learn.microsoft.com/en-us/windows/win32/api/uiautomationcore/nf-uiautomationcore-irawelementproviderfragmentroot-getfocus) reports the focused element in the fragment, including the element hosting another framework's focused child.

Likewise, [`WM_GETOBJECT` guidance](https://learn.microsoft.com/en-us/windows/win32/winauto/handling-the-wm-getobject-message) distinguishes `UiaRootObjectId` from MSAA `OBJID_CLIENT` and other requests; a control that does not implement a request should let the default procedure run so UIA/MSAA can find a proxy. Intercepting or returning zero for all child requests is therefore not a documented hide mechanism. [`ProviderOptions_OverrideProvider`](https://learn.microsoft.com/en-us/dotnet/api/system.windows.automation.provider.provideroptions) exists, but its presence alone is not evidence that default RichEdit properties, patterns, focus or events are suppressed. UIA can merge host/default-provider information; the result must be observed externally.

## Smallest standards-based, reversible experiment

Do **not** first alter the RichEdit window, its focus, or IME message path. Under an opt-in diagnostic switch, evolve only the existing canvas provider into a source-generated COM fragment root and add one implementation-only input-HWND proxy:

```text
main window default provider
  └── canvas fragment root: source-backed Document / TextPattern
        └── input HWND proxy: RawView-only implementation host, no semantic TextPattern
             (physical GetFocus() still returns RichEdit HWND)
```

The root implements `IRawElementProviderSimple`, `IRawElementProviderFragment`, `IRawElementProviderFragmentRoot`, and `IRawElementProviderHwndOverride` as distinct native COM interfaces/vtables (the C++ interfaces are not a C# inheritance shortcut). `GetOverrideProviderForHwnd(input)` returns the proxy; any other HWND returns null. `Navigate` makes the proxy reachable from the root and back; the root obtains `UiaHostProviderFromHwnd(canvas)`, while the window-backed proxy uses the input HWND host as specified for repositioning. Probe `ServerSideProvider | OverrideProvider` on the proxy **as a hypothesis**, not as a guaranteed filter. The proxy advertises `IsControlElement=false`, `IsContentElement=false`, a non-Document type and no custom TextPattern; its runtime ID must be stable and distinct from the canvas root. The root reports logical `HasKeyboardFocus=true` only while `GetFocus()==input`, maps fragment `GetFocus`/`SetFocus` to that HWND without moving native focus to canvas, and raises a source-root focus change when appropriate. The source root continues to publish `AccessibleCanvasState(generation,snapshot,CanvasFrame)` atomically; no page-local text enters the root. See [provider navigation and event requirements](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-serversideprovider).

This is **an experiment, not a claim that the proxy suppresses RichEdit**. The default host may still supply RichEdit's Document type/TextPattern; UIA's focused element may remain the raw proxy or underlying RichEdit despite root focus properties. If so, record that exact result and stop—do not add a second focus state or intercept `WM_GETOBJECT` broadly to make a screenshot pass. A later, separately reviewed UIA-only child-`UiaRootObjectId` override might be necessary, but it must leave MSAA/other IDs and native input intact and be measured against focus/IME/reader behavior before adoption.

The switch is disabled by default, does not change `Mote.Engine` or the single-binary packaging, and can be removed without document-data migration. On detach/`WM_DESTROY`, invalidate source ranges, disconnect providers per Microsoft's [provider-lifetime guidance](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-serversideprovider), and leave RichEdit's existing subclass/native behavior in place. On any COM/AX failure, revert to the current opt-in canvas UIA behavior rather than crash or corrupt the editor; do not treat the fallback as accessibility acceptance.

## Falsifying external acceptance matrix

Use the existing external WindowsDesktop UIA process against **published win-x64 and win-arm64 AOT executables**, not only generated-COM unit tests. Query `AutomationElement.FromHandle(canvas)`, `FromHandle(input)`, `ElementFromPoint` over both painted canvas and island, and `GetFocusedElement` before/after click, typing, New, and close. Walk **RawView, ControlView, ContentView** from the main window, capture `(RuntimeId, HWND, ControlType, Name, IsControlElement, IsContentElement, HasKeyboardFocus, TextPattern availability)` for each node, and subscribe to focus/structure/text/selection events. Store logs/screenshots in repo `.temp/` or `.cache/`, with no user document text/path in telemetry. Compare baseline and opt-in experiment in a fresh process to avoid cached proxies; also hold a pre-New element/range and verify stale access fails.

| Required observation | Failure that falsifies one-logical-editor acceptance |
| --- | --- |
| Exactly one ControlView **and** ContentView Document with whole-source TextPattern; RawView input proxy may remain but is not Document and cannot return page text. | RichEdit remains a second Document, any client obtains a 16-unit page TextPattern as the editor, or canvas source Document disappears. |
| UIA `GetFocusedElement` and focus events resolve to the source Document while `GetFocus()` Win32 remains input HWND; caret/selection and offscreen marker belong to the same generation. | UIA focus remains a hidden/non-content proxy, oscillates between two Documents, or the root claims focus after native focus leaves the editor. |
| RichEdit keyboard/clipboard and actual Pinyin candidate commit/cancel remain intact, including caret candidate rectangle; no extra engine commit for preedit. Narrator and NVDA speak the global caret and do not read the bounded page twice. | Any lost key/IME candidate, focus theft, duplicate or silent speech, page-local announcement, unexpected edit, or change to existing save/reopen bytes. A clean tree alone is insufficient. |
| External clients continue to retrieve bounded source text/visible ranges, and old providers become unavailable after New/close without retaining a closed large snapshot. | A source request routes to RichEdit, stale data leaks, or the provider/host reference cycle keeps the document alive. |

If the standards-based fragment override cannot satisfy both tree and focus/IME tests, preserve the present opt-in behavior and keep the one-document accessibility gate open. Do not hide or destroy the input HWND: it is a working OS text-service boundary, not merely a duplicate visual widget.
