# Strict one-on-disk-binary desktop feasibility

Status: validated feasibility decision, 2026-09-29. This document supersedes any earlier interpretation that a `.app` directory or an executable with private `.dll`/`.dylib` companions satisfies the product requirement. **It does not.** The allowed runtime dependencies are operating-system-provided DLLs/frameworks, not product-shipped native libraries, extracted payloads, a helper process, or an app bundle masquerading as one file. Separate OS/architecture-specific binaries are expected; “one binary” is per target, not one PE/Mach-O for all platforms.

## Decision

**Use a native OS UI shell (Win32/RichEdit on Windows; AppKit/NSTextView on macOS) behind a narrow editor-view adapter, with the existing C# engine/formats compiled into one Native AOT executable.** Keep all editor state and file lifetime in the engine. The native text control is an input/presentation adapter, not the source of truth. The one-binary GUI route is directly demonstrated on macOS; Windows has a demonstrated one-binary native-link mechanism and OS-provided RichEdit, but still needs its own end-to-end GUI test. Preserve a larger-file route to a virtualized document surface rather than claiming an entire native text control remains fast for 100 MB files. A native control gives us real platform input methods and accessibility to start from; the virtualized route needs its own OS text-input and accessibility bridge before release.

Avalonia is not intrinsically incompatible with static linkage; however, **this checkout's Avalonia 12.1.3 dependency graph and publish output are incompatible with the strict requirement**. Making it comply would mean rebuilding and maintaining static variants of SkiaSharp, HarfBuzzSharp, Windows ANGLE, and the macOS Avalonia native backend, changing their P/Invoke binding/link modes, and validating every supported architecture. No stock NuGet static archives for those packages were found. A community static Avalonia sample exists, but its current example targets `net10.0-windows` and configures only `win-x64` native archives; it is not evidence for the macOS backend or this product's complete dependency set. This route has higher build-maintenance risk than using OS-native UI and does not solve the large-file text-control problem by itself.

The Windows static-link test is intentionally only a mechanism probe; it is not a Win32 product UI test.

## Alternatives and product consequences

| Route | Strict binary? | IME/accessibility starting point | Dominant risk / decision |
| --- | --- | --- | --- |
| Stock Avalonia 12 + AvaloniaEdit | **No**, observed private native libraries on Windows and macOS | Mature cross-platform editor behavior | Keep as development reference only; do not ship under current contract. |
| Rebuild static Avalonia/Skia/HarfBuzz/ANGLE/AvaloniaNative | Theoretically yes, not demonstrated for mote or macOS | Preserves AvaloniaEdit behavior if successful | Four native build pipelines, symbol/P/Invoke rewiring, code-signing and release reproducibility; a Windows-only community example is insufficient. Only reconsider after a bounded, cross-platform static prototype actually emits one file and passes GUI/IME/accessibility tests. |
| Native Win32 RichEdit + AppKit NSTextView | **Yes**; macOS GUI demonstrated, Windows uses system `Msftedit.dll` and OS APIs | Native platform input, selection, clipboard and accessibility facilities | Two platform adapters and duplicated view text. Use as initial full-product shell, but benchmark memory/open/edit and make the large-file path explicit. |
| Fully custom canvas (DirectWrite/CoreText) + input/accessibility bridge | Yes, if only OS frameworks | Must implement text input composition, caret geometry, selection, clipboard, screen-reader text navigation, semantics | Necessary candidate for continuous 100 MB editing, but not a cheap “just draw text” substitute. Prove input/accessibility before replacing native controls. |
| Static SDL3 + custom text editor | SDL itself supports static libraries and reports composition events; potentially yes | Less OS-native control semantics and no complete document accessibility from SDL alone | Adds a native build dependency yet still requires custom text layout, IME and screen-reader work. Not preferable to direct OS shell for this product. |

Windows Rich Edit 4.1 (`Msftedit.dll`, `RICHEDIT50W`) is an OS-provided component with Text Services Framework support and UI Automation text-control support. AppKit documents `NSTextInputClient` as the contract for custom text views; built-in `NSTextView` implements it. These are meaningful production-practice advantages over a bespoke canvas, but a protocol/class check is **not** a manual Chinese/Japanese/Korean IME test, and standard-control accessibility is **not** equivalent to a complete accessible semantic outline. A custom view should expose the full logical document through UI Automation TextPattern on Windows and appropriate `NSAccessibility` text operations on macOS, including navigation to offscreen text. Production Monaco's screen-reader mode pages text rather than exposing only a visual canvas. CHI 2024 user research on programmers with visual impairments also emphasizes navigation and reading workflow; therefore accessibility must be an acceptance gate, not a decorative follow-up.

The engine/view adapter must have a crisp contract: engine snapshots are canonical; view sends UTF-16 edit deltas and selection/caret changes; engine returns accepted versioned changes; the adapter applies only changed spans and guards against echo loops. For large files, a native full-document control may allocate another whole-document buffer and invoke expensive native layout. A viewport-backed control must preserve continuous scroll/caret semantics and offscreen editing, not revert to page buttons. Performance experiments should compare 1/10/100 MB files, a 50 MB line, CJK composition and selection, and track first editable paint, edit-to-paint p95, peak resident memory, scrolling, and accessibility query latency. It is acceptable for global parsing to be asynchronous; text editing cannot become read-only merely because derived analysis is partial.

## Mac-specific unresolved distribution risk

Apple's common application-bundle guidance places `Info.plist` and the executable inside `.app`; `CFBundleDocumentTypes`, icons and common notarization workflows usually assume a bundle. However, Apple also explicitly documents [an embedded `Info.plist` for single-file tools](https://developer.apple.com/library/archive/documentation/Security/Conceptual/CodeSigningGuide/Procedures/Procedures.html) and [reading `(__TEXT,__info_plist)` from an unbundled Mach-O](https://developer.apple.com/documentation/corefoundation/cfbundlecopyinfodictionaryforurl%28_%3A%29). The positive `open -a` and `codesign` probes show this is not merely theoretical: a standalone Native AOT Mach-O with embedded metadata is recognized as an application by Launch Services on macOS 15 ARM and Intel. Apple's notarization guidance also covers command-line targets and tickets attached to executables. Nevertheless, Finder document double-click, file-type association, Dock identity and Developer ID-signed/notarized Gatekeeper behavior remain open. The earlier `open -a` probe rejected a *relative* path without embedded metadata; its negative result was confounded and should not be cited as proof of incompatibility. A `.app` wrapper is forbidden by the user contract, so release acceptance must test these exact bare-file behaviors rather than silently packaging a bundle. If modern macOS cannot meet them, expose the incompatibility to the user and seek a product decision; do not weaken “strictly one binary” by euphemism.

## Next discriminating gates

1. **Native shell round-trip:** real text input (ASCII, Chinese Pinyin, Japanese composition), selection, paste, undo, and save on both OSes through the canonical engine, with no process-private native library and a `file`/`otool`/PE import inventory gate.
2. **Accessibility:** VoiceOver and NVDA/Windows Narrator read current line, offscreen line, selection and diagnostics; compare with native text-control baseline. Run on interactive target machines, because headless CI protocol conformance cannot certify behavior.
3. **Large-document control crossover:** instrument memory/layout/edit latency of native controls at 1/10/100 MB and one 50 MB line; switch to a virtualized adapter only on measured failure, while retaining identical document and I/O semantics.
4. **Bare macOS distribution:** sign/notarize a lone Mach-O, transfer to a clean macOS machine with quarantine metadata, launch via Finder, test Open With/document association and Dock identity. The result decides whether the product's strict binary and polished native macOS distribution promises can coexist.
