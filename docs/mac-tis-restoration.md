# Why the hosted Apple Pinyin activation probe did not restore ITABC

Status: **diagnosis only; no additional mutation run** (2026-09-30). This note complements `docs/mac-real-ime-acceptance.md` and does not certify a real IME test.

## Observation and code path

CI [36688502809](https://github.com/kleedaisuki/mote/actions/runs/36688502809), commit `191cc111d8c4a4232328025ddb0cdb112b1dd671`, ran `tests/MacRealImeActivationProbe/Activate.m` on disposable macOS 15.7.9 x64 and 26.6.2 Arm64 runners. The exact reports are `.cache/mac-real-ime-run-36688502809/{x64,arm64}/mac-real-ime-activation.json`. On both: SCIM parent and ITABC mode began disabled; enabling both and selecting ITABC each returned `noErr` and post-query state confirmed selected/enabled. Restoration selected the exact original ABC/US source, then called `TISDisableInputSource(ITABC)` and `TISDisableInputSource(SCIM)`, each returning `noErr`. At the final fresh `TISCreateInputSourceList(NULL, true)` lookup, original source was selected, SCIM was disabled, but ITABC was unselected **and still enabled**. Thus `activation_passed=true`, `restoration_passed=false`, `real_ime_tested=false` on both. These are observed TIS properties, not an observation of Settings UI or a new login session.

The helper reacquires a TIS source reference before each operation and state query, so a single retained stale `TISInputSourceRef` is not the obvious explanation. But every query is in the **same process** and can still share framework/service caching. Critically, `(void)waitFor(modeID, @"enabled", NO)` discards whether the mode actually became disabled during the two-second poll. It does not emit a sample between the child-disable and parent-disable calls. `restore_error` remains empty because it records nonzero OSStatus/exception, not a false `waitFor` result; `restoration_passed` correctly catches the final mismatch. Nothing in this report proves the child was ever observed disabled, nor that the parent disable caused re-enablement.

## What Apple documentation does and does not establish

Apple's [Text Input Source Services Reference](https://leopard-adc.pepas.com/documentation/TextFonts/Reference/TextInputSourcesReference/TextInputSourcesReference.pdf) (2007, pp. 5, 12–13, 18) says an input mode requires its parent enabled to **become enabled or selected**, `TISDisableInputSource` returns `paramErr` if a source cannot be disabled and otherwise `noErr`, and `kTISPropertyInputSourceIsEnabled` reports current enabled state. It does **not** document a timing guarantee, an atomic rollback transaction, a promise that disabling a parent cascades to its modes, or how a modern built-in SCIM mode behaves on macOS 15/26. Apple [QA1810](https://developer.apple.com/library/archive/qa/qa1810/_index.html) (2014) notes that since Mavericks keyboard input modes act as individual sources rather than merely a group under the parent. Therefore, both child and parent deserve independent verification; `noErr` alone is not a substitute for postconditions. The old reference describes intended API semantics, not proof of present implementation correctness.

## Causal hypotheses, ranked only as investigation priorities

| Hypothesis | Why it fits | Distinguishing observation |
| --- | --- | --- |
| Child disable is accepted but does not take effect for this Apple built-in mode in these runner sessions | Same `noErr`/enabled mismatch on two OS versions; QA1810 treats modes as independently managed | Query from a **separate, fresh process** after child disable while parent remains enabled; if both processes report enabled throughout, this explanation gains weight. The exact reason could still be OS policy/bug, not inferable from this run. |
| Delayed propagation or service reconciliation re-enables ITABC | The helper polls child state for only ~2 s, then immediately disables parent; no intermediate sample is saved | Time-stamped same-process and independent-process observations after child disable and again after parent disable, over a bounded interval. A false→true transition supports reconciliation; persistent true supports ineffective disable. |
| Process-local TIS state/cache differs from service/user-session state | Fresh references all originate from one helper process | Independent read-only `TISCreateInputSourceList` observer before/after each operation. If observers disagree, neither a local `noErr` nor local enabled flag can be taken as session truth without further analysis. |
| Parent/mode ordering or a last-mode invariant affects restoration | Hierarchy matters for enabling; the reference does not specify disable ordering or cascading | Only after the temporal/cross-process trace, consider a **separate disposable-runner** controlled order experiment. Do not reverse order casually on a non-disposable Mac or infer this from the current report. |

## Next smallest safe discriminator (proposed, not run)

On a **new dedicated GitHub-hosted macOS runner only**, retain the existing identity guards and require the initial original source plus SCIM/ITABC disabled state to match the known disposable-session preconditions. Use the same enable/select/restore calls and `@finally` cleanup, but add a read-only, independently launched TIS observer process that reports only source IDs, enabled/selected bits, monotonic timestamps, and OSStatus; never logs text, presses keys, opens mote, edits preference files, or requests permissions. After restoring ABC/US, call child disable **once** while SCIM stays enabled; record the Boolean return of a bounded wait plus same-process and observer states immediately and through a bounded 5–10 s interval. Then disable SCIM once, sample both sources from both processes through another bounded interval, and make the final acceptance condition match the exact initial source/parent/mode state in the **independent observer** as well as the helper. If child never becomes disabled, stop interpreting the parent call as the cause. If child becomes disabled then re-enables after parent disable, investigate that transition specifically. If the two processes disagree, isolate TIS cache/service behavior before changing the order. A failed cleanup must leave the job non-gating but report failure prominently and discard its runner. Do **not** proceed to a real-key/candidate test until exact restoration is demonstrated.
