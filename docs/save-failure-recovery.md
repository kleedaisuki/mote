# Save failure recovery contract (2026-10-01)

## Decision

Treat a commit exception as an uncertain filesystem outcome, not proof that the original survived. Preserve the original exception object/type/HResult/stack; attach structured `SaveFailureInfo` for explicit UI only. Optional telemetry still reads only the bounded phase and original HResult, never this path-bearing object.

Use one fixed same-directory staging slot `.mote-save-<SHA-256 of normalized target filename>.recovery`, created exclusively with `CreateNew`. The public `Document.GetSaveRecoveryPath` defines the exact discoverability mapping: absolute target directory, UTF-8 filename SHA-256 in lowercase hexadecimal (64 characters); filename casing is folded on Windows/macOS, and macOS canonical Unicode spellings are normalized to NFC first. The 84-character sidecar component avoids exceeding the 255-character component limit for long target names; full-path limits/permissions can still reject staging before commit. Case-sensitive Windows/macOS directories may conservatively collide on distinct case spellings, safely refusing Save rather than erasing content. Alternate hard-link/short-name aliases are not a universal quota guarantee. A successful commit consumes it. A fully encoded/flushed/fingerprinted snapshot whose commit fails remains there, even when target inspection fails or reports missing. Never clean a staging slot that this save did not create. A pre-existing slot blocks Save without adoption/deletion; this bounds automatic retained content to one snapshot per target across processes/restarts. No automatic expiry is safe for a potentially unique copy. Explicit export or discard is required; no target overwrite or retry is part of recovery.

`PendingSaveRecovery` owns the captured snapshot version and byte hash, not later edits. While pending, Save is rejected before allocating another stage. Export copies to a caller-selected new path **distinct from the attempted Save target**, verifies exact bytes, then removes the owned stage; it does not change document identity, dirty state or saved version. `SaveRecovery.AttemptedTargetPath` records the failed Save/Save As destination independently of `Document.FilePath`; export rejects its normalized lexical path even if Windows 1176 left it missing. This prevents accidental target restoration outside the Save identity/external-change protocol. Common Windows/macOS case aliases and macOS NFC aliases are rejected conservatively; filesystem-wide alias identity is still not promised. Discard requires explicit caller approval and verifies stage hash before deletion, or acknowledges an actually observed Missing slot without deleting anything. Unknown/inaccessible or changed slots are never treated as missing. Failed export/discard leaves ownership pending. A pre-commit encoding/write/hash error with failed cleanup may retain incomplete/unverified bytes (no completed snapshot hash); automatic export/deletion refuses these bytes. Native UI explicitly instructs manual inspection/copy and close/reopen after resolving that sidecar, rather than presenting it as a full snapshot or repeatedly offering an impossible export. Dispose never deletes recovery. After restart, the fixed filename is discoverable; existing bytes must be inspected/copied/removed explicitly outside the old Document rather than automatically trusted.

Classification compares actual target and staging bytes with saved/original hashes, with before/after stamp checks. Outcomes are `OriginalSnapshot`, `SavedSnapshot`, `OtherContent`, `Missing`, or `Unknown`; errors are secondary bounded HResults. Failure-only inspection degrades every non-OutOfMemoryException error (including security/provider failures) to Unknown rather than replacing the primary exception; catastrophic resource exhaustion is not a promised recovery boundary. Owned pending recovery is recorded before inspection/annotation. Optional exception Data reads/writes can fail without masking the primary: UI evidence becomes unavailable and opt-in telemetry records unknown phase plus the original filesystem HResult, never the annotation failure message. They describe observations, not future guarantees or platform crash durability. A successful replacement followed by SavedStamp failure is a separate committed-but-bookkeeping-failed state, never an automatic retry.

## Data location trade-off

Configuration/cache/traces default to the configured ~/.mote home. Atomic staging must reside beside the target. Failure recovery deliberately retains that staging file in place: relocating a possibly unique snapshot to a home on a different volume can fail and creates another destructive step. This narrowly scoped content sidecar is an explicit exception, not telemetry/cache. It inherits parent-directory staging permissions, which may be less restrictive than the original target; extended streams and metadata are not verified or exported as part of the primary-content snapshot. Sensitive documents therefore require appropriately restricted parent-directory permissions. It inherits staging permissions; no stronger confidentiality or ACL-preservation guarantee is made. UI exposes the path locally, never in telemetry. A later home recovery catalog can index sidecars without moving/deleting their bytes; it is outside this fix.

## Evidence and scope

Microsoft [ReplaceFileW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew) documents 1175 retaining original names, 1176 without backup removing the target while leaving replacement under its old name, and 1177 leaving the old target under a different name. These are documented possible states, not observed mote loss. [.NET File.Replace](https://learn.microsoft.com/en-us/dotnet/api/system.io.file.replace?view=net-10.0) allows null backup and requires the same volume. No backup protocol, in-place fallback, generic retry, metadata-ignore flag, external-change policy relaxation or crash-durability claim is introduced.

The existing final stamp + SHA-256 guard and explicit Save As token remain unchanged. The check-to-replace race remains non-atomic. [Pillai et al., OSDI 2014](https://www.usenix.org/conference/osdi14/technical-sessions/presentation/pillai) motivates separating live return-code outcomes from crash persistence; its Linux evidence does not explain the Windows incident.

## Planned acceptance

Deterministically inject commit outcomes (1175, target-absent 1176, target-new exception, missing/altered stage, inspection failure), cleanup failure with a primary exception, and post-commit bookkeeping failure. Assert exact primary identity/HResult, dirty state, unchanged Save As association, owned-stage retention, bounded repeated Save, pre-existing-slot nondeletion, export/discard validation and subsequent-edit semantics. Retain real Windows sharing/read-only controls. Fault injection establishes application policy, not OS reproduction of 1176.

## Residual concurrency boundary

Hash/stamp inspection and later path deletion are not a portable atomic compare-and-delete operation. Explicit recovery actions verify immediately before deletion and refuse changed/unreadable bytes, but another writer with access to the directory can replace a same-name object after verification. The Save target guard has the analogous documented race. This fix does not promise protection against adversarial concurrent directory writers, alternate-name aliases, or arbitrary file-filter behavior; stronger file-ID/handle-based deletion would require platform-specific contracts and a separate implementation. Existence alone is never used as proof of absence in outcome inspection.

## Native dialog and lifecycle contract

Every native Save failure message starts exactly `Save failed.` and reports inspected target outcome (or explicitly unknown). No universal `original retained` claim remains. Windows shell still uses the editor-owned standard MessageBox (`#32770`, title `mote`, OK/IDOK=1); this is a UI identity cue, not byte evidence. On a retained complete stage, the next Save/Save As command explains its captured snapshot version and invokes the Save picker for a NEW, non-overwritten recovery export. Successful export does not associate that path with the Document or mark any buffer version saved; the user must explicitly Save again. Export is not recorded as SaveCompleted. Cancel preserves the pending stage. Closing/New warns with the local sidecar path and keeps the pre-existing dirty-buffer discard contract; no stage deletion or implicit Save occurs. On Windows a retained-stage warning (editor-owned OK-only) precedes `Discard unsaved changes?` (YES=6 permits buffer discard, NO=7/CANCEL=2 refuses). Diagnostic drivers must match owner/PID and exact modal purpose, not dismiss arbitrary modals.

Open failures after restart now positively discover an existing same-target deterministic slot and show its local path as **unowned and unverified**. The controller does not read sidecar contents, associate it with the buffer, or delete it. A different missing target receives no unrelated-sidecar hint; successful Open remains unchanged even when the slot exists. A negative File.Exists result produces no hint and is not a claim that recovery is absent.
