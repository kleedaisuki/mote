# Target-host screen-reader acceptance: source and preview

Status: protocol design, **not an executed Narrator or VoiceOver pass**, 2026-09-30. This is for the ordinary `Continuous` native editor and its **separate read-only Preview**. It does not change production code, CI, local accessibility permissions, or OS input settings. Keep [`--legacy-page` as the rollback comparator](../src/Mote.Native/README.md), not as evidence that Continuous is accessible.

## Why this gate is distinct

The published-binary [Windows UIA probe](../tests/WindowsAxExternalProbe/README.md) and [macOS AX probe](../tests/MacAxExternalProbe/README.md) establish useful source-backed range, selection, focus/tree, stale-object and bounded-error facts on target hosts. They do **not** run a screen reader. The [current release audit](release-gaps.md) therefore keeps real Narrator/VoiceOver, IME coexistence, reader navigation and preview speech open. A Windows source `Document` plus a **different**, read-only Preview `Document` may be correct; a second bounded **source** Document is not. The Windows preview's `Mote preview` name is a best-effort native annotation, while macOS sets that label on its read-only `NSTextView`; either must still be confirmed by the reader, not inferred from source code. [Microsoft's Document control contract](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-supportdocumentcontroltype) requires a Text pattern, and [Apple's VoiceOver evaluation criteria](https://developer.apple.com/help/app-store-connect/manage-app-accessibility/voiceover-evaluation-criteria) call out actual custom-text speech, navigation, selection and focus behavior.

| Evidence level | What it can establish | What it cannot establish |
| --- | --- | --- |
| Unit/provider ABI | Methods, ranges, HRESULT/AX errors and lifetime invariants | A target OS client, spoken output or usable interaction |
| Cross-process UIA/AX on published AOT | Actual API responses, tree identity, focus properties, offscreen bounded strings | Which methods the reader calls, what it speaks, or whether the user can finish a task |
| **Actual Narrator/VoiceOver task plus speech record** | Spoken source/preview identity, reader-driven text navigation, selection and editing feedback | Other readers, other IMEs, blind-user usability or latency distributions from one run |
| Assisted user session and repeated workloads | Discoverability, recovery and workload variability | Universal accessibility on all configurations |

Microsoft explicitly recommends **automated checks plus focused manual assistive-technology testing** and testing the main app tasks with Narrator, not treating UIA inspection alone as the experience. [Microsoft accessibility testing](https://learn.microsoft.com/en-us/windows/apps/design/accessibility/accessibility-testing). Research on assistive-technology-aided record/replay similarly shows why an accessibility tree or static scanner can miss failures that arise during interaction; its evaluated platform was **Android TalkBack**, so it suggests a future method rather than validating this desktop product. [Salehnamadi et al., CHI 2023](https://doi.org/10.1145/3544548.3580679).

## Test object, environment and result classification

1. Publish the **same source revision** as a strict one-file Native AOT executable for each target RID. Record Git commit, executable SHA-256, size, OS build, CPU architecture, reader version, UI language/voice, keyboard layout, display scale, and whether the ordinary route or a diagnostic flag was used. The ordinary route is the release candidate; a passing opt-in historical fragment is not a substitute. Verify the exact target process/window and foreground before each action. Do not inspect unrelated desktop content.
2. Use only disposable, synthetic files under `.temp/screen-reader/` and reports under `.cache/screen-reader/`. Record fixture UTF-16 length, line count, file SHA-256, exact target line/offset and expected post-edit byte hashes. Capture an app-only window plus the reader's speech panel or a consented audio track; no real document, path, clipboard history, other apps, or background desktop should enter an artifact. Restore the tester's reader/IME/voice settings after a session.
3. For the **first falsifier**, generate one LF Markdown file of roughly **24–32 Ki UTF-16 units** with 400 short lines, a pronounceable first-line marker (`cobalt forest beacon`) and a last-line marker (`violet river amber`). Place the last marker beyond the current bounded input island and the preview's 16 Ki/120-line budget; verify that with the existing external API probes before testing speech. This keeps `GetText(-1)` below the 65,536-unit budget, so an initial failure is not automatically an oversized-range failure. The preview can legitimately contain the first marker, but must not masquerade as the full editable source or speak the remote marker as if it were preview text. The test asks a reader to **navigate to** the remote source line, not to read 400 lines aloud.
4. Use separate 1 MiB and 100 MiB **many-short-line** fixtures for the scaling phase. Put distinct pronounceable markers near start, middle and end, with CR/LF/CRLF and supplementary emoji in an additional small correctness fixture. Do not ask the reader to “Read All” over 100 MiB or select/copy the whole file; those are unbounded tasks. First establish that a single line/word/character request and a distant jump respond without crash, false truncation or loss of the current reader. Treat a **10-second no-response watchdog** as a liveness failure/abort, not a claimed acceptable latency. Record command-to-first-speech, command-to-caret/selection change, process working set and error/dialog state over at least five fresh processes per size before setting a p95 product target.
5. Classify every step as `pass`, `product-fail`, `harness/permission-blocked`, or `inconclusive`. A missing reader/caption facility, denied macOS Accessibility trust, stolen global focus, or an unreadable recording cannot become a pass. A reader that is speaking another window is not a Mote product failure until the exact-PID/foreground preconditions are re-established. Preserve negative trials and the order of commands; never retry a non-idempotent edit or Save blindly.

The witness must include **the reader's emitted speech** (audio heard by a trained tester and, where available, the reader's own text recap/caption), not only a UIA `GetText` or AX `StringForRange` response. Exact punctuation/voice phrasing is configurable; the semantic oracle is the correct marker, correct source versus preview identity, and no duplicate bounded-host document or unexplained restart. Use a tester fluent in the reader's navigation model for final judgment. Apple recommends completing real tasks with VoiceOver rather than only inspecting properties. [Apple accessibility testing](https://developer.apple.com/documentation/accessibility/performing-accessibility-testing-for-your-app).

One result record per action should contain `scenario`, `OS/reader/version`, `binarySha256`, `fixtureSha256`, `sourcePID`, `foregroundPID-before/after`, `command`, monotonic start/first-speech/end times, a short **synthetic-only** spoken-marker transcript or app-only caption/audio artifact reference, UIA/AX identity as a **corroborating** field, and the four-way result classification with a reason. Collect UIA/AX properties before/after the spoken task rather than flooding the live reader with a simultaneous inspector; otherwise the inspector itself may perturb focus or response time.

## Smallest discriminating experiment on Windows: Narrator

Use an interactively logged-in Windows 11 target, the ordinary `mote <synthetic-file>` route, and a build with the [Narrator speech recap](https://support.microsoft.com/en-us/accessibility/windows/narrator/complete-guide-to-narrator) feature if available. Start/stop Narrator with `Win+Ctrl+Enter`; open its **Speech Recap** with `Narrator+Alt+X` and keep the last-spoken strings/live transcription visible without operating that window during the task. A tester should also listen: recap text is the reader's own output, but does not judge intelligibility or a missed audio cue. If this Narrator build lacks recap, use consented audio plus a human timestamped transcript, not UIA text as a replacement. Record the chosen Narrator modifier (Caps Lock or Insert), verbosity and scan-mode state. [Narrator reading commands](https://support.microsoft.com/en-us/accessibility/windows/narrator/chapter-4-reading-text), [speech recap](https://support.microsoft.com/en-us/accessibility/windows/narrator/complete-guide-to-narrator).

| Action on the 24–32 Ki fixture | Minimum speech/behavior oracle |
| --- | --- |
| Keyboard-focus the **source**, issue `Narrator+Tab`; do not navigate Preview yet. | One source identity, `Mote editor` or an equivalently unambiguous editable document. No second `RichEdit Control` source announcement. Capture external UIA focused/runtime IDs only as a cross-check. |
| Issue the reader's **move to end of text** (`Narrator+E` in the recorded standard layout), then `Narrator+I` for the current line; use `Narrator+U/O` to check neighboring lines. | The reader itself reaches and speaks `violet river amber` from the remote source. An empty/error response, return to line 1, or text from the bounded input ribbon fails. If the command is unavailable in the tester's layout, record the discovered equivalent using `Narrator+F1`; do not silently substitute a native `Ctrl+End` and call reader navigation passed. |
| Move to the read-only Preview by keyboard (its RichEdit is a separate tab stop), then `Narrator+Tab` and read one preview line; return to source. | Clearly announced `Mote preview`/read-only context, no remote source marker as preview content, no duplicate editable source. If the preview cannot be reached or named, record that separately even if source speech succeeds. |

These three actions are the **first gate**. They distinguish a clean UIA tree from a reader that cannot navigate a source-backed `TextRange`; they also challenge the missing text-range movement/geometry/event surface noted in the [provider design](accessibility-provider-design.md). As a *diagnostic after a failed reader-end command*, native `Ctrl+End` followed by `Narrator+I` can separate reader navigation failure from source-caret speech failure, but it does not rescue the reader-navigation result. Microsoft's Narrator guide documents current/next/previous line and selection commands; the tester must use the layout actually installed. [Narrator standard layout](https://support.microsoft.com/en-us/accessibility/windows/narrator/welcome-to-the-new-standard-keyboard-layout-for-narrator).

## Smallest discriminating experiment on macOS: VoiceOver

Use a logged-in target Mac running the ordinary one-Mach-O Continuous route. The operator may start/stop VoiceOver with `Command+F5` **for the test session** and must restore the prior state afterward. Show VoiceOver's **Caption Panel** before opening Mote; Apple says the panel shows what VoiceOver is speaking. Record a narrow synthetic-app-plus-caption capture and have a tester listen as well. The `VO` modifier is Control-Option or Caps Lock according to the recorded setting. [VoiceOver basics](https://support.apple.com/guide/voiceover/get-started-with-voiceover-vo4be8816d70/mac), [Caption Panel](https://support.apple.com/en-kw/guide/voiceover/unac078/mac).

| Action on the same fixture | Minimum speech/behavior oracle |
| --- | --- |
| Navigate to `Mote editor`, use `VO-Shift-Down Arrow` to interact with the text area, then `VO-L` on the first line. | The proxy is reached as **one source text area**, the first marker is spoken, and the native input island is not a second spoken editor. Record first-responder/focused AX element only as a cross-check. |
| Use VoiceOver's **move to end of text** (`VO-End`, keyboard-equivalent noted by Apple) and `VO-L`, then `VO-Up/Down Arrow` for adjacent lines. | `violet river amber` is spoken from the remote source without an unexplained return to the first line or preview. A successful native `Command+Down Arrow` fallback is diagnostic only, not a pass for VoiceOver navigation. [VoiceOver text commands](https://support.apple.com/en-ca/guide/voiceover/cpvokys06/mac). |
| Stop interacting (`VO-Shift-Up Arrow`), navigate to `Mote preview`, interact/read one line, then return to source. | The read-only preview is named/distinguishable, its bounded content is not presented as the editable full source, and source focus/orientation returns predictably. |

The [external Swift AX test](../tests/MacAxExternalProbe/README.md) has already shown a full source count/offscreen bounded strings on both architectures, but VoiceOver may request different selectors or a whole long logical line. A 50 MiB single-line `AXVisibleCharacterRange` is **whole-logical-line metadata**, not painted-pixel extent; do not call its large value a painting defect or speech pass. The provider may refuse a >65,536-unit string request without truncation, so the first VoiceOver test intentionally uses a smaller file; the large-file phase must later show that VoiceOver can recover with bounded requests. [Mac AX visible-range interpretation](accessibility-provider-design.md).

## Subsequent task matrix, after the first gate

| Task | Functional and speech oracle | Failure boundary to preserve |
| --- | --- | --- |
| Source caret, word and character | At beginning, after a reader-driven remote jump, and after native `Ctrl/Cmd+End`, request current line, next word and current character. Spoken marker/location follows the **source** caret or reader cursor once; no input-ribbon echo. | Capture UIA/AX source selection and physical focus alongside speech, but do not substitute either for speech. A reader cursor and keyboard insertion caret may legitimately differ until synchronized; report the exact command that joined them. |
| Global selection across a viewport/input-host edge | Begin near a measured bound/visible-row edge, select a short phrase across it with standard `Shift` selection (or reader selection), then ask Narrator `Narrator+Shift+Down Arrow` / VoiceOver `VO-Fn-F6` to read the selection. Copy the small phrase and compare exact bytes. | No whole-100-Mi selection, no hidden host-only selection, no duplicate/partial phrase. [Narrator selection command](https://support.microsoft.com/en-us/accessibility/windows/narrator/welcome-to-the-new-standard-keyboard-layout-for-narrator), [VoiceOver selection](https://support.apple.com/guide/voiceover/select-text-mchlp2741/10/mac/27), [VoiceOver read selection](https://support.apple.com/en-my/guide/voiceover/vo2718/mac). |
| Edit, Undo, Save/reopen | At the announced source marker insert one pronounceable word using the **physical keyboard**, hear one edit/caret acknowledgement, Undo and hear the original line, Redo once, Save, close and reopen; verify streaming full-file SHA-256 at each expected state. | Reader speech is checked separately from byte correctness. A silent edit or stale spoken line fails even when Save bytes are correct; a correct announcement with wrong bytes also fails. |
| Preview and status | Move to Preview and back after analysis completes; announce its name/read-only state and the bounded rendered text, while source remains editable. Attempt one `X` while Preview owns focus and verify **neither Preview nor source bytes change**. Announce or discover nonfatal format/status changes without repeated speech spam. | A second **preview** text/document is allowed, a duplicate **source** editor is not. If preview content is truncated or provisional, do not imply a complete semantic rendering. |
| 1/100 MiB bounded response | From a fresh ready source, reader-jump to a known middle/end line and request **one** line/word; repeat after one edit/Undo. Record time to first spoken content, no-response watchdog, memory, CPU and whether the same cached reader remains usable. | A `GetText(-1)` budget refusal must not be reported as complete text or silently truncated speech. One 100 MiB read-all/whole-selection request is not a valid bounded-response test. Re-run on x64/ARM64 target hosts after the small fixture passes. |
| Real IME candidate coexistence | In an explicit Chinese Pinyin test session, type a **real physical-key** candidate while Narrator/VoiceOver is on; navigate/confirm or Escape. Observe OS candidate placement, reader feedback, source/ribbon focus, composition lifetime, and exact committed/cancelled bytes. | Do not inject synthetic `WM_IME_*` messages. Do not make a claim from the prior Windows Pinyin run without a simultaneous reader, or from Mac AX properties without a real Mac IME. If reader shortcuts consume a composition key, preserve that as a product interaction defect rather than forcing a commit. |

The first gate is deliberately small and falsifying; only then expand to large files and IME. A source API pass with a silent Narrator/VoiceOver remains a screen-reader failure. A reader that speaks the first line but cannot move to a distant line remains a **whole-document** failure. A reader that speaks the source but cannot distinguish the preview is a **two-surface** failure. Do not convert a negative into `E_NOTIMPL` “acceptable” by changing the test to native keyboard navigation after the fact.

## Hosted versus attended evidence

GitHub-hosted runners provision a fresh VM for each job; the current repository can execute AOT builds, inventories and cross-process UIA/AX/keyboard probes there. [GitHub-hosted runner model](https://docs.github.com/en/actions/how-tos/manage-runners/github-hosted-runners/use-github-hosted-runners). The existing hosted Mac Swift probe explicitly treats denied `AXIsProcessTrusted` as infrastructure unavailable; Apple documents that trust query and its asynchronous prompt behavior. [Apple Accessibility trust API](https://developer.apple.com/documentation/applicationservices/1459186-axisprocesstrustedwithoptions). Those facts do **not** prove a usable Narrator/VoiceOver speech channel, a stable foreground interactive session, a human listening, or real candidate speech on GitHub's current VMs.

| Environment | Appropriate near-term use | Not an accepted inference |
| --- | --- | --- |
| Existing hosted CI | Keep single-binary, UIA/AX source/preview identities, bounded range and exact-byte keyboard probes; upload explicit blocked/inconclusive artifacts. | A passing API check or generated synthetic speech string is **not** actual reader output. |
| Dedicated, logged-in target host (self-hosted runner or supervised workstation) | Run real reader, show Speech Recap/Caption Panel, record app-only synthetic speech evidence, then repeat task matrix with physical keys and real IME. | One attended pass is not a performance/reliability distribution or user study. |
| Future automated reader replay | Automate **actual** Narrator/VoiceOver commands only after proving the reader process, caption/recap capture, exact target PID/focus, audio/AX permissions and a human-reviewed control trial. | OCR of a panel, UIA/AX queries alone, or a simulated reader client cannot independently certify usable speech. |

The next useful action is **one attended 24–32 Ki fixture session per OS**, with the two reader-end-line commands and source/preview identity captured as actual reader speech. If either fails, preserve the exact utterance/error and command sequence, use the native-key fallback only to locate the layer, and fix that layer before adding CI choreography. Only after these passes should the large-file and live-IME matrix become a release gate.
