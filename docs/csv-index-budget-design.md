# CSV retained-index budget: dense rows or sparse certified checkpoints

Status: design, **not implemented or measured** (2026-09-30). This follows the implemented [two-window CSV projection](csv-sparse-projection.md) and the policy-private [semantic IR direction](semantic-ir-evolution.md). Scope is one CSV `IWindowedFormatSession`; `Document`/`TextSnapshot` remain the sole text owner. The 32 MiB figure is a target for **reachable format-index state retained by one session after a call**, not a promise about the text rope, a returned projection still held by a caller, transient allocation, or process RSS.

## The actual failure mode

`CsvIncrementalSession` currently retains every logical record as a six-`int` `Row` in 1,024-row `Segment` arrays, plus each segment's width histogram. The existing 100 MiB benchmark fixture has about 2,139,952 49-character records. Even if `Row` occupies only 24 bytes, its row arrays alone need about **48.98 MiB**, before segment objects, dictionaries, arrays, and list capacity. A 100 MiB file of `a\n` records is much worse. A warmed two-window timing of 0.1015 ms median therefore says nothing about the memory budget or cold `Full` cost. A cap applied only *after* `ParseAll` would not solve this.

There are two distinct kinds of knowledge to preserve: (1) the exact whole-document semantic count for a specific snapshot version, and (2) enough verified record starts to reach a requested viewport without rescanning from byte zero. Neither requires one object per record. Conversely, a physical-line or arbitrary byte offset is **not** a safe CSV seek point: a quoted field can contain CRLF ([RFC 4180](https://datatracker.ietf.org/doc/html/rfc4180)).

## Decision

Use a private, tagged cache state rather than interpreting an empty `_segments` list as both “empty file” and “uncached complete”:

| State | Retained facts | Allowed claim |
| --- | --- | --- |
| `None` | No index or count | No old-version semantic claim. |
| `Prefix` | Existing bounded whole-record prefix | Only its current-version certified prefix. |
| `DenseFull` | Existing `Segment` rows; no retained checkpoint copy | Current-version `Complete`, exact count; existing record-level incremental reuse. |
| `SparseFull` | Certified checkpoint offsets, first-row width, exact diagnostic count, version | Current-version `Complete`; viewport rows must be reparsed from a checkpoint. |

Build a checkpoint at the `After` offset of a **fully parsed logical record** whenever at least 64 Ki UTF-16 units have elapsed since the previous checkpoint; offset zero is implicit. For a 100 Mi-unit file with short records this is roughly 1,600 `int` offsets (about 6.3 KiB payload). A giant quoted record may create a larger gap; reparsing that record is unavoidable without storing an internal quote-state index. Even the existing *dense* index reparses an intersecting giant record to obtain bounded cell payload, so a warm tail viewport inside that record can still cost O(record length). This is a concrete, CSV-specific representation, not a general IR or a second copy of the file.

While performing `Full`, calculate `expectedWidth` from the first row and stream `total += row.ErrorCount + (row.Width != expectedWidth ? 1 : 0)` for each later row. Build sparse checkpoints in a **local candidate from the first record**, even while dense indexing is still enabled; discard that candidate if the result stays `DenseFull`. Stop retaining dense segments *before* their budget threshold is crossed; discard the dense prefix and continue the **same full scan**, preserving the running count/checkpoints. Thus a 100 MiB short-row file can finish with `SparseFull` without a second whole-file parse or a >32 MiB retained row index. The existing `Project` can remain the dense path; a private sparse row enumerator binary-searches the greatest checkpoint at or before each requested window start, with one-checkpoint lookbehind when that checkpoint **equals** the start. That lookbehind preserves the existing zero-length-window behavior that can own the preceding row whose `After` equals the window start, including at EOF. It calls the existing `ParseRow` from this verified boundary and stops after the first record beginning beyond that window. Reparse only intersecting records with `capture=true`; preserve the same 4,096-row/8,192-cell fair per-window caps, source spans, deduplication, and `Truncated` semantics. For a long row spanning both windows, the shared source-start key emits it once. No decoded field values are retained by the session.

The smallest defensible first cap is **256 live `Segment` objects**, not a purportedly exact managed-object byte counter. Each segment references at most one 1,024-element `Row[]`; sliced segments may share arrays, but counting each segment as if it owns one is conservative. The 256-segment threshold limits dense representation to about 262,144 rows. On current .NET 10 layout, a 24-byte `Row`, a generously charged 32 bytes per histogram slot (at most about 2,048 slots for at most 1,024 distinct widths), and object/list/checkpoint overhead give roughly 22–24 MiB, leaving meaningful room below 32 MiB. **This is an engineering bound to validate structurally and against CoreCLR retained-graph inspection, not a CLR layout guarantee or an AOT heap-dump measurement.** Enforce it *during* all dense builders: cold `ParseAll`, `ResumeAll` when a `Prefix` becomes `Full`, and `ParseIncremental` including reused suffix slices; none may first build an unbounded candidate and check only at commit. On overflow, finish or restart an authoritative streaming `Full` and commit `SparseFull`. A new-version checkpoint list is always generated from the new snapshot's verified record boundaries, never copied or merely offset-translated from an old version. If the structural estimate and CoreCLR retained graph challenge the 32 MiB target, lower the fixed segment cap rather than adding a runtime-specific accounting framework. A still simpler fallback—discard *all* row data and scan from zero for every new window—is correct but makes tail scrolling O(file size), so keep checkpoints.

### State and version invariants

1. A checkpoint is a position **after** a parser-verified record delimiter/EOF, never a guessed newline. Offsets are sorted, unique, within `[0, snapshot.Length]`, and tagged with that snapshot version. When a requested zero-length window starts exactly at a stored `After`, seek from the preceding checkpoint (or implicit zero), so the preceding record can still own that boundary; the same rule covers `start == snapshot.Length`. `SparseFull` exists only after a successful entire-file scan. Its `TotalDiagnosticCount` equals a fresh full oracle and includes row-local CSV001–CSV003 errors plus the current first-row-width CSV004 mismatches, including offscreen rows.
2. `Complete` concerns validation, not payload delivery. On the same version, sparse-window projection reparses from certified checkpoints and reports `SourceIndexed=true` for each requested window only after crossing its end or EOF; both windows are still bounded by the public 512 Ki aggregate request limit and fair projection caps. For an empty file, retain exact total zero and a whole-file certificate without inventing a row. Do not turn an unindexed zero-length window at the start of a giant record into `SourceIndexed=true`.
3. An edit to `SparseFull` invalidates its exact count and **all checkpoints at or after the affected record**. First-row width edits can change CSV004 everywhere. The safe initial implementation does not attempt suffix reuse in sparse mode: `Full` rescans authoritatively; `Visible` falls back to the existing bounded prefix/`Provisional` behavior. Never publish an old exact total under a new version, including Undo/Redo or a missing edit chain. A later optimization may certify a checkpoint *before* an edit and parse a local viewport from there, but must not claim a global count until the suffix has been checked.
4. Build the prospective state and output locally. Only after the final cancellation check atomically replace the session's `(version, mode, rows/checkpoints, exact count)`. Cancellation or parser failure must leave the previous committed version untouched. `Dispose` releases both representations. The public `Analyze` signature and legacy `Full` behavior remain unchanged: projecting all rows is currently allowed only when the source is at most 1 Mi UTF-16 units **and** has at most 4,096 rows **and** at most 8,192 cells **and** every row is at most 64 Ki source units. Otherwise even `Full` has bounded projection with exact whole-file semantics; sparse mode must preserve this distinction.

## Implementation seam and failure behavior

Keep the one-session serialized-caller contract. Add a private `CsvCacheMode` and a private `FullScan` result containing either segments or checkpoints plus exact total, not another public interface. Refactor `Project` minimally so its bounded delivery loop accepts a per-window row enumerator and a separately supplied exact total/certified extent; do **not** duplicate the cell parser or create a generalized row-query engine. Use a single cursor during cold `Full` and `ResumeAll`; checkpoint generation and count accumulation are constant-time per row, including the previously indexed prefix when resuming. Dense incremental reuse remains the current path if its candidate cache fits. When switching to sparse after a dense incremental candidate overflows, a fresh streaming `Full` is simpler and safer than trying to synthesize exact semantics from partially reused row summaries. Catch neither cancellation nor parse mismatch as “success”; preserve the previous committed state and let the caller receive the error.

The cost is explicit: sparse-mode `Full` after an edit is O(file length), and the immediate `Visible` result may be provisional away from the head. This is preferable to falsely claiming fresh semantics or retaining an unbounded graph, but it is **not yet an editing-fluidity acceptance result**. If target-host traces show unacceptable post-edit provisional duration, the next slice is checkpoint-prefix reuse with bounded local parsing plus an idle full revalidation. Do not introduce that invalidation machinery before the cap and correctness are measured.

## Verification and instrumentation gate

| Test or measurement | Required observation |
| --- | --- |
| 3/10/100 MiB 49-character rows; 100 MiB `a\n`; distinct-width rows; repeated edits that slice segments | After each committed call, cache mode, segment/checkpoint count, and a conservative `EstimatedRetainedIndexBytes` stay below 32 MiB. Inspect the managed retained object graph in a matching CoreCLR build; use structural accounting plus allocation and RSS measurements on all four Native AOT RIDs. Do **not** claim an AOT managed heap-dump result. |
| Distant head/tail windows; quoted CRLF crossing windows; one giant quoted record; zero-length window exactly on checkpoint and at EOF; overlap/touch | Exact row/cell absolute UTF-16 spans, once-only row owners, fair row/cell quotas, truthful `SourceIndexed`/`Truncated`; checkpoint seeker never starts inside quotes or loses the preceding row at an exact boundary. Record the giant-record warm-tail scan cost rather than folding it into ordinary short-row medians. |
| First-row width edit; offscreen malformed rows; missing edit chain; Undo/Redo; cancellation just before commit | `Full` total and diagnostic codes equal a fresh-session oracle at the same version; no prior-version count/checkpoint leak; cancellation retains old cache state. |
| 100 MiB cold `Full`, `Prefix`→`Full`, warm two-window head/tail, tail scroll, head/middle/tail edit followed by `Visible` and idle `Full` | Report p50/p95 parse/projection time, scanned UTF-16 units, allocations, structural index estimate, and RSS on four Native AOT RIDs; report the actual managed retained graph only on CoreCLR. Keep user input-to-compositor and source-readiness measurements separate; the current warm managed benchmark cannot substitute. |

For retained-graph validation, a **CoreCLR** .NET heap dump/`dumpheap` plus `gcroot` can identify objects reachable through the session ([Microsoft diagnostics](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/dotnet-dump)). Native AOT does **not** support managed heap analysis, although selected tracing/counters are available when enabled; validate its cache with structural accounting and measure allocations/RSS separately ([Microsoft Native AOT diagnostics](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/diagnostics)). Allocation counters report **allocations over time**, not retained bytes ([GC allocation API](https://learn.microsoft.com/en-us/dotnet/api/system.gc.gettotalallocatedbytes?view=net-10.0)). Keep dumps/test files under repository `.cache/` or `.temp/`; never publish source-bearing dumps as CI artifacts. Make the budget visible in opt-in diagnostics as aggregate counts only, not file content.

## Why this balance

Apache Arrow explicitly contrasts a whole-table CSV reader with a `StreamingReader`: bounded memory is bought with different throughput and reuse properties ([Arrow CSV documentation](https://arrow.apache.org/docs/cpp/csv.html)). The SLE 2021 *Fast Incremental PEG Parsing* paper improves large-file incremental parsing partly by pruning memoization; it supports the principle that selective retention can beat “memoize everything,” but its grammar/workloads do **not** establish this CSV threshold, semantic count correctness, or Native AOT latency ([Yedidia and Chong, 2021](https://people.seas.harvard.edu/~chong/pubs/gpeg_sle21.pdf)). Here the useful hybrid is concrete: dense row summaries while affordable, certified record-boundary checkpoints when they are not, and exact streaming validation in either mode. Reject a universal compressed AST, an opaque GC-heap threshold, or a misleading `Complete` based on viewport-only sampling.

**Next smallest implementation slice:** introduce `CsvCacheMode`, enforce the fixed dense-segment cap in `ParseAll`, `ResumeAll`, and `ParseIncremental`, and generate checkpoint/count candidates from the current snapshot; add 100 MiB short-row exact-count, `Prefix`→`Full`, incremental-overflow, and post-cancellation tests before wiring sparse window projection. This first slice may temporarily fall back to one-pass no-cache projection for oversized input, but must not ship a false complete result or an uncapped `_segments`. Then implement checkpoint-seeking projection and measure the four RIDs before enabling a user-facing performance claim.
