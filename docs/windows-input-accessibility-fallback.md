# Windows input architecture if fragment-root UIA cannot unify the editor

Status: **contingency design, not an implementation decision or acceptance claim**, 2026-09-29. This is deliberately separate from the active [fragment/HWND override experiment](windows-uia-tree-design.md). Do not change its conclusions until external Raw/Control/Content/focus and reader results arrive. The target is one source-backed UIA Document for a strict one-file Native AOT executable **without sacrificing the already observed Microsoft Pinyin path**.

## Preserve what works, name what does not

`WindowsRichEditIsland` currently owns a visible, focused `RICHEDIT50W` child of the canvas. Its bounded projection handles ordinary editing and native IME. A local Windows x64 opt-in-canvas probe selected actual Chinese mode, captured Microsoft's `ni'hao` candidate strip, committed `你好`, cancelled a real candidate, and saved/reopened exact bytes ([input evidence](native-input-accessibility.md), disposable `.temp/ime-probes/run-20260929-204700-709/` et al.). This is strong evidence for **that binary and those three workflows**, not physical-keyboard, Narrator/NVDA, other IMEs or ARM64 acceptance. An external UIA probe of a published x64 AOT binary then showed two Documents: the canvas source provider and focused 16-unit RichEdit host in Raw/Control/Content (`.cache/ax-uia-external/invalid-operation.txt`). The engine is canonical; the host is only an input service. The duplicated semantic identity is a UIA tree defect, not a reason to rewrite a working text-input stack first.

Two invariants outrank any attractive tree screenshot:

1. **One committed source:** `Document/TextSnapshot` owns global UTF-16 text, save, undo, selection and source ranges. RichEdit/any replacement owns only bounded provisional composition and emits one versioned final edit. UIA never advertises the island's page as the whole file.
2. **One functional focus:** an external client must find one focused semantic Document, while the OS's active text service still receives real keystrokes, preedit/candidate geometry and cancel/commit. A ContentView count of one is insufficient if Narrator follows an inaccessible RawView focus proxy or stops speaking composition. Microsoft's [TextEdit pattern](https://learn.microsoft.com/en-us/windows/win32/winauto/textedit-control-pattern) explicitly models active composition, conversion target and events; Mote's current source TextPattern does **not** inherit that behavior from RichEdit automatically.

## Ranked fallbacks, only after the active fragment probe fails

| Route | Mechanism and likely advantage | Hard unknown / cost | Judgment |
| --- | --- | --- | --- |
| **A. Put the source provider on the already focused RichEdit HWND** | Intercept only the child's UIA `WM_GETOBJECT`/`UiaRootObjectId` in its existing subclass and call `UiaReturnRawElementProvider(inputHwnd,...)` with the **source-backed** provider. Demote the canvas provider to Pane/no TextPattern, or let the canvas use its default non-Document host provider. Physical focus, visible RichEdit, IME message delivery and bounded text stay unchanged. `GetHostRawElementProvider` uses the input HWND. [Microsoft's WM_GETOBJECT guidance](https://learn.microsoft.com/en-us/windows/win32/winauto/handling-the-wm-getobject-message) supports returning a custom provider for that specific HWND/request. | RichEdit's own UIA/MSAA/default provider may still be combined with the new provider or supply page-local patterns/events. A custom source provider might suppress native TextEdit composition speech. `ProviderOptions_OverrideProvider` is a flag, not proof of substitution. Needs external A/B evidence. | **First fallback experiment:** smallest change to the input architecture and preserves the demonstrated Pinyin host. Do not ship until one-node/focus/speech behavior is measured. |
| **B. Windowless RichEdit text services inside the canvas HWND** | Microsoft explicitly supports [`CreateTextServices(ITextHost)`](https://learn.microsoft.com/en-us/windows/win32/controls/about-windowless-rich-edit-controls): `ITextServices` supplies RichEdit behavior **without its own child HWND**; host forwards keyboard/mouse through `TxSendMessage` and receives notifications through `ITextHost::TxNotify`. Canvas becomes the physical focus HWND and owns the one source UIA Document. Still keep only bounded input text. | Substantial `ITextHost`/`ITextHost2` COM implementation, paint/DC/scroll/caret/candidate geometry and lifecycle. [`ITextHost2::TxGetWindow`](https://learn.microsoft.com/en-us/windows/win32/api/textserv/nf-textserv-itexthost2-txgetwindow) connects text services to the host HWND, but **does not prove** Pinyin parity. Windowless RichEdit also has its own optional UIA interfaces (`IRicheditWindowlessAccessibility`, `IRicheditUiaOverrides`); do not accidentally register a second page-local provider ([textserv.h](https://learn.microsoft.com/en-us/windows/win32/api/textserv/)). Native AOT requires source-generated COM or explicit vtables, and host pointer lifetime must be ended with [`ShutdownTextServices`](https://learn.microsoft.com/en-us/windows/win32/api/textserv/nf-textserv-shutdowntextservices). | **Second fallback**, only if A demonstrably cannot unify UIA while preserving IME. It removes the separate HWND rather than trying to hide it. |
| **C. Canvas HWND + application-owned TSF text store** | Implement [`ITextStoreACP`](https://learn.microsoft.com/en-us/windows/win32/tsf/text-stores) against the engine's UTF-16 source and a provisional composition layer, with canvas focus/caret rectangles. No RichEdit provider exists. This gives direct control over input and source-backed UIA. | Largest surface: TSF manager/context, advise sink, [document lock protocol](https://learn.microsoft.com/en-us/windows/win32/tsf/document-locks), reentrant edits, composition, candidate rectangle, multilingual IMEs and UIA TextEdit events. UI-thread deadlocks and Native AOT COM ABI are high risks. | **Last-resort architectural replacement**, not a quick fix for a UIA tree shape. Prototype only after A and B fail causal tests. |

Avoid a fourth pseudo-route: moving the HWND offscreen, shrinking to 1×1, making it transparent, disabling IME (`ES_NOIME`), or asking the app to handle all IME operations (`ES_SELFIME`). The latter style meanings are documented by [Microsoft](https://learn.microsoft.com/en-us/windows/win32/controls/rich-edit-control-styles); none is a documented way to keep RichEdit candidate/focus behavior while removing its accessible identity. A hidden HWND can still be discovered from its handle or receive focus, and a misplaced native caret may move the candidate window. Likewise, returning zero for every child `WM_GETOBJECT` request can trigger fallback proxies or damage MSAA/other object IDs; [Microsoft distinguishes UIA and MSAA object IDs](https://learn.microsoft.com/en-us/windows/win32/winauto/handling-the-wm-getobject-message). Do not treat a single filtered tree as evidence of safety.

## Minimal discriminating experiment for route A

Use a fresh-process, opt-in diagnostic build of the existing one-file Windows shell; do not change the default path. Hold `AccessibleCanvasState(generation,snapshot,frame)` and the provider-local detach token exactly as now. A child-HWND UIA responder catches **only** `UiaRootObjectId` and returns a source provider bound to `_input`; every other `WM_GETOBJECT` ID and every keyboard/IME/mouse message continues through `DefSubclassProc`. The canvas no longer advertises a Document in this branch. Compare `ServerSideProvider` versus `ServerSideProvider | OverrideProvider` only if the first run shows a merged/native RichEdit provider; neither configuration is assumed correct. New/Open changes document generation and invalidates old ranges; recoverable provider detach must not invalidate the controller-shared document.

The external probe must independently query `FromHandle(canvas)`, `FromHandle(input)`, `GetFocusedElement`, `ElementFromPoint`, Raw/Control/Content walkers, runtime IDs, host HWND, ControlType, all Text/TextEdit pattern availability, DocumentRange length/remote marker, global selection, and focus/text/composition events. Perform this **before, during and after** a real Microsoft Pinyin candidate, then Save/reopen; add Narrator and NVDA speech observations. Pass requires exactly one source Document in Control/Content, the same source Document as focused element while Win32 focus remains input, no page-local TextPattern, correct offscreen ranges, real candidate/cancel/commit and spoken caret/preedit without duplication or silence. Include small CR/LF/CRLF+astral fixtures and a 100 MiB offscreen marker. A UIA tree query may miss the candidate; use privacy-scoped foreground-app capture and source bytes as in the existing positive Pinyin probe. Repeat on published win-x64 and win-arm64. Logs/screenshot/fixture stay under repository `.temp/` or `.cache`, not user telemetry.

**One falsifying result is enough to reject route A as product-ready:** an extra RichEdit Document/16-unit TextPattern, `GetFocusedElement` not the source Document, merged provider returning stale/page-local text, or lost/silent IME candidate. If only the native TextEdit pattern disappears, test whether a source-backed `ITextEditProvider` can truthfully expose active composition before rejecting A; do not claim the current `ITextProvider` does it. If COM callback failure occurs, detach only the provider and leave the RichEdit input/engine alive. Never save provisional text as a workaround.

## Migration if A fails and B is justified

Build B as a **parallel opt-in input adapter**, not an in-place rewrite of the working island. Preserve the existing typed `CanvasCommittedEdit(G,V,nonce,TextChange,active)` and projection/CRLF law, so the controller, engine, format sessions and source UIA ranges do not know which native input adapter is active. Replace the RichEdit child HWND only within the experimental canvas branch: canvas gains keyboard focus, `ITextHost` supplies current caret-local geometry, `ITextServices::TxSendMessage` receives the same physical input, and `TxNotify` maps final native changes into the existing transaction. Call `ShutdownTextServices` before releasing the host/canvas; its documentation says the text-services instance retains an **unowned host pointer**. A bounded source window remains mandatory; a windowless RichEdit with a full 100 MiB text buffer merely recreates the mirror failure without a child HWND.

The first B probe should be a **tiny independent AOT host under `.temp/`**: one canvas HWND, one windowless text-service object containing a short disposable fixture, actual Chinese-mode Pinyin candidate/commit/cancel, exact caret rectangle, and one UIA Document from canvas. This distinguishes “windowless RichEdit retains OS IME” from “a C# Native AOT `ITextHost` merely compiles.” Only then integrate global edits, long-file rebasing and AX. Route C requires its own design review; in particular TSF's lock and provisional-composition protocol must not be implemented as a few `WM_IME_*` handlers. The present visible RichEdit mode remains the rollback until the replacement beats its verified workflows on both Windows architectures.

## External precedent, with limits

VS Code's [screen-reader mode and accessible view](https://github.com/microsoft/vscode-docs/blob/main/docs/configure/accessibility/accessibility.md) and its [bounded textarea edit context](https://github.com/microsoft/vscode/blob/main/src/vs/editor/browser/controller/editContext/textArea/textAreaEditContext.ts) show a production editor treats input focus and accessibility content as an explicit design problem; browser DOM/ARIA behavior is **not** a Windows HWND/UIA contract. Windows Terminal's [TSF data provider and caret-rectangle code](https://github.com/microsoft/terminal/blob/main/src/cascadia/TerminalControl/TermControl.cpp) demonstrates that a production custom surface can own a TSF adapter, but its terminal semantics do not establish a general editor's selection/reconversion/AX correctness. A recent [CHI 2026 study of programmers using screen readers](https://doi.org/10.1145/3772318.3790726) reinforces that editor complexity and assistive-technology behavior matter to actual users; it cannot decide COM provider precedence. The discriminating target-OS reader/IME experiments above, not analogy, choose the fallback.
