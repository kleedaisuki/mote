# One painter for source text; a visible input ribbon for the native host

Status: **recommended opt-in canvas design, not implemented or OS-accepted**, 2026-09-29. Scope is the current strict one-binary `Mote.Native` Win32/AppKit canvas with a bounded RichEdit/NSTextView input host. It does not change the default page editor. The source/selection transaction stays as in [input-island-design.md](input-island-design.md), horizontal anchor as in [horizontal-navigation-design.md](horizontal-navigation-design.md), and one semantic editor remains the [UIA/AX release gate](accessibility-provider-design.md).

## Evidence and the correction that matters

The initial Windows 50 MiB far-pan screenshot `.temp/windows-horizontal/a3f5a0040d534108b081b31feec19df0/far.png` was overinterpreted. Its visible canvas prefix `P9SJGYM` and host suffix `M2PD8...` are **contiguous offsets of one source line**, and the probe had clicked the remote row *before* capture. That image does not prove a stale binding or wrong text. It does show a borderless RichEdit child painting in the same logical row as DirectWrite. A newer focused Win32 probe using 40 repetitions of `iW中🧪éمرحبا\t` checked 41 grapheme boundaries near the active caret: after matching the caret within 8 px, RichEdit `EM_POSFROMCHAR` and the DirectWrite row transform diverged by up to **63.3 px** at neighboring boundaries (owner's `.temp/WindowsHorizontalProbe` result). One aligned caret is therefore not a whole-row glyph-parity certificate. The canvas also owns semantic color, diagnostics and global selection; a child-window paint can cover those overlays. This is the causal issue, not source-string identity.

Windows' [`WS_CLIPCHILDREN` behavior](https://learn.microsoft.com/en-us/windows/win32/winmsg/window-features) makes the child the painter inside its rectangle; parent drawing cannot reliably repair text beneath it. [`EM_POSFROMCHAR`](https://learn.microsoft.com/en-us/windows/win32/controls/em-posfromchar) reports a **local character point**, not equivalence of the surrounding typography. On macOS, the current `PlaceHost` hides `_hostScroll` when TextKit/CoreText alignment fails or the source row is absent. Apple's [`NSView.isHidden`](https://developer.apple.com/documentation/appkit/nsview/ishidden) explicitly says hiding the current first responder transfers first-responder status to another key view. Thus hiding the `NSTextView` to avoid paint is not a safe IME/focus fallback. Apple's [`NSTextInputClient.firstRect(forCharacterRange:)`](https://developer.apple.com/documentation/appkit/nstextinputclient/firstrect%28forcharacterrange%3Aactualrange%3A%29) returns the candidate-relevant screen rectangle; a visually absent or moved first responder cannot be assumed to preserve that geometry.

## Decision for this experimental slice

Use an **always-visible, reserved one-row input ribbon below the canvas source viewport**. The canvas/DirectWrite or Core Text is the **sole painter of every document row**. RichEdit/NSTextView is the sole painter inside the ribbon and retains real focus and bounded provisional text. No same-row overlay, no transparent/zero-size/offscreen host, no host rebind merely because the user pans horizontally. This is a deliberate UX trade-off: IME candidates appear at the labeled ribbon rather than visually beside the canvas caret. It is simpler and more honest than a conditional overlay whose typography, semantics, geometry and AX ranges must all agree. The ordinary page editor remains the rollback until real users and screen readers accept that trade-off.

```text
window editor area
┌────────────────────────────────────────────────────┐
│ source canvas: viewportHeight = available - ribbon │
│ one immutable CanvasFrame; hit-test/selection/AX    │
│ visible ranges are source-backed and clipped here  │
├────────────────────────────────────────────────────┤
│ INPUT • editing at line/offset …   [native text host]│
│ focused RichEdit/NSTextView, bounded caret context  │
└────────────────────────────────────────────────────┘
```

The ribbon is visibly distinct from a document line (border/background/label, not a second editor pane). Its text is a *projection of the current global caret neighborhood*, never another committed model. For a 50 MiB line it remains 2-16 Ki UTF-16 units, not a mirror. The label says where typing will edit when the caret is outside the source viewport; scrolling does **not** move global `Anchor/Active`, change `Document.Version`, rebind to the remote row, or silently alter the selected source interval. Clicking a remote canvas cluster is different: it explicitly changes global selection, then safely rebinds the ribbon to that new caret when not composing. Clipboard, delete, undo and Save continue to use the controller's source selection. The ribbon must not intercept canvas pointer drags or turn a global selection into a host-local one. When the source caret is visible, the canvas may show a **nonblinking location marker**; the native ribbon alone owns the blinking system caret. This prevents two apparent insertion points, but does not solve the possible UIA/AX conflict between source-caret geometry and the native candidate rectangle—reader tests must decide whether this provisional UX is usable.

### Geometry and state transitions

The **target invariant** is a synchronized UI-thread geometry transition, not a claim that today's `NativeCanvasBinding` already contains a ribbon rectangle. The OS shell computes `sourceRect` and `ribbonRect` from one client-bounds measurement, emits the reduced `CanvasViewportResized(sourceRect.Height)`, and the controller publishes a version-matched `CanvasFrame` generated for that body height. The shell must not paint a frame produced for the old height against new ribbon bounds; hold the last consistent pair or repaint after the matching frame arrives. Source paint, pointer hit-test, caret reveal and AX visible/point geometry clip to `sourceRect`. Never let a `ViewportSlice` claim pixels covered by the ribbon. The ribbon height is based on actual native line height plus label/insets, not a magic 1 px; if a tiny window cannot fit both a usable host and a nonzero source viewport, show a recoverable size/experimental-mode warning rather than hide or misplace the input. Theme colors can change without moving the host; font/DPI/resize requiring native reflow is deferred while marked text is active.

| State/action | Required behavior |
| --- | --- |
| Ready, scroll/pan/resize | Canvas viewport moves and paints remote source. Ribbon stays physically on-screen, focused and bound to the *unchanged* global caret. Resize can change canvas height; native host movement is allowed only outside composition. |
| Pointer click/drag in source canvas | Hit-test using canvas row transform; publish global `Anchor/Active`. Outside composition, project the new caret into a bounded ribbon binding; pointer capture/selection remains canvas-owned and focus returns to the native host. |
| Text key or IME begins while caret is offscreen | Do not redirect the edit to visible remote text. Ribbon's explicit location label tells the user the edit target. A controller may reveal the unchanged caret in the source canvas when input begins, but **must not move/recreate the host after composition starts**; if event order cannot certify a pre-composition reveal, defer reveal until final commit. Pinyin preedit remains native-only and `Document.Version` stays fixed. |
| Composition active | Keep ribbon frame, native text, font, selection and focus stable; allow only canvas repaint/scroll that does not affect the host. Save/New/Close/Undo/Format still settle or visibly veto under the existing transaction contract. Cancel emits no engine edit; commit emits one `(G,V,nonce,TextChange)` and then may reveal the source caret. |
| Native/graphics failure | Keep canonical snapshot and committed selection; do not show a false source row. Disable the opt-in adapter with an actionable error or return to existing page mode only after preedit safely settles. Never discard marked text to make layout simpler. |

Windows: keep the visible `RICHEDIT50W` HWND as keyboard-focus/IME target and position it entirely in the reserved ribbon; do not infer its glyph coordinates from DirectWrite. `EM_POSFROMCHAR` should put the actual native caret and candidate within the ribbon. Do not use [`IMC_SETCANDIDATEPOS`](https://learn.microsoft.com/en-us/windows/win32/intl/imc-setcandidatepos) as a reflexive patch; Microsoft documents it for applications that draw composition text themselves, whereas RichEdit owns this composition. macOS: keep `NSTextView`/its scroll host **unhidden and in the view hierarchy** as first responder, with the text input candidate's `firstRect` within the ribbon. The canvas no longer skips any document row merely because the host binding's line matches it. On both OSes, accessibility still exposes **one source-backed Document** via the current provider integration; the ribbon must not add a page-local Document or make source `VisibleRanges` include its duplicate projection.

## Why not a conditional active-row sole-painter now?

A hybrid could let the native host exclusively paint the active document row and use the ribbon only when caret/source coverage is offscreen. That would keep candidates next to text for common short lines. But it is **not** a smaller proven change: the 2 Ki host must cover the complete visible interval; its scroll-to-left-source alignment must be certified at both edges, not just the caret; semantic tokens, diagnostics, global selection and AX `VisibleRanges`/bounding rectangles for that row must be rendered/reported by the host rather than silently disappearing. Moving between host-owned and canvas-owned rows during a real candidate requires a composition-frozen transition. The 63.3 px mixed-script discrepancy rules out painting both. Do not add an `if (caret visible) skip canvas row` special case until a separate focused experiment demonstrates all those invariants. Likewise, rebinding the host to the panned remote text while the global caret remains elsewhere would misrepresent where typing occurs, and moving the caret on scroll violates the user's selection contract.

A second, narrower **future experiment** is a *visible caret/preedit clipping layer*: keep the native host genuinely on-screen at the source caret, but clip its drawing to a measured caret/composition rectangle while canvas paints the remainder. Windows [`SetWindowRgn`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowrgn) and AppKit [`NSClipView`](https://developer.apple.com/documentation/appkit/nsclipview) or [`clipsToBounds`](https://developer.apple.com/documentation/appkit/nsview/clipstobounds) can limit drawing; these API descriptions do **not** establish that a RichEdit/NSTextView first responder, candidate rectangle, text selection or UIA/AX geometry remains correct under such clipping. The test must compare physical pixels and hit-tests at the clip seam, real Pinyin/CJK preedit growth, native focus, semantic overlay visibility and reader speech on both architectures. It must never reduce the focused host to an invisible 1×1 rectangle or claim exact dual-shaper parity. If that experiment succeeds, it could restore caret-adjacent candidates without promoting the ribbon to final UX; until then the ribbon is only the reversible experimental baseline.

VS Code's production [textarea edit context](https://github.com/microsoft/vscode/blob/main/src/vs/editor/browser/controller/editContext/textArea/textAreaEditContext.ts) explicitly positions its native input element differently when the primary cursor is outside the viewport and handles visible composition separately. That supports making the offscreen-caret state explicit, not borrowing DOM/ARIA hiding behavior as a Win32/AppKit proof. Mote's OS-native candidate geometry and one-source UIA/AX contract still require target-platform tests.

## Falsifying experiments and release gate

1. **First reproduce the exact state before changing layout:** open the 50 MiB unique-marker fixture, leave global caret near the start, pan 40 MiB **without clicking**, and capture physical pixels plus `(generation, version, anchor, active, frame row windows, host HWND/view rect, focus, native selection)`. If current bottom-clamped host already paints over a source row, the ribbon fixes a measured defect; the earlier after-click ASCII image alone did not establish it.
2. **Ribbon visual/source oracle:** repeat far pan, vertical away/back, remote click, drag-select across the viewport, and small-file editing on win-x64/win-arm64 and osx-x64/osx-arm64 published one-file binaries. Screenshots must show canonical source rows only above a clearly labeled ribbon, no duplicate/covered glyphs, and exactly unchanged selection/version on scroll. Compare source offsets and clipboard/save/reopen bytes; include CR/LF/CRLF, emoji, combining marks, CJK, Arabic, tabs, semantic tokens and diagnostics. Clip/AX visible ranges must exclude the ribbon projection.
3. **Real input/reader gate:** with the actual Microsoft Pinyin Chinese mode and a physical or OS-key-equivalent keyboard, begin candidate while caret is on-screen and after panning offscreen; capture only the foreground app's candidate/ribbon rectangle. Commit `你好`, cancel, Save/reopen, and test Save/New/Close while preedit is live. Repeat on Mac with a real CJK IME and verify `NSWindow.firstResponder` never changes during ribbon use. External UIA Raw/Control/Content/focus and AppKit AX must still expose one source Document; Narrator/NVDA/VoiceOver must announce caret and composition without reading both source and ribbon as separate editors. A correct screenshot with lost focus or silent candidate **fails**.
4. **Performance:** record input→engine commit, edit→draw submission, UI-thread p95/p99, bounded host UTF-16 length, per-frame shaped units and working set on 1 MiB many-line/50 MiB single-line files. Ribbon must not add a full text mirror or require `GetLine()` on the long row. A slower but correct opt-in experiment is not a default-release pass; compare to the existing page editor on the same RID.

This decision isolates the unsolved typography problem instead of pretending one caret measurement proves two shapers identical. If real IME/reader tests reject ribbon candidate placement, the next product investigation is a **single-painter caret-row host with full semantic/AX parity**, not an invisible focused control. Until then, keep `--canvas-experimental` opt-in and the working native page editor available.
