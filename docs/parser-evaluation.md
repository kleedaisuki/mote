# Format parser evaluation for mote

Status: evidence and decision note, 2026-09-29. Scope: .NET 10, Native AOT, one shipped desktop executable, single-file editing with source-mapped semantics and no silent source rewriting. This evaluates package capabilities, not measured performance in mote. It supplements [architecture.md](architecture.md), which defines the engine/policy boundary and explains why current `Analyze(string)` reparses whole strings.

## Decision summary

| Format | Recommended foundation | Source fidelity and semantic boundary | Main gate |
| --- | --- | --- | --- |
| TOML | Tomlyn 2.10.1 `SyntaxParser` plus semantic pass | Lossless trivia-preserving syntax tree with source spans; parser also exposes events/diagnostics. Keep the original text as authority. | Tomlyn v1+ implements **TOML 1.1**; most 1.0-valid files may be accepted as its subset, but do not claim strict TOML 1.0 validation without a separate versioned policy. |
| Markdown | Markdig 1.3.2, CommonMark-first pipeline | AST with positions and `trackTrivia` lossless round-trip support; project semantic projection (headings, references, links) separately. | HTML rendering is not inherently safe for untrusted Markdown. Disable raw HTML and sanitize dangerous links/HTML at the preview boundary. Test trivia/AST coexistence and exact round trips. |
| YAML | Evaluate SharpYaml 3.13.1 as primary editor substrate; YamlDotNet 18.1.0 is viable semantic fallback | SharpYaml has UTF-16 spans and lossless flat syntax tokens, parser events, and model; none is a tolerant incremental semantic tree. YamlDotNet has parser events and node marks but not documented lossless rewriting. | Both strict parsers can fail mid-edit; keep source as authority, publish a located error and explicitly partial projection. Never serialize an object model back over user text. |
| JSON | `System.Text.Json.Utf8JsonReader` or a dedicated UTF-16 scanner wrapping its semantics | Forward tokens can be source-mapped by `TokenStartIndex` and `BytesConsumed`, with byte→UTF-16 mapping. DOM is not a source-preserving editor tree. | Strict reader throws on incomplete edits; keep recovery separate. Avoid duplicate-key semantic collapse and preserve original bytes/spelling. |
| CSV | Purpose-built source-mapped record scanner for editor; Sylvan.Data.Csv 1.4.4 as independent streaming comparison/bulk read path | Source spans for cells, quoting, newlines, and dialect status must be first-class. Sylvan is fast streaming/tabular API but not an editor CST. | Huge quoted records, long lines, and dynamic dialect defeat naive line splitting or fixed-buffer assumptions. |
| Plain text | Engine line/chunk index | No external parser. | Avoid mandatory whole-file allocations. |

All version numbers are package-page observations as of 2026-09-29, **not package pinning recommendations without reproducible AOT publishing**. Repository currently carries handwritten policies with narrower grammars. A dependency swap must retain the existing public policy contract until intentionally migrated and tested.

## Evidence by format

### TOML: syntax tree first, serialization last

Tomlyn's current official documentation distinguishes object serialization, which discards comments/formatting, from low-level `TomlLexer`, `TomlParser`, and `SyntaxParser`. `SyntaxParser.Parse` returns a tolerant `DocumentSyntax` carrying diagnostics; `doc.ToString()` is specified to reproduce the original source including trivia. Its syntax nodes have exact source spans. The package says Native AOT/trimming are supported, with reflection-based object mapping disabled by default under `PublishAot`; typed serialization should use generated `TomlSerializerContext`. The key version nuance is that Tomlyn v1+ targets TOML 1.1.0 **only**. TOML 1.0-valid files commonly remain valid under 1.1, so mote should open them normally when accepted; what it cannot promise from this parser alone is strict 1.0 conformance or rejection of 1.1-only constructs. Sources: [Tomlyn low-level API](https://xoofx.github.io/Tomlyn/docs/low-level/), [syntax API](https://xoofx.github.io/Tomlyn/api/Tomlyn.Syntax/), [version/AOT policy](https://xoofx.github.io/Tomlyn/docs/), [Tomlyn 2.10.1 NuGet](https://www.nuget.org/packages/Tomlyn/).

**Implementation implication:** retain `DocumentSyntax` as a format-private concrete syntax tree (CST); build an explicit table/key-path graph to detect duplicate or conflicting definitions and typed values; emit immutable common presentation projections. Do not use a CLR object serializer as the editor's canonical representation. Full fidelity is valuable even if the first adapter still needs `string` materialization and full reparse; do not label it incremental until changed-region reuse exists.

### Markdown: CommonMark AST plus a safe rendering boundary

Markdig documents CommonMark 0.31.2 coverage, >600 spec tests, an AST with precise source locations, HTML rendering, and opt-in round-trip support that tracks whitespace/newline trivia. Package license is BSD-2-Clause. The project's own docs describe `Markdown.Parse(..., trackTrivia: true)` and a round-trip renderer; the source-facing claim is stronger than simple AST positions. A historical [issue #561](https://github.com/xoofx/markdig/issues/561) reports an interaction between `trackTrivia` and emphasis parsing; it is **not evidence of a current 1.3.2 defect**, but justifies targeted regression tests. Sources: [Markdig project](https://github.com/xoofx/markdig), [Markdig 1.3.2 NuGet](https://www.nuget.org/packages/Markdig/).

**Implementation implication:** use one explicit pipeline instance for parse and render, with extensions intentionally chosen. The preview must not treat user-authored raw HTML or links as trusted: disable HTML parsing where feasible, encode/sanitize anything that crosses into Avalonia WebView-like surfaces, and regression-test `javascript:` URLs, image destinations, and entity decoding. The AST describes Markdown structure, but reference-definition resolution, link validity and outline semantics are separate passes. Exact-source formatting should be an edit proposal, not a reserialize-over-source operation.

### YAML: stronger source fidelity is not tolerant editing

SharpYaml 3.13.1 advertises YAML 1.2 Core Schema, `IsAotCompatible`, `IsTrimmable`, and a source-generated object serializer. The important editor API is `YamlSyntaxTree.Parse(text)`: an **immutable flat token list** with trivia/source spans; `ToFullString()` reproduces source. `WithTextChange(start, length, rawReplacement)` returns a new tree preserving outside bytes, but official docs explicitly say it **reparses and validates the complete result** and throws on invalid YAML. This is not an incremental parser and not a semantic object editor. For semantics, `Parser.CreateParser(new StringReader(text))` yields parsing events; `YamlStream.Load` yields a model, but the model is not lossless and materializes aliases as copies. `YamlException.Start/End` provide located errors. Sources: [SharpYaml source/feature list](https://github.com/xoofx/SharpYaml), [SharpYaml 3.13.1 NuGet](https://www.nuget.org/packages/SharpYaml), [syntax tree and limitations](https://xoofx.github.io/SharpYaml/docs/low-level/syntax-tree/), [parser events](https://xoofx.github.io/SharpYaml/docs/low-level/parser/), [located exceptions](https://xoofx.github.io/SharpYaml/api/SharpYaml.YamlException/).

YamlDotNet 18.1.0 is a mature alternative with low-level parser/emitter and representation model; its `YamlNode.Start/End` marks provide positions. The project claims YAML 1.2 parsing but YAML 1.1 emitting in its compatibility table, and does not claim lossless comment/trivia re-emission. It is MIT-licensed. Its broader production adoption is useful, but usage volume is not proof of AOT warning-free behavior or editor round-trip safety. Sources: [YamlDotNet project/compatibility](https://github.com/aaubry/YamlDotNet), [representation node source](https://github.com/aaubry/YamlDotNet/blob/master/YamlDotNet/RepresentationModel/YamlNode.cs), [YamlDotNet 18.1.0 NuGet](https://www.nuget.org/packages/YamlDotNet/).

**Implementation implication:** prefer SharpYaml if AOT publish and semantic-spans probes pass; otherwise use YamlDotNet events for semantic coverage while retaining original text as canonical source. Model anchors/aliases as a graph with cycle checks rather than flattening copies. An invalid in-progress document must remain fully editable; catch located errors and mark analysis partial, never replace source with a strict parser's writer output.

### JSON: streaming token positions, not DOM source truth

`Utf8JsonReader` is a forward-only UTF-8 reader. `TokenStartIndex` points at token start (including opening quote for strings); `BytesConsumed` can delimit processed token input. These are byte offsets, while mote's engine uses UTF-16 offsets. An explicit mapping per line/chunk or a UTF-16 scanner is mandatory; simple character-count conversion is wrong for non-ASCII, astral code points, and escaped spellings. `JsonDocument` is useful for read-only semantic access but is not a trivia-preserving editable tree. Use the source token stream to detect duplicate property names within each object if mote chooses to diagnose interoperability hazards; do not turn duplicates into one silently by dictionary conversion. Sources: [Microsoft `Utf8JsonReader`](https://learn.microsoft.com/en-us/dotnet/api/system.text.json.utf8jsonreader?view=net-10.0), [`TokenStartIndex`](https://learn.microsoft.com/en-us/dotnet/api/system.text.json.utf8jsonreader.tokenstartindex?view=net-10.0), [JSON RFC 8259](https://www.rfc-editor.org/rfc/rfc8259).

### CSV: a data reader is not a source-mapped editor parser

Sylvan.Data.Csv 1.4.4 is a high-performance streaming reader/writer with configurable delimiter, header, quoting, lax mode and raw-record APIs. It is MIT-licensed; the package is small in NuGet terms (151.1 KB archive) but this is **not** a Native AOT binary delta. Its options documentation says records must fit the configured buffer or parsing fails, material for mote's adversarial very-long-row case. Its `DbDataReader` orientation makes it a strong independent correctness/performance oracle for ordinary tabular workloads, not an evident source-span-bearing CST for cell-level editing. Sources: [Sylvan reader documentation](https://github.com/MarkPflug/Sylvan/blob/main/docs/Csv/Sylvan.Data.Csv.md), [options and record-buffer caveat](https://github.com/MarkPflug/Sylvan/blob/main/docs/Csv/Options.md), [release notes](https://github.com/MarkPflug/Sylvan/blob/main/docs/Csv/Sylvan.Data.Csv.Releases.md), [NuGet 1.4.4](https://www.nuget.org/packages/Sylvan.Data.Csv/), [repository license](https://github.com/MarkPflug/Sylvan).

**Implementation implication:** scan CSV as record-boundary state across chunks, not lines; publish per-cell raw span and decoded value separately. Header status and type inference are hypotheses, not guaranteed CSV semantics. Preserve delimiter, quote style and line endings on Save; formatting is opt-in. Compare decoded cells against Sylvan on valid corpus, while using adversarial records to verify mote's unlimited-record correctness or an explicit resource cap.

## AOT/startup/large-file qualification, not claims

No authoritative source above provides **mote-specific** cold-start, native image size, first-edit latency, or 100 MB edit throughput. Package download sizes and author microbenchmarks are not substitutes. The next dependency decision requires a small in-repository `.temp/parser-probe` or `.cache/parser-bench` experiment on Windows and macOS GitHub Actions, publishing Release Native AOT with each dependency individually and combined. Record: publish success and all ILLink/AOT warnings; executable size delta; fresh-process wall-clock from launch to editor-ready after opening 0 B/1 MB/100 MB inputs; RSS/private bytes after parse; p50/p95 typing-to-paint and parse completion; allocations; exact source round-trip on comments/CRLF/non-BMP text; malformed-in-progress recovery; diagnostic/source-span agreement. Run same corpus and measurement harness against current policies. Warm-process parser benchmarks are useful but must be reported separately from cold startup.

**Critical architecture constraint:** all recommended libraries take a full `string`, `TextReader`, or UTF-8 span/sequence. Merely passing a `TextSnapshot` through the policy signature does not make parsing non-materializing. A bounded viewport/partial-analysis path must be explicit; full semantic passes can remain asynchronous and version-checked until a genuinely reusable parser is built. Research on incremental parsing warns that reuse depends on grammar and edit location; [architecture.md](architecture.md) records the relevant research and its applicability limit. Do not assume one generic incremental parser will serve TOML, YAML, Markdown and CSV equally well.

## Focused acceptance probes before integration

1. **TOML:** TOML 1.0 vs 1.1 discriminating corpus; comments and mixed newline byte-identical round trip; duplicate dotted paths/table arrays; malformed quote recovery; exact UTF-16 spans.
2. **Markdown:** all selected CommonMark tests; `trackTrivia` round trip; emphasis and nested links with trivia; reference changes invalidating distant uses; preview raw-HTML/URL safety.
3. **YAML:** anchors, aliases, cycles, merge keys, flow/block scalars, directives, multi-document streams; malformed intermediate text must not crash; count/position spans; AOT warnings and model lossiness.
4. **JSON:** duplicate keys, escaped property names, deep nesting, comments/trailing commas as explicit policy, non-BMP byte↔UTF-16 offsets, malformed intermediate text.
5. **CSV:** huge quoted single record, embedded CRLF, escaped quotes, final empty cell/record, dialect detection confidence, exact source round trip and random cell edits.

Decision changes only if probes show (a) a candidate fails real-world grammar/semantics, (b) AOT trim/publish breaks it, (c) startup/size materially violates product budgets, or (d) source-preserving spans cannot support the editor contract. Otherwise the strategic path is external grammar foundation plus mote-owned semantic projection and edit transactions—not a proliferating handwritten parser for each format.
