# Live native theme transition: independent review (2026-09-30)

## Scope and method

Reviewed the uncommitted runtime-theme diff in `NativeShell`, `NativeEditorController`, the Win32 shell/RichEdit island and interop, and the AppKit shell/text island; traced their callers and the new controller/policy-transition tests. The source tree was frozen, so this review changed no production file and did not rerun the root agent's completed Release builds/tests. This was a source-and-contract review, not a Windows/macOS appearance or real-IME acceptance run.

## Disposition of the Windows RichEdit undo concern: not a demonstrated product defect

**API contract.** In ordinary (non-canvas) Windows mode, a theme transition with matching semantic analysis enters `WindowsEditorShell.SetTheme` at lines 475–485 and calls `ApplySemanticColors`. That method reimports the RichEdit page through `EM_SETTEXTEX` at lines 1049–1062 with `SetTextEx.Flags` left at zero (interop lines 147–152). Microsoft's [SETTEXTEX contract](https://learn.microsoft.com/en-us/windows/win32/api/richedit/ns-richedit-settextex) says this `ST_DEFAULT` operation deletes the control's undo stack. This is a native-control contract, not evidence that Mote's canonical undo history is lost.

**New product evidence.** The Windows owner subsequently ran a disposable real-`RICHEDIT50W` probe against the patched shell; the method, environment, raw-output path, and limitations are recorded in [the native RichEdit performance note](native-richtext-performance.md#live-theme-and-undo-hwnd-follow-up-2026-09-30). With matching semantic analysis, light→dark transitions preserved exact displayed UTF-16 text, selection `[800,805]`, and first visible line `53`. Both Ctrl+Z via the shell accelerator and Edit-menu Undo restored exact engine and RichEdit text after two edits. `EM_CANUNDO` returned `1` after restyle; direct `EM_UNDO` on a disposable edit returned `1` but did not diverge engine/native text. Thus `EM_CANUNDO` is not evidence of a user-visible loss or bypass. No user-reachable native Undo route outside the engine was demonstrated. The documented `ST_DEFAULT` behavior remains true, but my earlier P2 severity and recommendation to replace the one-pass RTF styling path were not justified by observed product behavior; **withdraw that finding**.

**Residual guardrail, not a release blocker on present evidence.** If a physical context-menu, assistive-technology, or other native Undo route becomes reachable, route it to the engine and verify it cannot independently mutate the RichEdit page. The probe did not exercise physical input, actual IME composition, or a full controller/disk-save workflow; those remain target-host acceptance items. Retain the measured one-pass RTF approach unless a reproducible regression supplies a reason to replace it: prior benchmark evidence found per-token formatting much slower on the bounded page.

## Other reviewed paths and residual validation

- The typed `NativeDocumentStamp` gates analysis against document generation/version in both shells; `SelectPolicy` publishes an empty same-version view to invalidate prior-language facts. The Win32 default editor defers analysis during IME settle; the canvas island waits for its final commit notification. No second source-backed defect was established in those paths.
- The controller coalesces effective-policy changes and defers `SetTheme` while `IsTextComposing`; its theme-error status is generic and does not interpolate document paths or text. The platform setters attempt best-effort rollback. No claim of *atomic* rollback under persistent native allocation failure is made without a host failure-injection test.
- The new fake-shell tests exercise policy resolution, coalescing, late deferral, rollback signaling, and canonical Undo/Redo. The subsequent real-HWND probe establishes the specific Windows text/selection/scroll and engine Undo observations above, but not RichEdit/AppKit callback ordering under real IME, actual candidate-window stability, physical native-command ingress, or visual selection/chrome contrast. Complete the existing Windows/macOS real-IME and live-appearance acceptance plan before treating those as verified.

**Current review result:** no substantive defect remains established within the inspected source and available host evidence. This is bounded by the unexercised target-host scenarios stated above, not a certification of every native behavior.
