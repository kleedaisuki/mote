# Oversized CSV projection independent review

## Scope and state

Review of the uncommitted `CsvIncrementalSession` oversized-record/field certificates and `CsvOversizedFieldTests`, 2026-09-30. No production code or checked-in tests changed by reviewer. Managed Windows/.NET 10 differential probes live under `.temp/csv-oversized-review`; this is not Native AOT, GUI, or retained-heap verification.

The certificates are generated by authoritative full parsing, retained without source strings, and version invalidated on edits. Global diagnostic totals are taken from full validation rather than the skipped projection parser. The legacy project-all branch excludes records longer than 64 Ki units, preventing null-window use with a giant-field certificate. Dense-to-sparse transition discards dense segments before their accounting limit, and cancellation commits only after projection completes.

## Independent evidence

- 1,500 randomized windows on mixed >70 Ki quoted/unquoted giant fields: exact global CSV001–004 totals and projected diagnostic/token coordinates matched fresh `CsvPolicy`.
- 449 disjoint windows on >64 Ki records consisting of quoted short fields, malformed unquoted fields, or empty fields: totals, local diagnostics, tokens, and cell spans/values matched fresh `CsvPolicy` under the existing inclusive zero-width ownership rule.
- EOF boundary probe of two 80-unit windows on comma-only records: lengths 65,535 / 65,536 / 65,537 / 131,071 / 131,072 each emitted the expected 162 zero-width cells.

## Open endpoint-delivery issue

Source SHA-256 at reproduction: `374B4BE54E7C6B36C1F16E8513D485509CB13592DA9BCD0283286999F77F17AE`.

For **131,073 commas**, warm windows `(0,80)` and `(length-80,80)` emit only **160 cells**, last start **131,071**, rather than 162 including starts 131,072 and EOF 131,073. The replay allowance counts the checkpoint-to-window gap, then stops at 65,536 replay units while still before the row end. Exempting `cursor.Position == certificate.Row.End` fixes the exact 131,072 fixture but not its immediate neighbor.

`Truncated` is truthful, so this is not an invented global-completeness claim. Nevertheless, tiny requested tail delivery is unexpectedly incomplete solely because of checkpoint alignment, and a benchmark that happens to align EOF exactly does not establish arbitrary head/tail source-map delivery. Suggested remedy: separate bounded pre-window replay from requested-window delivery accounting, or otherwise provide a justified allowance covering the seek gap and bounded requested width; retain truncation for genuinely large requests/output quotas. Owner/root notified with reproduction before integration. Review is pending the coordinated correction.

## Resolution and final disposition

The endpoint issue above was corrected by separating checkpoint lookbehind from requested delivery. Current source SHA-256: `2FC53504ED0FA96E03D6CDC72B370F56FA3EACC84D8B80BB0A91C5BB55D25F49`. A window receives `2 * 64 Ki + min(window.Length, 512 Ki) + 1` source-replay allowance: field-start checkpoints can overshoot their nominal 64 Ki spacing by one ordinary field of at most 64 Ki. Since allowance is checked between fields, there can additionally be one terminal ordinary-field overshoot of at most 64 Ki; replay remains O(number-of-windows * 64 Ki + aggregate requested width). Giant certified fields do not require source replay. Legacy ranges above 512 Ki can remain explicitly truncated, rather than changing compatibility into unbounded output.

The failure-directed independent rerun passed all eight comma-only record lengths **65,535 / 65,536 / 65,537 / 131,071 / 131,072 / 131,073 / 196,608 / 1,000,000**, each with the exact 162 requested cells, including EOF. The reviewed quota-skip correction also explicitly marks truncation when abandoning an exhausted but still-interested window before serving the next window.

**No remaining material production blocker found in this review scope.** Earlier independent differential evidence is not rerun because the subsequent edits are confined to replay allowance and truncation signaling, and only the demonstrated failing boundary family required new verification. Existing owner tests cover edits/version invalidation and cancellation; those were inspected, not broadly rerun by reviewer. The warm giant-field speedup is mechanically plausible because projection uses version-certified field/record spans and emits no giant decoded value; it is not evidence of cold-index, post-edit full-scan, GUI latency, Native AOT, or real retained-heap acceptance. The retained-index estimate includes certificates and the dense-to-sparse threshold, but this review does not establish target-platform heap layout or an actual 32 MiB heap measurement.
