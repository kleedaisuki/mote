# mote architecture and implementation contract

Status: target architecture, 2026-09-29. The public promise is a fast **single-file** editor, not a workspace IDE: opening one file creates one independent document session, and all language intelligence is in the shipped application. **Delivery is strictly one on-disk executable binary per OS/architecture**—not a folder of companions, self-extracting bundle, or `.app` directory. OS-provided system libraries/frameworks remain allowed; no mote-shipped DLL/dylib, font, config file, or resource sidecar is allowed. Avalonia `Mote.Desktop` is an interim development UI and fails that delivery contract. `Mote.Native` is the intended Win32/AppKit product shell, still under construction. The legacy `IDocumentPolicy.Analyze(string)`/`FormatAnalysis.SourceText` API remains; an additive snapshot-based session contract is implemented for Plain text, CSV and Markdown, but the native controller still calls the legacy API. Do not confuse the interface or background scheduling with full incremental analysis of all formats.

## 1. Product workflow and boundaries

The dominant interaction is `mote path` (or Open), immediate editable text, useful structure and diagnostics shortly afterward, and safe Save. No project discovery, indexing service, external language server, runtime plugin loading, or network operation occurs on that path. Multiple windows may each hold a document, but no operation requires a project/workspace. Filename extension selects a policy; the user can override it without changing file bytes. Unknown extensions select PlainText.

```
path → open/encoding → Document + versioned TextSnapshot → TextView
                                   │ edit(version n → n+1)
                                   ▼
                           analysis scheduler
                                   │ immutable snapshot, edit delta
                                   ▼
                   compile-time registered document policy
                                   │
                 FormatAnalysis(version n+1, semantic projections)
                                   │ publish iff version still current
                                   ▼
                    editor overlays + preview/outline
```

The microkernel analogy is **mechanism versus policy**, not an OS-like plugin ABI. `Mote.Engine` owns text, versions, change transactions, undo/redo, I/O, format-agnostic scheduling/cache mechanisms, and document lifetime. `Mote.Formats` owns language grammars, tolerant parsing, semantic resolution/validation, formatting, and projections. `Mote.Configuration` resolves startup settings/paths, `Mote.Themes` maps semantic roles to immutable presentation values, and `Mote.Telemetry` records opt-in diagnostics. `Mote.Native` is the product composition root and OS shell; `Mote.Desktop` remains an interim noncompliant Avalonia UI, not the release target. Dependency direction is `Mote.Formats → Mote.Engine`, `Mote.Native → Engine/Formats/Configuration/Themes/Telemetry`; `Mote.Engine` must not depend on format or UI modules. The scheduler therefore accepts a generic analysis callback/result or lives in the composition layer while retaining its version/cancellation machinery in Engine. Source modules remain separately testable but are statically linked into one Native AOT executable. Native AOT forbids runtime assembly loading and runtime code generation, so registries are explicit source code or generated at build time, not reflection-discovered plugins [Microsoft Native AOT](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/).

## 2. Ownership, data and invariants

| Owner | State/data | Invariant |
| --- | --- | --- |
| Engine `Document` | Current immutable text root, monotonic `Version`, file identity, encoding/BOM, dirty state, undo transactions | Text bytes are never silently changed by analysis or view; a committed edit advances version exactly once. |
| Engine `TextSnapshot` | Structurally shared UTF-16 text chunks and newline aggregate/index | Snapshot is immutable, readable after later edits, disposed/released at bounded lifetime; no whole-file string copy per keystroke. |
| Engine `TextChange` | Replacement in an old-version half-open `TextSpan` plus inserted text | Coordinates are UTF-16 code-unit offsets; old-version span and new text uniquely define the transition. Reject edits that split a surrogate pair. Edits between CR and LF are allowed: they turn one CRLF ending into separately valid CR/LF text. UI caret movement respects grapheme clusters. |
| Engine analysis coordinator | Cancellation token, latest submitted/published version, bounded caches | A result is published only for the exact current document/version/policy; cancellation is advisory, version check is authoritative. |
| Format policy | Private parse tree/semantic index, recovery state, semantic projections | A policy may retain caches only for one document session; never mutate engine text; every reported span belongs to the result version. |
| UI | Selection, scroll, layout, active command and presentation state | UI never owns canonical text or parser state; view requests bounded lines/spans; layouts and overlays are version-tagged. |

**Coordinate choice.** Canonical in-memory offsets are UTF-16 to align with .NET `string` and desktop text APIs. UTF-8 is an I/O representation, not an engine coordinate. An adapter for a byte-offset parser must maintain explicit UTF-8↔UTF-16 checkpoints per chunk/line and test astral characters and mixed newline sequences. `TextSpan` is `[Start, End)` in a particular snapshot. Never combine spans from different versions or silently clamp them after edits. The line index counts LF, CRLF and lone CR as line endings; ordinary edits and Save preserve their original bytes unless the user explicitly normalizes them. CR-only navigation, chunk-straddling CRLF, and an edit splitting CRLF have regression tests. `TextSnapshot` offers chunk/line iteration, `Slice`, and offset↔line/column mapping; whole-file `GetText()` should not be on a hot path.

**Text backing.** Use a balanced piece tree/rope of bounded chunks with aggregate UTF-16 length and line-break count; original chunks are immutable, insertions append into edit-owned chunks, and snapshots share unchanged nodes. Avoid both one giant `string` and `List<string>` per line. A small-file fast path may use fewer nodes but must implement the same API and semantics. VS Code's production piece-tree redesign documents why chunked original buffers, line aggregates, and stable edit costs matter for large files [VS Code engineering](https://code.visualstudio.com/blogs/2018/03/23/text-buffer-reimplementation); Zed's rope experience explains the value of cheap snapshots for background analysis [Zed engineering](https://zed.dev/blog/zed-decoded-rope-sumtree). The exact B-tree fanout/chunk size is benchmark-driven, not part of the API.

**File identity and Save.** Open records path, observed metadata/content fingerprint, encoding and BOM; default to strict UTF-8 (plus recognized UTF-8/UTF-16 BOMs), and do not silently replace invalid bytes. Unsupported/ambiguous encoding requires an explicit choice or a lossless read-only view. Save writes a sibling temporary file, flushes it, checks external modification, then replaces the destination using platform-appropriate semantics; keep the original if any step fails. A save of snapshot `v` clears dirty state only if the current document still equals `v`. Save As updates identity only after successful commit. Crash recovery and backup semantics require platform tests, not a claim of universal atomic durability.

## 3. Policy interface: small common projections, rich private semantics

The common intermediate representation (IR) is a **source-mapped presentation/interaction projection**, not an alleged universal Markdown/CSV/YAML AST. Distinct syntax and semantic models stay inside policies. This prevents the engine from accumulating six formats' special cases. The following is an **illustrative target shape**, not an exact restatement of today's type signatures: the stable base API remains `TextChange(int Start, int DeleteLength, string InsertText)`, `Analyze(string)`, `Format(string)` and `RenderHtml(FormatAnalysis)`. `IncrementalContracts.cs` now adds `IIncrementalDocumentPolicy`, `IFormatSession`, `DocumentAnalysis`, coverage/completeness and versioned edits; three policies implement sessions. Their presence alone cannot improve product large-file behavior until `Mote.Native` uses them, and the remaining parsers avoid whole-file materialization where required.

```csharp
/// <summary>A half-open UTF-16 range in one text snapshot.</summary>
public readonly record struct TextSpan(int Start, int Length);

/// <summary>One immutable text transition from BaseVersion to BaseVersion + 1.</summary>
public readonly record struct TextChange(long BaseVersion, TextSpan Replaced, string Inserted);

/// <summary>Immutable, source-mapped analysis for exactly one document version.</summary>
public sealed record FormatAnalysis(
    long Version,
    AnalysisCompleteness Completeness,
    IReadOnlyList<SemanticNode> Nodes,
    IReadOnlyList<Diagnostic> Diagnostics,
    IReadOnlyList<HighlightSpan> Highlights,
    IReadOnlyList<FoldRange> Folds,
    IReadOnlyList<RenderBlock> RenderBlocks);

/// <summary>Static policy boundary; implementations own private parse/semantic state.</summary>
public interface IDocumentPolicy
{
    string Id { get; }
    FormatAnalysis Analyze(TextSnapshot snapshot, TextChange? change,
        FormatAnalysis? previous, AnalysisRequest request, CancellationToken cancel);
    FormatEdit? Format(TextSnapshot snapshot, TextSpan? selection,
        FormatOptions options, CancellationToken cancel);
}
```

`AnalysisRequest` carries required viewport span and requested depth (fast visible projection versus complete file), not UI objects. `AnalysisCompleteness` explicitly states `VisibleOnly`, `Partial`, or `Complete`; absence of a diagnostic in a partial result is **not** proof of validity. `SemanticNode` carries stable *kind*, display label, source span, parent/child relationships and optional navigation target. `Diagnostic` carries severity, code, source span and message. `HighlightSpan` is a semantic role such as `key`, `scalar`, `heading`, `link`, `invalid`, not a theme color. `RenderBlock` is a typed, source-mapped render instruction (`paragraph`, `heading`, `table`, `code`, `scalar`, etc.) with escaped text and safe link target, not arbitrary HTML injected into a webview. All projections are immutable and bounded in the visible fast lane; policies can retain their own richer tree and indexes. Rendering consumes the projections and never reparses text itself.

The **analysis invariant** is syntax → semantic resolution → projections, with error nodes/recovery so an unfinished edit still yields a useful tree. `HighlightSpan`s must originate from syntactic or semantic classification, not regex-only colorization. Policy-specific examples:

| Policy | Semantic commitments (not merely lexical coloring) | Reparse/invalidation unit |
| --- | --- | --- |
| JSON | Structural object/array tree, decoded scalar types, duplicate-object-name warning, exact syntax errors; no schema claims without a selected schema. JSON names *SHOULD* be unique rather than unconditionally invalid [RFC 8259](https://www.rfc-editor.org/info/rfc8259/). | Smallest enclosing container where safe; fallback full parse. |
| TOML | Dotted-key/table path resolution, duplicate key/table conflicts, typed values and cross-entry conflicts per TOML version [TOML spec](https://toml.io/en/v1.0.0). | Table section plus dependent path index. |
| YAML | Indentation/flow syntax, tag-aware scalar values, anchors/aliases, duplicate mapping keys where equality is decidable; cyclic alias graph guarded in renderer [YAML 1.2.2](https://yaml.org/spec/1.2.2/). | Document/collection with dependency tracking; may need full fallback. |
| Markdown | CommonMark block/inline tree, headings and outline, reference-definition resolution, link/image targets, fenced blocks, safe preview [CommonMark spec](https://spec.commonmark.org/spec). | Block region plus reference dependents. |
| CSV | Quoted records, rows/columns, dialect/header status, inconsistent field-count diagnostics, tabular preview; type inference is explicitly tentative, never a hard validation error [RFC 4180](https://www.rfc-editor.org/info/rfc4180/). | Record boundaries, with quote-state lookback. |
| Plain text | Line model, search, whitespace/encoding diagnostics and text rendering. | Changed lines. |

Formatting is a **proposed text edit**, not a mutation of the parse tree. Apply it through the same engine transaction, with snapshot version precondition. Preserve comments/trivia and unsupported syntax; if a formatter cannot guarantee this, report unavailable rather than silently discard data. Preview and text share one source mapping; clicking a rendered block navigates to its source span.

## 4. Scheduling, large files, responsiveness

An edit must first commit text and paint an unstyled/last-known-safe viewport. Parsing cannot block the UI thread. The coordinator coalesces keystroke bursts, gives visible-range work priority, cancels obsolete work, and discards stale completions. A viewport job may use lexical boundary state for immediate provisional styling, but semantic projection follows from a tolerant tree and carries its completeness flag. Background complete analysis is scheduled after interaction settles; it must yield/cancel by time or chunk, and it never blocks saving. Important cross-region dependencies (Markdown references, YAML aliases, TOML keys) must invalidate their dependents; a cheap local parse is not automatically a complete semantic answer. Tree-sitter's documented edit/reparse/structural sharing and changed ranges are useful design references but do not by themselves solve semantic dependency invalidation [Tree-sitter](https://tree-sitter.github.io/tree-sitter/using-parsers/3-advanced-parsing.html). Rust-analyzer's on-demand derived-query design is another reference; a full Salsa-like framework is overkill for six single-file formats until dependency profiles justify it [rust-analyzer architecture](https://rust-analyzer.github.io/book/contributing/architecture.html).

**Terminology gate:** `Analyze(snapshot, change, previous, ...)` is an incremental *API*, not evidence of incremental *implementation*. If a format currently reparses the entire document on every edit, document and benchmark it as full reparse with versioned asynchronous publication. Claim locality only after tests prove unchanged-region reuse and semantic-equivalence against full reparse. Research on incremental scannerless GLR reports substantial reuse and speedups for small edits, but also extra full-parse overhead and reduced incrementality under grammar nondeterminism; this motivates per-format measurement rather than assuming a general parser wins [Sijm, SPLASH 2019](https://doi.org/10.1145/3359061.3361085), [TU Delft thesis, 2021](https://repository.tudelft.nl/record/uuid%3A6ddf9fbd-c39e-4aae-b6ce-13389def6a9f).

For a very large file, use the **same exact text and edit semantics**, not a separate read-only mode. Only amount of *derived work* changes: chunked load/line indexing, virtualized visible lines, bounded layout, capped diagnostics shown at once, and explicit partial-analysis status. Avoid `ReadAllText`, entire-file line arrays, whole-file render trees and synchronous pretty-print. Very long individual lines require horizontal clipping and segmented shaping; file size alone is a poor predictor of this case. Full semantic validation remains available on demand or idle, with progress and cancellation. A correctness-preserving global operation may be O(file size); its latency is visible and asynchronous rather than hidden behind fake 'instant' semantics. Scintilla's production large-document mode similarly separates text capacity from styling cost [Scintilla](https://www.scintilla.org/ScintillaDoc.html).

Targets are *acceptance hypotheses*, not measured claims: warm UI shell ≤150 ms on a supported desktop, 1 MB UTF-8 open-to-editable ≤250 ms, 100 MB open-to-editable ≤2 s on NVMe, local typing p95 input-to-paint ≤16 ms, and ≤2× file-size resident memory before full semantic analysis. CI records cold/warm startup, first paint/editable, p50/p95 edit latency, viewport scroll latency, memory and file-size distribution on actual OS runners; release gates should be set from measurements, not guessed thresholds. Include adversarial inputs: one 50 MB line, deeply nested JSON/YAML, YAML alias cycles, multiline CSV quotes, repeated Markdown references, non-BMP Unicode, mixed newlines, malformed syntax, and edits at start/end/middle.

## 5. UI and deployment decision

**Chosen release direction:** `Mote.Native` uses OS-provided Win32/RichEdit on Windows and AppKit text controls on macOS behind `INativeEditorShell`. The engine remains the sole canonical document owner; the native control holds a bounded editable projection. Common shell semantics—commands, page/global coordinates, source-mapped analysis, file dialog outcomes, theme roles, and close confirmation—are modeled once above OS interop. Windows imports system DLLs only; macOS links/loads system AppKit and Objective-C runtime only. Earlier [AppKit](https://github.com/kleedaisuki/mote/actions/runs/36538939111) and [bare-Mach-O Launch Services](https://github.com/kleedaisuki/mote/actions/runs/36539669129) probes established feasibility. **The integrated milestone is demonstrated:** hosted [CI run 36542765032](https://github.com/kleedaisuki/mote/actions/runs/36542765032) passed Windows/macOS solution tests and Native AOT on win-x64, win-arm64, osx-x64 and osx-arm64; each strict publish inventory contained one executable, zero sidecars, and native GUI startup/standalone macOS Launch Services smoke passed. Reported artifact sizes for that run are 5.21, 5.31, 12.14 and 11.87 MB in that RID order. At commit `40bdfd2`, [CI run 36543623820](https://github.com/kleedaisuki/mote/actions/runs/36543623820) again passed all six jobs and added an enforced Windows `dumpbin /dependents` allowlist gate on **both win-x64 and win-arm64**; macOS `otool` system-path and four-target one-file gates also passed. The PE gate covers **static imports only**: a dynamic `LoadLibrary` call is not proved safe by `dumpbin` and still requires source review and GUI runtime tests. These results close binary-count/static-import feasibility, **not** real open-edit-save, IME/accessibility, signing/notarization, global large-file semantics, or paint latency. Native AOT is target-specific and cannot cross-compile across operating systems [Microsoft Native AOT cross-compilation](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/cross-compile). See [feasibility record](single-binary-feasibility.md) for probe details and unresolved bare-Mach-O distribution behavior.

**Why Avalonia is interim only:** The existing `Mote.Desktop`/Avalonia app provides a useful GUI and AOT test harness but is **not compliant** with strict delivery. A measured Windows x64 publish emitted `Mote.Desktop.exe` plus `av_libglesv2.dll`, `libHarfBuzzSharp.dll`, and `libSkiaSharp.dll`; `PublishSingleFile` plus `IncludeNativeLibrariesForSelfExtract` still emitted all three DLLs ([reproducible local inventory](../packaging/README.md)). Avalonia's macOS backend likewise uses `libAvaloniaNative.dylib` [Avalonia macOS backend](https://docs.avaloniaui.net/docs/platform-specific-guides/macos). Hiding companions in an archive or extracting them on first run would violate the operational requirement. Static-linking the graphics stack is theoretically possible only with suitable native archives and interop changes [Microsoft Native AOT native linking](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/interop); it is not an established low-risk path here. `Mote.Desktop` may remain as a non-release comparison/test harness, but no release artifact may silently use it.

**Native control risks:** OS text controls improve IME, clipboard, accessibility and startup integration, but do not by themselves solve a 100 MB continuous-file view. Current `NativeDocumentView` carries bounded page text and `TextChanged` reports the complete page; global selection/search, cross-page copy, caret mapping and p95 edit allocations require explicit verification. If a control forces page-local semantics, evolve one engine-owned virtual view adapter rather than adding format/file-size special cases. Test CJK IME, emoji/grapheme movement, VoiceOver/Narrator, theme contrast, drag/drop, high DPI, and malformed-input recovery on real target systems. WebView as canonical editor, language servers, reflection/plugin loading, universal AST, and mandatory whole-file parsing before editability remain rejected for the stated constraints.

## 6. Configuration, local state and theme policies

Runtime-owned files default to the current user's **`~/.mote`**, never to the edited file's directory or an implicit workspace: `config.toml`, replaceable `cache/`, durable `data/`, and opt-in `traces/`. On Windows `~` is the user profile; on macOS it is the Unix home. Resolve settings before constructing the UI or trace sink. Precedence is built-in defaults → optional `MOTE_HOME` root override → validated individual `[paths]`, `[appearance]`, and `[telemetry]` values in that root's `config.toml`. An explicitly enabled `MOTE_TRACE=1` may opt in tracing, but must use the configuration-resolved trace directory rather than silently reverting to a platform app-data path. The config loader does not create files/directories on read; invalid entries produce diagnostics and retain safe defaults. An explicit user path override may intentionally relocate a directory outside `~/.mote`; that is an override, not a default leak. See [configuration contract](configuration.md) and `Mote.Configuration` implementation. Repository experiments/tests remain under the repository's `.cache` and `.temp` per project instructions, not under production `~/.mote`.

`Mote.Themes` is a statically linked, UI-neutral policy registry, parallel to format policies. Built-in IDs are `mote-dark` (default), `mote-light`, and `mote-high-contrast-dark`; `system` resolves through OS appearance without a runtime-loaded plugin. The original palette uses restrained familiar VS Code/JetBrains-like structure, **not copied proprietary theme assets**, and maps editor/chrome/preview/selection/diagnostic plus semantic-token roles. Theme changes should repaint without reparsing or mutating text. Validate selection foreground and controls as well as token colors; static contrast tests are a guard, not proof of real platform accessibility. See [theme policy](themes.md), [VS Code theme color roles](https://code.visualstudio.com/api/references/theme-color), and [JetBrains color-scheme guidance](https://www.jetbrains.com/help/idea/configuring-colors-and-fonts.html). No font or theme file is bundled beside the executable.

## 7. Slices and verification order

This is an **integration order**, not permission to ship a knowingly incomplete product:

1. Define engine types/invariants and tests: UTF-16 spans, immutable snapshots, text edits, line index, undo grouping, newline/encoding preservation. Make the same API serve small and large files.
2. Define the policy boundary/projection IR and static registry. Plain text exercises it; JSON exercises tolerant structural/semantic diagnostics and stale-result handling. Add corpus-based format tests for all six policies.
3. Add viewport-first analysis coordinator and version publication rules. Test rapid edits, cancellation races, policy switches and memory reclamation.
4. Integrate `Mote.Native` Win32/AppKit shells behind `INativeEditorShell`, with source-mapped native render panels, format commands, configuration-resolved theme, and reliable IME/accessibility. Keep Avalonia only as an interim/non-release comparison. Test real Windows/macOS input and global large-file editing, not only headless unit tests.
5. Integrate safe Save, conflict detection, recovery and **one-binary inventory enforcement**. Publish AOT early and repeatedly; treat trim/AOT warnings as defects. CI must reject any release payload with a companion DLL/dylib/resource file or extraction dependency, then launch the actual native shell on each target architecture. Separate signing/notarization trust work from the one-binary count: a signed folder or `.app` is still noncompliant.
6. Profile dominant workloads and tune chunk sizes, line layout and invalidation using evidence. Record baselines and regressions; do not optimize speculative parser internals at the expense of visible editing.

An implementation is complete only when all six formats offer real structure/semantics, diagnostics, rendering and editing; the native UI handles ordinary input/IME/accessibility; Save protects data; large files remain continuously editable; configuration/theme/trace paths honor the `~/.mote` contract; and every target publish is one launchable binary with no shipped sidecar.

## 8. End-to-end tracing and telemetry

`Mote.Telemetry` is a cross-cutting module, not an engine dependency on a logging framework. Use a small static vocabulary of `ActivitySource` operations (`mote.startup`, `document.open`, `document.decode`, `document.edit`, `analysis.parse`, `analysis.semantic`, `analysis.publish`, `view.layout`, `view.paint`, `document.save`) and low-cardinality event names. .NET `Activity` provides span identity and parent/child correlation compatible with OpenTelemetry without requiring a network exporter [Microsoft .NET tracing](https://learn.microsoft.com/en-us/dotnet/fundamentals/networking/telemetry/tracing), [OpenTelemetry trace conventions](https://opentelemetry.io/docs/specs/semconv/general/trace/). Each operation records monotonic elapsed time (e.g. `Stopwatch.GetTimestamp`/`GetElapsedTime`), success/failure/cancel status, document format, size bucket, document version, and operation-specific counts (bytes decoded, dirty regions, nodes/diagnostics, visible lines). Wall-clock UTC is for cross-record ordering only, not duration arithmetic.

The default product mode emits no persistent user-content telemetry. An explicit local opt-in flag/environment variable enables a JSONL sink under configuration-resolved **`~/.mote/traces`** by default; this is the first persistence format because it streams, can be inspected with standard tools, and does not add SQLite startup/native packaging cost. Each line has `schema_version`, `utc_time`, `session_id`, `trace_id`, `span_id`, `parent_span_id`, `operation`, `duration_us`, `status`, and a bounded `attributes` object. Never record document text, snippets, full paths, filenames, link targets, CSV cell values, parse error messages containing source text, or command-line arguments by default. Treat even file extension as potentially identifying; record the normalized format enum only. Additional sensitive attributes require separate explicit consent and retention limits, following OpenTelemetry's guidance to opt in sensitive/verbose attributes [OpenTelemetry convention guidance](https://opentelemetry.io/docs/specs/semconv/how-to-write-conventions/).

The sink uses a bounded, single-consumer queue and async append; UI/editor work uses non-blocking `TryWrite`, never waits for disk. On overflow, drop the new record, count drops atomically, and emit a later aggregate `telemetry.dropped` record when capacity returns; expose the count in diagnostics. Flush at normal shutdown with a short timeout but never delay a user save. Use a typed manual `Utf8JsonWriter` or source-generated serializer, never reflection-based serialization; bound record size and queue memory, rotate files by size and age, and fail closed (disable sink with a visible warning) on persistent write errors. .NET bounded channels provide explicit drop behavior and callbacks [Microsoft Channels](https://learn.microsoft.com/en-us/dotnet/core/extensions/channels). Benchmark harnesses should inject a run ID and emit the same trace IDs around open/edit/parse/presentation, and paint only if an actual paint hook exists, so p95 regressions can be attributed to stages; compare telemetry-off and telemetry-on overhead and enforce no paths/content in a schema/privacy test. SQLite can be added only if actual query/retention needs outweigh another native dependency.

## 9. Research opportunity, not a dependency

A promising research question is whether a **policy-owned semantic dependency summary per stable syntax region** can keep global diagnostics correct while the foreground analyzes only visible regions. For example, each Markdown block exports reference definitions/uses; each TOML table exports resolved paths; each YAML subtree exports anchor definitions/uses. On edit, reparse local region, update a compact dependency graph, and recompute only impacted consumers. The hypothesis is that this lowers p95 semantic-update latency without a heavyweight general query engine. Compare against full reparse and syntax-only changed-range strategies on realistic and adversarial corpora; measure latency, peak memory and diagnostic equivalence, not just parser time. This is motivated by production on-demand analysis [rust-analyzer](https://rust-analyzer.github.io/book/contributing/guide.html) and error-resilient incremental parsing in IDEs [ReSharper PSI](https://www.jetbrains.com/help/resharper/sdk/PSI_Overview.html). Recent PEG error-recovery work underscores that a parser must keep useful structure under incomplete edits, but its benefits depend on grammar shape and are not an automatic adoption recommendation [Medeiros & Mascarenhas, 2025 preprint](https://arxiv.org/abs/2507.03629).
