# Whole-document accessibility provider: source-backed prototype and release gaps

Status: **input-independent range core plus opt-in Windows/AppKit provider hooks; cross-process source-range probes pass on both target architectures, but Windows one-editor tree acceptance fails**, 2026-09-29. This document owns the accessibility slice of [virtual-editor-design.md](virtual-editor-design.md); input-composition risks remain in [input-island-design.md](input-island-design.md). No Narrator, NVDA, VoiceOver, Accessibility Inspector, complete TextPattern, or real-IME accessibility pass is claimed.

## The single-editor invariant

`AccessibleDocument` in `src/Mote.Native/Accessibility/` publishes one immutable `AccessibleCanvasState(generation, TextSnapshot, CanvasFrame)` at a time. The frame carries global anchor/active offsets; the snapshot carries its own version. There is **no input-host binding, copied island text, or dependency on whether the island can be created**. Its `DocumentRange` is always `0..Snapshot.Length`, independent of the caret-local input island or painted viewport. Every `AccessibleRange` carries `(generation, version, start, end)` in half-open UTF-16 source coordinates. A stale range is rejected after a document swap or edit rather than interpreted against unrelated bytes. Selection direction remains available separately from its ordered interval. The model never calls `TextSnapshot.GetText()` without a bounded `(start, length)` and never uses `GetLine()` on a long logical line.

`WindowsTextProviderCore` and `MacAccessibilityTextCore` are **platform semantic adapters, not registered OS providers**. The Windows core covers document range, global selection, visible slice ranges, line/range mappings, `GetText(maxLength)`, and a controller-owned scroll request. The Mac core covers character count, selected/visible range, source string-for-range, and line/range mappings. The Mac visible range covers *whole logical lines* (including horizontal clipping), matching [Apple's explicit `visibleCharacterRange` rule](https://developer.apple.com/documentation/appkit/nsaccessibility-swift.struct/attribute/visiblecharacterrange); a 50 MiB single line may therefore be represented by a 50 MiB `NSRange` without allocating its text. This is **not a physical glyph-visibility assertion**: only bounded `CanvasFrame.RowWindows` and target-host paint/PNG evidence describe the horizontal source window. The Windows visible ranges describe only actually shaped source slices, not hidden portions of a long line. Word-unit and grapheme-unit navigation, point hit-testing, and bounding rectangles are **not yet implemented**; the OS provider cannot truthfully advertise a full editable text pattern until these are resolved.

| Concern | Current invariant | Remaining OS gate |
| --- | --- | --- |
| Offscreen text | Range `GetText` reads directly from immutable rope snapshot. | Register and query a real OS element; verify `DocumentRange` and offscreen `StringForRange`. |
| Per-request memory | 65,536 UTF-16 units maximum; `maxLength=-1` over that fails explicitly, never silently truncates. | Determine what HRESULT / AppKit failure behavior actual readers tolerate, and whether a larger or adaptive budget is needed. The current policy is *not* proof of screen-reader usability. |
| Selection | Global anchor/active, no island-local inference. | Raise correct selection/text-change events and verify spoken cursor location. |
| Visibility/scroll | Version-matched frame; `IAccessibleViewport.TryScrollIntoView(range, alignToTop)` is the intended UI-thread hook. | Controller must reveal offscreen source and publish a new frame; veto safely if moving the host would destroy active composition. Geometry must come from real shaper hit-testing. |
| Single speech source | Source model contains no duplicate island text. | Hide the bounded RichEdit/NSTextView from the OS accessibility tree **without removing keyboard focus/IME**; verify tree and speech. |
| Native AOT | Range cores are ordinary AOT-compatible C#. | Windows COM provider needs source-generated `ComWrappers` or explicit ABI-safe vtables; Mac needs actual AppKit accessibility element/selectors. Validate x64 and arm64 ABIs and one-file inventory. |

## Interface hook to integrate

The controller owns the view and exposes **one** synchronous UI-thread operation: `IAccessibleViewport.TryReveal(AccessibleRange range, bool alignToTop) -> AccessibleRevealResult`. `AccessibleRange` itself carries generation/version, so the callback validates both plus range bounds against current source. Results are `Revealed`, `CompositionBlocked`, `StaleRange`, `NotVisible`, and `WrongThread`. Only `Revealed` means the controller revealed the requested source boundary in `CanvasInteraction` **and published a matching `AccessibleCanvasState` whose bounded painted slice actually contains it** before returning. Active IME composition returns `CompositionBlocked` without forced commit/cancel. `NotVisible` reports a valid current range that cannot be represented in the painted bounded slices; a callback on the wrong thread returns `WrongThread`, never posting then synchronously waiting for the UI thread. The Windows prototype maps `StaleRange` to `UIA_E_ELEMENTNOTAVAILABLE` and composition/not-visible/wrong-thread to `UIA_E_INVALIDOPERATION`, not false `S_OK`. Whether external COM callbacks arrive on the provider's owning UI apartment is a target-OS gate; if they do not, `ScrollIntoView` may be unavailable until a safe dispatcher design is proven.

The shell owns OS provider lifetime; the controller calls `AccessibleDocument.Publish(new AccessibleCanvasState(G,snapshot,frame))` atomically after each committed source/selection/viewport transition, **even if a grapheme-safe input island cannot be bound**. It calls `Invalidate()` on close; that clears the retained snapshot while rejecting old client ranges. The provider must not independently scroll a second viewport, replace the island's text, or accept a range from another generation. `Publish` rejects regressing generations/versions and copies the bounded slice list so later view-cache mutation cannot change an already visible AX frame. This single publication replaces the former separate `Rebind`/`SetFrame` sequence that could mix source, selection and geometry.

## Design pressure from platform and production evidence

Microsoft's [`ITextProvider`](https://learn.microsoft.com/en-us/windows/win32/api/uiautomationcore/nn-uiautomationcore-itextprovider) requires document/selection/visible ranges and point mapping; [`ITextRangeProvider::GetText`](https://learn.microsoft.com/en-us/windows/win32/api/uiautomationcore/nf-uiautomationcore-itextrangeprovider-gettext) says `-1` means no length limit and includes offscreen text. Therefore returning a successful 64 Ki prefix for an unbounded request would lie to the client. **Current HRESULT policy:** `S_OK` only for an exact result within the 65,536-unit budget; `E_INVALIDARG` for `maxLength < -1`; `UIA_E_ELEMENTNOTAVAILABLE` for an invalidated document/range; `UIA_E_INVALIDOPERATION` for a request exceeding the provider's *policy* budget, with no BSTR result; actual allocation failure remains `E_OUTOFMEMORY`. This changed from the original policy after the published-AOT A/B probe below: `E_OUTOFMEMORY` poisoned a cached UIA TextPattern proxy, whereas `UIA_E_INVALIDOPERATION` kept it usable for smaller requests. This is an empirical interoperability choice, **not** a dedicated oversize rule in [UIA's error-code list](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-error-codes) or a Narrator pass. An explicit failure is safer for data correctness, but may make a reader unusable if it insists on whole-document retrieval; this is the principal unresolved API tension. Preserve the full `DocumentRange` even if `GetText(-1)` fails for huge ranges so clients that navigate and make bounded requests can still reach every source offset. Do **not** assert that Narrator does so: no authoritative public call trace establishing its range-request pattern was found. Instrument privacy-safe `(method, maxLength, range length, HRESULT, duration)` and test Narrator plus NVDA on small/100 MiB fixtures before release. Microsoft's [`WM_GETOBJECT`](https://learn.microsoft.com/en-us/windows/win32/winauto/wm-getobject) path and [server-side provider guidance](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-serversideprovider) define the Windows registration path. .NET's [source-generated COM interop](https://learn.microsoft.com/en-us/dotnet/standard/native-interop/comwrappers-source-generation) is the AOT-compatible option; ordinary runtime COM wrappers are not.

Apple's [`NSAccessibilityProtocol`](https://developer.apple.com/documentation/appkit/nsaccessibilityprotocol) includes selected/visible text ranges, string-for-range, frame-for-range, and line mappings. Apple's [visible-character-range guidance](https://developer.apple.com/documentation/appkit/nsaccessibilitystatictext/accessibilityvisiblecharacterrange%28%29) says to include entire lines even when horizontally clipped. A future AppKit subclass must implement those selectors with pointer-sized `NSRange`/`NSInteger` signatures and return screen-space geometry from the same canvas shaper.

Production precedent is informative but not a drop-in solution: VS Code [documents a distinct screen-reader optimized mode](https://github.com/microsoft/vscode-docs/blob/main/docs/configure/accessibility/accessibility.md) and [describes a focused hidden editor neighborhood](https://github.com/microsoft/vscode/issues/257834). That demonstrates the importance of testing what assistive technology actually speaks, not merely the backing text representation. Mote's strict native-provider goal deliberately differs: it should expose whole-document source ranges rather than claiming its bounded IME host is the accessible document. VS Code's browser/ARIA implementation cannot establish Windows UIA or AppKit behavior for Mote.

## Independent core-contract audit, 2026-09-29

This section reviews the **source-backed cores**, not an OS-registered provider. It deliberately separates a proven model property from a future UIA/AppKit contract. During the audit, the accessibility owner repaired the identified core findings below and reported **11 focused accessibility tests passing**; the table preserves their failure mechanisms so future adapters do not reintroduce them. No on-screen provider or reader result follows from those unit tests.

| Priority | Concrete finding and mechanism | Smallest discriminating repair/test |
| --- | --- | --- |
| **Fixed in core — frame identity can cross documents at the same version** | Initially `SetFrame` checked only `CanvasFrame.Version`; a delayed frame from document A at version 0 could be accepted after B bound at version 0 and overwrite B's selection/visibility. The repair requires an **expected document generation** together with the frame version, and focused tests reject mismatches. `Rebind` still relies on the controller to increment generation for a new document; the OS integration must maintain that invariant. | In a controller/OS callback test, bind equal-length A and B at version 0, deliver A's late frame with A's generation after B binds, and confirm B's visible range/selection is unchanged. Do not let a platform wrapper drop the generation token. |
| **Fixed in core — empty UIA visibility result** | Originally zero slices yielded an empty array, contrary to Microsoft's [`ITextProvider::GetVisibleRanges`](https://learn.microsoft.com/en-us/windows/win32/api/uiautomationcore/nf-uiautomationcore-itextprovider-getvisibleranges), which asks for a **degenerate range** when no text is visible. The repair returns one degenerate range at the current viewport source anchor, covered by a focused test. | The real COM wrapper must still return a non-null SAFEARRAY containing that range; inspect empty document and empty-visible-frame behavior in Accessibility Insights. |
| **Fixed in core — adjacent visible rows were advertised as disjoint** | Originally one range was emitted per slice, omitting delimiters. The repair merges adjacent complete-line spans, including their exact 1- or 2-unit source delimiters, while keeping horizontally clipped windows disjoint. A focused CRLF/LF test covers this. Microsoft asks one range per contiguous visible text span ([same contract](https://learn.microsoft.com/en-us/windows/win32/api/uiautomationcore/nf-uiautomationcore-itextprovider-getvisibleranges)). | Verify in the actual shaper/provider that `HasHiddenPrefix/Suffix`, line IDs and slice order truthfully describe geometry; `ValidateFrame` currently checks bounds but not those cross-field relationships. Compare to a native-control oracle for adjacent CR/LF/CRLF and clipped long lines. |
| **Fixed at scalar/CRLF cutoff; grapheme boundary remains open** | Initial `GetText(range, maxLength)` could end after a high surrogate or CR of CRLF. The repair floors a truncated result by one code unit at either seam, so a bounded successful read no longer creates half of those pairs; focused tests cover them. It does **not** certify extended grapheme boundaries (combining marks/ZWJ), and `MakeRange` still permits a caller-supplied start/end inside a surrogate pair. Apple's [`NSString`](https://developer.apple.com/documentation/foundation/nsstring) explicitly distinguishes UTF-16 code units from composed-character boundaries. | Define/test provider-created range movement and cutoff at UAX #29 cluster boundaries without exceeding `maxLength`; distinguish exact caller-requested source ranges from user-facing character navigation. Include astral, combining, ZWJ and CRLF fixtures. |
| **Fixed in core — UIA's no-visible sentinel briefly became a false Mac line** | After the UIA repair, `VisibleRanges()` always returns one degenerate range when there are zero slices. The original Mac adapter checked only `visible.Count == 0`, so it could expand that sentinel to an entire logical line at the anchor. The repair computes `VisibleLogicalLineRange()` from **one captured binding** and returns the degenerate anchor range when no slice is painted; a 50 MiB-line regression covers it. | The eventual AppKit selector must preserve the no-visible distinction and not replace the source binding midway through its native call. |
| **Fixed in core; OS provider threading still open** | Initially `GetText` validated against one `_binding` read and later read `_binding.Snapshot` again, allowing a concurrent `Rebind` to validate A but return B. `SetFrame` could also validate then overwrite a newer binding. The repair captures one immutable binding per core read via `Volatile.Read`, while `Rebind`/`SetFrame` publish under a lock and `SetFrame` checks generation/version inside it. Mac whole-line visibility is computed from one capture. This removes the identified core time-of-check/time-of-use path, not all future native callback or UI-thread deadlocks. | Stress Rebind/GetText/SetFrame interleavings, then choose and document the real COM/AppKit callback thread/dispatcher model; `TryScrollIntoView` must not synchronously wait on a blocked UI thread. COM apartment/message-loop behavior is material here ([Microsoft COM apartments](https://learn.microsoft.com/en-us/windows/win32/com/processes--threads--and-apartments)). |
| **Release gate — valid unbounded requests may fail, and Mac's visible range can exceed the cap** | `ITextRangeProvider::GetText(-1)` means the **entire** requested range, including offscreen text ([Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/uiautomationcore/nf-uiautomationcore-itextrangeprovider-gettext)). The core rightly refuses to return a successful truncated prefix above 65,536 units, but choosing `E_OUTOFMEMORY` for an artificial budget has no dedicated “too large” UIA specification and may cause readers to stop. The Mac core can accurately report a 50 MiB visible logical line while `StringForRange` then fails for that same range. That tension is not fixed by the range model. | Instrument privacy-safe `(method, requested length, maxLength, HRESULT/nil, duration)` during actual Narrator/NVDA/VoiceOver tasks on small and 100 MiB files. Check whether clients request bounded subranges after a large-range failure. If they require unbounded materialization, design a user-visible, standards-compatible bounded-access mode or explicitly carry this as a release blocker; never claim a false full range or truncate a successful `GetText(-1)`. |

Two integration hooks require particular care even after the core fixes. First, `ITextProvider::GetSelection` and AppKit selected range must reflect the **global** anchor/active, while the native input island remains focusable for IME; verify one accessible editor and no duplicate speech in the real tree. Second, `TryScrollIntoView` must atomically move the controller viewport, publish a current-generation/current-version frame, and return failure if composition cannot be preserved. A stale range must map to an OS-appropriate failure on **every** provider method, not only Windows `TryGetText`; never show geometry from the old file after a successful-looking scroll. `GetText(-1)`'s exactness and whole-document `DocumentRange` are separate properties: the latter is already modeled, but reader interoperability is still an experiment.

## OS registration feasibility prototypes, 2026-09-29

**Windows.** `src/Mote.Native/Windows/Accessibility/WindowsUiaBridgePrototype.cs` defines source-generated IUnknown COM interfaces with the Windows SDK `IRawElementProviderSimple`, `ITextProvider` and `ITextRangeProvider` GUIDs and vtable order. In experimental canvas mode, the shell's canvas HWND routes `WM_GETOBJECT` to `WindowsUiaBridgePrototype.HandleGetObject(hwnd,wParam,lParam)`, which obtains a generated COM pointer and calls the OS `UiaReturnRawElementProvider`, following [Microsoft's WM_GETOBJECT contract](https://learn.microsoft.com/en-us/windows/win32/api/uiautomationcoreapi/nf-uiautomationcoreapi-uiareturnrawelementprovider); `Close(hwnd)` notifies UIA from `WM_DESTROY`. The probe publishes a source-backed Document control element, document/selection/visible ranges as `SAFEARRAY(VT_UNKNOWN)`, exact bounded `BSTR` text, and a source viewport scroll callback. A Windows in-process test calls its **actual generated COM vtable** to get the document range, read a bounded offscreen prefix, reject an oversized unbounded request, and inspect the selected-range SAFEARRAY. A published win-x64 Native AOT executable has now also passed an **external** UIA-client bounded/offscreen/stale-range probe, detailed below; no screen-reader pass. Windows SDK `UIAutomationCore.h` at 10.0.26100.0 supplied GUID/order/enum values; [source-generated COM documentation](https://learn.microsoft.com/en-us/dotnet/standard/native-interop/comwrappers-source-generation) explains why ordinary runtime COM wrappers are unsuitable for Native AOT.

This Windows object is **not yet a conformant, default-enabled Text pattern**. `RangeFromPoint`, character/word/line movement, bounding rectangles, selection mutation, text search, attributes, and events are explicit `E_NOTIMPL` placeholders. The root provider binds its HWND and calls [`UiaHostProviderFromHwnd`](https://learn.microsoft.com/en-us/windows/win32/api/uiautomationcoreapi/nf-uiautomationcoreapi-uiahostproviderfromhwnd), but external tree inspection found a **second focused RichEdit Document**; this is a failing one-editor gate, not an untested assumption. Registering this partial pattern in the default editor would mislead clients because [Microsoft's Document control type](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-supportdocumentcontroltype) requires a usable Text pattern. Validate COM reference counts, SAFEARRAY/BSTR ownership, `VARIANT` ABI, and text-pattern method behavior on both win-x64 and win-arm64 before default enablement. The in-process vtable test and external bounded-range probe are useful evidence, **not** a Narrator pass.

**macOS.** `src/Mote.Native/Mac/Accessibility/MacAccessibilityElementPrototype.cs` dynamically subclasses `NSAccessibilityElement` through the existing Objective-C runtime bridge. In experimental canvas mode, the shell attaches one AX text-area child to the real canvas view, hides the bounded input view from the AX tree while leaving native focus untouched, updates parent-space frame after resize, and disposes on the AppKit UI thread before view teardown. It preserves/restores the prior child list/accessibility flag. It provides source-backed `accessibilityNumberOfCharacters`, selected/visible UTF-16 ranges, `accessibilityStringForRange:`, `accessibilityLineForIndex:`, and `accessibilityRangeForLine:`. Apple's [`NSAccessibilityElement` guidance](https://developer.apple.com/documentation/appkit/nsaccessibilityelement-swift.class?language=o_6) supports a non-view element attached to the parent view's accessibility children; [`NSAccessibilityProtocol`](https://developer.apple.com/documentation/appkit/nsaccessibilityprotocol) defines the text selectors. The code compiles in the shared C# project on Windows and its shell hook compiles for target Mac builds, but **no published-binary external AXUIElement, Accessibility Inspector or VoiceOver result has passed yet**. Hiding the input view still must be tested against focus, VoiceOver editing, and real IME candidate tracking.

This Mac object now sets its [parent-space frame](https://developer.apple.com/documentation/appkit/nsaccessibilityelement-swift.class/accessibilityframeinparentspace) from canvas bounds and maps focused-element queries/requests to the real `NSTextView` first responder. It still lacks `accessibilityFrameForRange:`, point-to-range mapping, selected-range setter, text-value behavior for requests above 65,536 units, and notifications; those new frame/focus hooks have no on-screen acceptance result. In particular, it returns `nil` for oversized `accessibilityStringForRange:` rather than a false truncated string; VoiceOver may or may not recover by smaller range requests. The Objective-C `NSRange`/`NSInteger` and callback return ABI must be checked on **both** osx-x64 and osx-arm64; compilation on Windows does not validate this. Probe with Accessibility Inspector then VoiceOver on an interactive logged-in Mac, including offscreen marker navigation and active real IME composition. Do not treat a successful in-process selector call alone as a speech pass.

## External Windows UIA probe: first published-AOT result and negative evidence

On Windows NT 10.0.26200.0, the Windows-shell owner used `.temp/WindowsAxExternalProbe` (a `net10.0-windows` WindowsDesktop UIAutomationClient process) against a strict one-file Native AOT win-x64 product binary at `.cache/ax_shell_aot/mote.exe` (6,085,632 bytes, SHA-256 `D514ABFA75B962D8E3A734A89E4061F3273C8E885A2BB96423CF65334581F60C`). The fixture contained 9,000 LF-delimited rows, more than 65,536 UTF-16 units, and an offscreen `TAIL_AX_MARKER_世界😀`. These observations are external UIA client calls to a **published executable**, not a direct managed-vtable unit test; there was no Narrator/NVDA speech trial.

The exact call order matters:

1. `AutomationElement.FromHandle(canvas)` obtained TextPattern; `GetSelection()` returned one range. `DocumentRange.GetText(128)` matched the engine-backed file prefix. The bounded RichEdit island contained only 16 UTF-16 units, so the external range was not simply the input host's page.
2. `DocumentRange.GetText(-1)` over the >64 Ki range failed as intended rather than returning a misleading truncated `S_OK`. **After this failure**, the *same cached TextPattern proxy* reported `ElementNotAvailableException` (`0x80040201`) for both `GetSelection()` and `GetVisibleRanges()`. A freshly acquired `AutomationElement`/TextPattern from the same canvas HWND again returned one selected range. This is a reproducible **proxy-poisoning negative result**, not proof that the server-side SAFEARRAY itself is broken: selection succeeded before the unbounded refusal, and reacquisition recovered. The hypothesized UIA-client/proxy reaction to `E_OUTOFMEMORY` remains to be discriminated experimentally.
3. In the control run **without** the oversized call, scrolling to bottom yielded one visible range whose `GetText(-1)` contained the offscreen tail marker. After New on the same HWND, old range access failed; after close, newly obtained range access failed. This supports reachable source-backed offscreen text, stale-generation invalidation and close invalidation in this fixture, but does not establish word/character navigation, geometry, IME coexistence or speech.
4. A separate tree query found `AutomationElement.FromHandle(input).Current.ControlType == Document`, name `RichEdit Control`, **and** the canvas's first ControlView child was also `Document`. Thus the bounded input host and source-backed provider are two Document nodes in ControlView. This violates the intended one-logical-editor tree until a focus-preserving remedy is measured; no duplicate-speech claim can be made without Narrator/NVDA.

The discriminating A/B experiment is now complete. Under the original `E_OUTOFMEMORY` mapping, the external WindowsDesktop client surfaced `COMException` `0x8000FFFF` for the oversized call, then the cached TextPattern's selection/visible queries failed `0x80040201`; fresh reacquisition worked. ## Bottom input-ribbon geometry contract (diagnostic)

The new physical input ribbon is **not a source-painted row**. `CanvasFrame.Slices/RowWindows` describe the body only; when the physical body height is zero, `CanvasInteraction.Resize(0)` publishes empty arrays. `AccessibleDocument.VisibleRanges()` then returns UIA's required one **degenerate** range, and the Mac visible-character selector returns a degenerate range at the same source top anchor. No provider-specific second visibility flag or nominal 1-pixel source row is allowed. A focused zero→normal→zero model test verifies empty/positive/empty visible ranges with unchanged source identity; the 26 focused AX tests passed after the frame contract landed.

On Windows, `WindowsUiaBridgePrototype.SetSourceBodyClientHeight(int)` receives **canvas client-coordinate units** (zero for tiny input-only layout). The fragment root Pane retains the full canvas outer rectangle; its sole source Document child and `ElementProviderFromPoint` use only the body rectangle, excluding the ribbon. The bridge maps client corners through `ClientToScreen`; it does **not** guess an extra DPI scale factor. UIA `ITextProvider.RangeFromPoint` and `ITextRangeProvider.GetBoundingRectangles` remain `E_NOTIMPL`, so no pixel-to-source text range is invented. A real-HWND focused test checks zero versus normal body height, but published high-DPI parity of UIA physical screen rectangles against actual canvas pixels at 96/144/192 DPI is **not yet verified**; [Win32 documents `GetWindowRect` DPI virtualization](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getwindowrect), so client-to-screen arithmetic alone is not a promotion claim.

On macOS, the custom source `AXTextArea` receives the canvas-local body `ObjC.Rect(0,min(36,h),w,max(0,h−36))` at **Attach**, before its AX child is exposed, and `UpdateBodyRect` updates its parent-space outer frame on later layout changes. The bounded `NSTextView` remains the physical input/IME owner but is hidden as a duplicate AX text area. The provider's text visible range still reads only one immutable engine-backed `CanvasFrame`; BodyRect affects the outer AX frame, **not** text-range pixel geometry. On the AppKit UI thread, shrinking must publish fewer/empty source rows before shrinking the AX body rect, while growing updates the body rect before publishing expanded rows; transient mismatches are thereby conservative. No range-frame or point-to-range selector is implemented yet. During marked-text composition, the Mac shell currently defers both resize publications to protect candidate geometry; a physical resize may temporarily leave old visible-range claims until composition ends. This is an explicit target-host interaction gate, not accepted accessibility geometry. Rapid normal→tiny→normal resize with AXFrame/visible-range queries and real IME composition is the discriminating next probe.

Initial `Attach(..., BodyRect)` validates the rectangle **before** claiming the input editor or global provider instance; this source-order fix prevents an invalid rectangle from entering `Dispose` with an uncaptured original input accessibility flag. A target-AppKit invalid-rect fault-injection test must still verify that failed Attach leaves the input flag and prior AX children unchanged, repeated Dispose is harmless, and a subsequent valid Attach succeeds. It was deliberately deferred until after the first hosted ribbon diagnostic to preserve the Mac probe's single-writer source freeze; it is **not** a passed regression yet.

### Hosted Mac AX whole-line range is not physical horizontal visibility

[CI run 36594818528](https://github.com/kleedaisuki/mote/actions/runs/36594818528), artifact `native-canvas-gui-osx-arm64`, contains three cross-process `AXUIElementCreateApplication(pid)` source-gate observations in `.cache/ci-run-36594818528/native-canvas-gui-osx-arm64/.cache/benchmarks/native-canvas-gui-osx-arm64.jsonl`. The tracked `benchmarks/NativeCanvasGui/CanvasAxGate.swift` calls `AXVisibleCharacterRange` **directly** on the unique source-backed proxy and decodes its returned CFRange; the benchmark does not expand a slice into a line in its own helper. The published-Mach-O in-process horizontal probe in the same run separately recorded a maximum source shaping slice of **16,384 UTF-16 units** and bounded horizontal paint.

| Source fixture / AX observation | Interpretation |
| --- | --- |
| One 50 Mi-unit logical line: AX `visibleStart=0`, `visibleLength=52,428,800` in the external source gate. | **Expected AppKit logical-line contract**, not a statement that 50 Mi units occupy the screen. [Apple explicitly says `visibleCharacterRange` returns entire lines, including horizontally clipped characters](https://developer.apple.com/documentation/appkit/nsaccessibility-swift.struct/attribute/visiblecharacterrange). The provider computes `VisibleLogicalLineRange()` from a nonempty painted slice and returns only an `NSRange`, not the 50 Mi text. |
| Many-line 100 Mi-unit fixture: AX visible range `0/2176` before paging and `2113/2240` after Next Page. | The logical-line envelope moves with vertical viewport state; these values do not encode exact per-glyph horizontal visibility. |

This investigation **rejects** the hypothesis that the 50 Mi AX value is a Swift-helper expansion or a provider defect requiring horizontal clipping of `AXVisibleCharacterRange`. No Mac provider source was changed. The separate interoperability tension remains: `accessibilityStringForRange:` refuses an over-65,536-unit materialization, so a client that requests the entire 50 Mi visible logical line as one string receives no value; whether VoiceOver instead asks bounded subranges is unmeasured. Keep the distinction among (1) whole-line AX metadata, (2) bounded painted source windows, and (3) bounded string extraction explicit in future probes and release claims.
