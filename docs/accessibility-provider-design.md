# Whole-document accessibility provider: source-backed prototype and release gaps

Status: **range core plus unconnected Windows/AppKit provider prototypes**, 2026-09-29. This document owns the accessibility slice of [virtual-editor-design.md](virtual-editor-design.md); input-composition risks remain in [input-island-design.md](input-island-design.md). No Narrator, NVDA, VoiceOver, Accessibility Inspector, or UIA-tree acceptance pass is claimed.

## The single-editor invariant

`AccessibleDocument` in `src/Mote.Native/Accessibility/` binds one immutable `TextSnapshot`, document generation, snapshot version, global anchor/active offsets, and one version-matched `CanvasFrame`. Its `DocumentRange` is always `0..Snapshot.Length`, independent of the caret-local input island or the painted viewport. Every `AccessibleRange` carries `(generation, version, start, end)` in half-open UTF-16 source coordinates. A stale range is rejected after a document swap or edit rather than interpreted against unrelated bytes. Selection direction remains available separately from its ordered interval. The model never calls `TextSnapshot.GetText()` without a bounded `(start, length)` and never uses `GetLine()` on a long logical line.

`WindowsTextProviderCore` and `MacAccessibilityTextCore` are **platform semantic adapters, not registered OS providers**. The Windows core covers document range, global selection, visible slice ranges, line/range mappings, `GetText(maxLength)`, and a controller-owned scroll request. The Mac core covers character count, selected/visible range, source string-for-range, and line/range mappings. The Mac visible range covers *whole logical lines* (including horizontal clipping), matching Apple's documented requirement; a 50 MiB single line may therefore be represented by a 50 MiB `NSRange` without allocating its text. The Windows visible ranges describe only actually shaped source slices, not hidden portions of a long line. Word-unit and grapheme-unit navigation, point hit-testing, and bounding rectangles are **not yet implemented**; the OS provider cannot truthfully advertise a full editable text pattern until these are resolved.

| Concern | Current invariant | Remaining OS gate |
| --- | --- | --- |
| Offscreen text | Range `GetText` reads directly from immutable rope snapshot. | Register and query a real OS element; verify `DocumentRange` and offscreen `StringForRange`. |
| Per-request memory | 65,536 UTF-16 units maximum; `maxLength=-1` over that fails explicitly, never silently truncates. | Determine what HRESULT / AppKit failure behavior actual readers tolerate, and whether a larger or adaptive budget is needed. The current policy is *not* proof of screen-reader usability. |
| Selection | Global anchor/active, no island-local inference. | Raise correct selection/text-change events and verify spoken cursor location. |
| Visibility/scroll | Version-matched frame; `IAccessibleViewport.TryScrollIntoView(range, alignToTop)` is the intended UI-thread hook. | Controller must reveal offscreen source and publish a new frame; veto safely if moving the host would destroy active composition. Geometry must come from real shaper hit-testing. |
| Single speech source | Source model contains no duplicate island text. | Hide the bounded RichEdit/NSTextView from the OS accessibility tree **without removing keyboard focus/IME**; verify tree and speech. |
| Native AOT | Range cores are ordinary AOT-compatible C#. | Windows COM provider needs source-generated `ComWrappers` or explicit ABI-safe vtables; Mac needs actual AppKit accessibility element/selectors. Validate x64 and arm64 ABIs and one-file inventory. |

## Interface hook to integrate

The controller owns the view and exposes **one** UI-thread operation: `TryScrollIntoView(AccessibleRange range, bool alignToTop)`. It validates generation/version, reveals the requested source boundary in `CanvasInteraction`, publishes `SetCanvasFrame`, and returns false if live IME composition cannot safely retain its candidate. The shell owns the OS provider lifetime and calls `AccessibleDocument.Rebind` after committed snapshot changes and `SetFrame` after scroll/resize/selection changes. The accessibility provider must not independently scroll a second viewport, replace the native island's text, or accept a range from a previous document. Prefer an immutable state handoff (binding plus frame) to multiple independently updated fields; otherwise UIA can observe mismatched source, selection, and geometry.

## Design pressure from platform and production evidence

Microsoft's [`ITextProvider`](https://learn.microsoft.com/en-us/windows/win32/api/uiautomationcore/nn-uiautomationcore-itextprovider) requires document/selection/visible ranges and point mapping; [`ITextRangeProvider::GetText`](https://learn.microsoft.com/en-us/windows/win32/api/uiautomationcore/nf-uiautomationcore-itextrangeprovider-gettext) says `-1` means no length limit and includes offscreen text. Therefore returning a successful 64 Ki prefix for an unbounded request would lie to the client. **Proposed HRESULT policy:** `S_OK` only for an exact result within the 65,536-unit budget; `E_INVALIDARG` for `maxLength < -1`; `UIA_E_ELEMENTNOTAVAILABLE` for an invalidated document/range; `E_OUTOFMEMORY` for a request that exceeds the provider's fixed per-call allocation budget (or actual allocation failure), with no BSTR result. `E_OUTOFMEMORY` here signals the provider cannot allocate within its enforced budget, *not* proof of physical RAM exhaustion. These are implementation choices, not a documented special-case prescription for oversize `GetText`; [UIA's error-code list](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-error-codes) has no dedicated "request too large" status. An explicit failure is safer for data correctness, but may make a reader unusable if it insists on whole-document retrieval; this is the principal unresolved API tension. Preserve the full `DocumentRange` even if `GetText(-1)` fails for huge ranges so clients that navigate and make bounded requests can still reach every source offset. Do **not** assert that Narrator does so: no authoritative public call trace establishing its range-request pattern was found. Instrument privacy-safe `(method, maxLength, range length, HRESULT, duration)` in a local build and test Narrator plus NVDA on small/100 MiB fixtures before release. Microsoft's [`WM_GETOBJECT`](https://learn.microsoft.com/en-us/windows/win32/winauto/wm-getobject) path and [server-side provider guidance](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-serversideprovider) define the Windows registration path. .NET's [source-generated COM interop](https://learn.microsoft.com/en-us/dotnet/standard/native-interop/comwrappers-source-generation) is the AOT-compatible option; ordinary runtime COM wrappers are not.

Apple's [`NSAccessibilityProtocol`](https://developer.apple.com/documentation/appkit/nsaccessibilityprotocol) includes selected/visible text ranges, string-for-range, frame-for-range, and line mappings. Apple's [visible-character-range guidance](https://developer.apple.com/documentation/appkit/nsaccessibilitystatictext/accessibilityvisiblecharacterrange%28%29) says to include entire lines even when horizontally clipped. A future AppKit subclass must implement those selectors with pointer-sized `NSRange`/`NSInteger` signatures and return screen-space geometry from the same canvas shaper.

Production precedent is informative but not a drop-in solution: VS Code [documents a distinct screen-reader optimized mode](https://github.com/microsoft/vscode-docs/blob/main/docs/configure/accessibility/accessibility.md) and [describes a focused hidden editor neighborhood](https://github.com/microsoft/vscode/issues/257834). That demonstrates the importance of testing what assistive technology actually speaks, not merely the backing text representation. Mote's strict native-provider goal deliberately differs: it should expose whole-document source ranges rather than claiming its bounded IME host is the accessible document. VS Code's browser/ARIA implementation cannot establish Windows UIA or AppKit behavior for Mote.

## Next acceptance experiment

1. On Windows, register an AOT-safe minimal `IRawElementProviderSimple`/`ITextProvider` on the canvas HWND and inspect `DocumentRange`, selected range, offscreen marker, `GetText(4096)`, `GetText(-1)` on a >64 Ki range, and `ScrollIntoView` with Accessibility Insights and Narrator/NVDA. On macOS, register the AppKit element and run analogous Accessibility Inspector/VoiceOver tasks. Keep logs/screenshots inside root `.temp/` or `.cache/`.
2. Use a document with CR, LF, CRLF, surrogate pair, a 100 Ki line, and a unique marker beyond the previous page boundary. Query a selected interval crossing the bounded island. Compare client-observed UTF-16 offsets and returned source text to engine snapshot; record latency, peak allocation, tree shape, spoken output, and whether the candidate window survives AX scrolling during real IME composition.
3. If clients require `GetText(-1)` for the entire 100 MiB file, investigate a compliant failure/streaming alternative or an accessibility-specific bounded reading mode **without advertising a false complete range**. Do not switch the canvas default until this is resolved empirically.

Unit tests in `tests/Mote.Tests/AccessibilityDocumentTests.cs` cover source range, stale generation, line-ending, bounded request, visible frame, and scroll-hook semantics. They cannot validate OS provider registration, COM/AppKit ABI, speech, focus, or IME coexistence.

## Independent core-contract audit, 2026-09-29

This section reviews the **source-backed cores**, not an OS-registered provider. It deliberately separates a proven model property from a future UIA/AppKit contract. During the audit, the accessibility owner repaired the identified core findings below and reported **11 focused accessibility tests passing**; the table preserves their failure mechanisms so future adapters do not reintroduce them. No on-screen provider or reader result follows from those unit tests.

| Priority | Concrete finding and mechanism | Smallest discriminating repair/test |
| --- | --- | --- |
| **Fixed in core — frame identity can cross documents at the same version** | Initially `SetFrame` checked only `CanvasFrame.Version`; a delayed frame from document A at version 0 could be accepted after B bound at version 0 and overwrite B's selection/visibility. The repair requires an **expected document generation** together with the frame version, and focused tests reject mismatches. `Rebind` still relies on the controller to increment generation for a new document; the OS integration must maintain that invariant. | In a controller/OS callback test, bind equal-length A and B at version 0, deliver A's late frame with A's generation after B binds, and confirm B's visible range/selection is unchanged. Do not let a platform wrapper drop the generation token. |
| **Fixed in core — empty UIA visibility result** | Originally zero slices yielded an empty array, contrary to Microsoft's [`ITextProvider::GetVisibleRanges`](https://learn.microsoft.com/en-us/windows/win32/api/uiautomationcore/nf-uiautomationcore-itextprovider-getvisibleranges), which asks for a **degenerate range** when no text is visible. The repair returns one degenerate range at the current viewport source anchor, covered by a focused test. | The real COM wrapper must still return a non-null SAFEARRAY containing that range; inspect empty document and empty-visible-frame behavior in Accessibility Insights. |
| **Fixed in core — adjacent visible rows were advertised as disjoint** | Originally one range was emitted per slice, omitting delimiters. The repair merges adjacent complete-line spans, including their exact 1- or 2-unit source delimiters, while keeping horizontally clipped windows disjoint. A focused CRLF/LF test covers this. Microsoft asks one range per contiguous visible text span ([same contract](https://learn.microsoft.com/en-us/windows/win32/api/uiautomationcore/nf-uiautomationcore-itextprovider-getvisibleranges)). | Verify in the actual shaper/provider that `HasHiddenPrefix/Suffix`, line IDs and slice order truthfully describe geometry; `ValidateFrame` currently checks bounds but not those cross-field relationships. Compare to a native-control oracle for adjacent CR/LF/CRLF and clipped long lines. |
| **Fixed at scalar/CRLF cutoff; grapheme boundary remains open** | Initial `GetText(range, maxLength)` could end after a high surrogate or CR of CRLF. The repair floors a truncated result by one code unit at either seam, so a bounded successful read no longer creates half of those pairs; focused tests cover them. It does **not** certify extended grapheme boundaries (combining marks/ZWJ), and `MakeRange` still permits a caller-supplied start/end inside a surrogate pair. Apple's [`NSString`](https://developer.apple.com/documentation/foundation/nsstring) explicitly distinguishes UTF-16 code units from composed-character boundaries. | Define/test provider-created range movement and cutoff at UAX #29 cluster boundaries without exceeding `maxLength`; distinguish exact caller-requested source ranges from user-facing character navigation. Include astral, combining, ZWJ and CRLF fixtures. |
| **Fixed in core — UIA's no-visible sentinel briefly became a false Mac line** | After the UIA repair, `VisibleRanges()` always returns one degenerate range when there are zero slices. The original Mac adapter checked only `visible.Count == 0`, so it could expand that sentinel to an entire logical line at the anchor. The repair computes `VisibleLogicalLineRange()` from **one captured binding** and returns the degenerate anchor range when no slice is painted; a 50 MiB-line regression covers it. | The eventual AppKit selector must preserve the no-visible distinction and not replace the source binding midway through its native call. |
| **Fixed in core; OS provider threading still open** | Initially `GetText` validated against one `_binding` read and later read `_binding.Snapshot` again, allowing a concurrent `Rebind` to validate A but return B. `SetFrame` could also validate then overwrite a newer binding. The repair captures one immutable binding per core read via `Volatile.Read`, while `Rebind`/`SetFrame` publish under a lock and `SetFrame` checks generation/version inside it. Mac whole-line visibility is computed from one capture. This removes the identified core time-of-check/time-of-use path, not all future native callback or UI-thread deadlocks. | Stress Rebind/GetText/SetFrame interleavings, then choose and document the real COM/AppKit callback thread/dispatcher model; `TryScrollIntoView` must not synchronously wait on a blocked UI thread. COM apartment/message-loop behavior is material here ([Microsoft COM apartments](https://learn.microsoft.com/en-us/windows/win32/com/processes--threads--and-apartments)). |
| **Release gate — valid unbounded requests may fail, and Mac's visible range can exceed the cap** | `ITextRangeProvider::GetText(-1)` means the **entire** requested range, including offscreen text ([Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/uiautomationcore/nf-uiautomationcore-itextrangeprovider-gettext)). The core rightly refuses to return a successful truncated prefix above 65,536 units, but choosing `E_OUTOFMEMORY` for an artificial budget has no dedicated “too large” UIA specification and may cause readers to stop. The Mac core can accurately report a 50 MiB visible logical line while `StringForRange` then fails for that same range. That tension is not fixed by the range model. | Instrument privacy-safe `(method, requested length, maxLength, HRESULT/nil, duration)` during actual Narrator/NVDA/VoiceOver tasks on small and 100 MiB files. Check whether clients request bounded subranges after a large-range failure. If they require unbounded materialization, design a user-visible, standards-compatible bounded-access mode or explicitly carry this as a release blocker; never claim a false full range or truncate a successful `GetText(-1)`. |

Two integration hooks require particular care even after the core fixes. First, `ITextProvider::GetSelection` and AppKit selected range must reflect the **global** anchor/active, while the native input island remains focusable for IME; verify one accessible editor and no duplicate speech in the real tree. Second, `TryScrollIntoView` must atomically move the controller viewport, publish a current-generation/current-version frame, and return failure if composition cannot be preserved. A stale range must map to an OS-appropriate failure on **every** provider method, not only Windows `TryGetText`; never show geometry from the old file after a successful-looking scroll. `GetText(-1)`'s exactness and whole-document `DocumentRange` are separate properties: the latter is already modeled, but reader interoperability is still an experiment.

## OS registration feasibility prototypes, 2026-09-29

**Windows.** `src/Mote.Native/Windows/Accessibility/WindowsUiaBridgePrototype.cs` defines source-generated IUnknown COM interfaces with the Windows SDK `IRawElementProviderSimple`, `ITextProvider` and `ITextRangeProvider` GUIDs and vtable order. `WindowsUiaBridgePrototype.HandleGetObject(hwnd,wParam,lParam)` obtains a generated COM pointer and calls the OS `UiaReturnRawElementProvider`, following [Microsoft's WM_GETOBJECT contract](https://learn.microsoft.com/en-us/windows/win32/api/uiautomationcoreapi/nf-uiautomationcoreapi-uiareturnrawelementprovider); `Close(hwnd)` notifies UIA from `WM_DESTROY`. The probe publishes one Document control element, source-backed document/selection/visible ranges as `SAFEARRAY(VT_UNKNOWN)`, exact bounded `BSTR` text, and a source viewport scroll callback. A Windows in-process test calls its **actual generated COM vtable** to get the document range, read a bounded offscreen prefix, reject an oversized unbounded request, and inspect the selected-range SAFEARRAY. A win-x64 Native AOT publish completed without warning (local output under `.cache/ax-uia-aot-probe`; no target-OS screen-reader test). Windows SDK `UIAutomationCore.h` at 10.0.26100.0 supplied GUID/order/enum values; [source-generated COM documentation](https://learn.microsoft.com/en-us/dotnet/standard/native-interop/comwrappers-source-generation) explains why ordinary runtime COM wrappers are unsuitable for Native AOT.

This Windows object is **not yet a conformant, enabled Text pattern**. `RangeFromPoint`, character/word/line movement, bounding rectangles, selection mutation, text search, attributes, and events are explicit `E_NOTIMPL` placeholders. The root provider now binds its HWND and calls [`UiaHostProviderFromHwnd`](https://learn.microsoft.com/en-us/windows/win32/api/uiautomationcoreapi/nf-uiautomationcoreapi-uiahostproviderfromhwnd), but focus/tree placement plus RichEdit suppression are untested. Registering it as a default Document element would mislead clients because [Microsoft's Document control type](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-supportdocumentcontroltype) requires a usable Text pattern. `HandleGetObject` and `Close` are not called by the current shell. Required hook: the canvas HWND's `WM_GETOBJECT` and `WM_DESTROY` handlers, plus one UI-thread controller `IAccessibleViewport` implementation. Validate COM reference counts, SAFEARRAY/BSTR ownership, `VARIANT` ABI, and text-pattern method behavior on both win-x64 and win-arm64 before enabling. The in-process vtable test is a valuable ABI probe, **not** an external UIA tree or Narrator pass.

**macOS.** `src/Mote.Native/Mac/Accessibility/MacAccessibilityElementPrototype.cs` dynamically subclasses `NSAccessibilityElement` through the existing Objective-C runtime bridge. It can attach one AX text-area child to a canvas view, hide the bounded input view from the AX tree while leaving native focus untouched, and restore the prior child list/accessibility flag on disposal. It provides source-backed `accessibilityNumberOfCharacters`, selected/visible UTF-16 ranges, `accessibilityStringForRange:`, `accessibilityLineForIndex:`, and `accessibilityRangeForLine:`. Apple's [`NSAccessibilityElement` guidance](https://developer.apple.com/documentation/appkit/nsaccessibilityelement-swift.class?language=o_6) supports a non-view element attached to the parent view's accessibility children; [`NSAccessibilityProtocol`](https://developer.apple.com/documentation/appkit/nsaccessibilityprotocol) defines the text selectors. The code compiles in the shared C# project on Windows, but **has not been executed or AOT-published on macOS**. Required hook: `Attach(canvasView,inputEditor)` after canvas creation and `Dispose()` before view destruction; the actual shell must preserve/restore any other accessibility children and test that hiding the input view does not impair VoiceOver editing or IME candidate tracking.

This Mac object now sets its [parent-space frame](https://developer.apple.com/documentation/appkit/nsaccessibilityelement-swift.class/accessibilityframeinparentspace) from canvas bounds and maps focused-element queries/requests to the real `NSTextView` first responder. It still lacks `accessibilityFrameForRange:`, point-to-range mapping, selected-range setter, text-value behavior for requests above 65,536 units, and notifications; those new frame/focus hooks have no on-screen acceptance result. In particular, it returns `nil` for oversized `accessibilityStringForRange:` rather than a false truncated string; VoiceOver may or may not recover by smaller range requests. The Objective-C `NSRange`/`NSInteger` and callback return ABI must be checked on **both** osx-x64 and osx-arm64; compilation on Windows does not validate this. Probe with Accessibility Inspector then VoiceOver on an interactive logged-in Mac, including offscreen marker navigation and active real IME composition. Do not treat a successful in-process selector call alone as a speech pass.

## Independent OS-bridge ABI and lifetime audit, 2026-09-29

This is a source review of the **opt-in, unconnected prototypes**, not a target-OS screen-reader pass. During review, the owner corrected the Mac Objective-C method encodings to include implicit `@:` and signed `NSInteger` (`q`), rejects callbacks for retained elements other than the active `self`, added parent-space geometry/focus hooks, and made the Windows HWND provider return the system host provider. Apple's [`class_addMethod`](https://developer.apple.com/documentation/objectivec/class_addmethod%28_%3A_%3A_%3A_%3A%29) requires those implicit arguments; [`UiaHostProviderFromHwnd`](https://learn.microsoft.com/en-us/windows/win32/api/uiautomationcoreapi/nf-uiautomationcoreapi-uiahostproviderfromhwnd) is specifically intended for the host-provider slot. The remaining distinctions are:

| Status | Source-backed observation | Discriminating acceptance |
| --- | --- | --- |
| **Windows ABI shape plausible, runtime registration unproven** | Source-generated COM interfaces list the SDK GUIDs and vtable order; `SAFEARRAY(VT_UNKNOWN)` insertion and local pointer release follow [`SafeArrayPutElement`'s AddRef ownership](https://learn.microsoft.com/en-us/windows/win32/api/oleauto/nf-oleauto-safearrayputelement). `GetProviderOptions=2` is server-side. A managed-runtime in-process vtable test exercises selected-range SAFEARRAY and BSTR, but the bridge is **not referenced by the shell**, so even a successful AOT publish need not contain or invoke it. | In published one-file win-x64 **and** win-arm64 binaries, opt-in hook canvas `WM_GETOBJECT`/`WM_DESTROY`, query the live HWND with an external UIA client, release returned BSTR/SAFEARRAY/interfaces, and inspect memory/ref-count and stale requests after close. Do not infer this from the managed unit test or file inventory. |
| **Windows closed-object source fix; OS behavior unproven** | `Close` now invalidates `AccessibleDocument` and clears its snapshot binding as well as UIA's HWND map; a retained provider/range should therefore fail future source reads rather than retain the closed rope. That source property has not been exercised through an external COM client. `GetPatternProvider` still advertises Text while many required TextRange methods and events return `E_NOTIMPL`/never fire. | Hold an old COM pointer across `WM_DESTROY`, assert `UIA_E_ELEMENTNOTAVAILABLE` and no closed 100 MiB snapshot retention, then inspect focus/document tree externally. Keep this provider opt-in until hit-testing, text units, geometry, mutations/events and reader behavior satisfy [Text/TextRange guidance](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-implementingtextandtextrange). |
| **Mac ABI must be executed per architecture** | `ObjC.Range` is two pointer-sized unsigned fields, and selectors return it by value through `[UnmanagedCallersOnly]`; `setAccessibilityFrameInParentSpace:` passes a 32-byte `NSRect` by value. The source signatures and class method encodings are plausible, but a Windows compile cannot establish x64 versus arm64 aggregate calling convention or the AOT callback's behavior. | Publish and invoke each selector on **osx-x64 and osx-arm64**, query [`method_getTypeEncoding`](https://developer.apple.com/documentation/objectivec/method_gettypeencoding%28_%3A%29), compare exact 0/CRLF/surrogate/offscreen `NSRange` results against the source snapshot, and exercise frame set/get after resize. Follow with Accessibility Inspector/VoiceOver, not merely direct selector calls. |
| **Mac attachment/focus lifecycle remains an OS gate** | Attach now copies the prior child array, removes the input editor, and adds the proxy while preserving other children; Dispose restores the prior array/input AX flag and invalidates/clears the source binding. The canvas/input pointers remain raw and unretained, so shell ordering must guarantee detach before view destruction. `Current(self)` prevents a retained stale AX element from reading a later document; the first-responder proxy and hidden input editor may still produce wrong tree focus or duplicate/missing speech. | On the AppKit main thread, attach with pre-existing non-input children, verify they remain reachable while attached, then detach **before view teardown** and compare the original child list/input AX flag. Hold an old AX element across detach/reopen and verify it cannot read a new document. Repeat with live focus, VoiceOver, and a real IME candidate; ensure callbacks never synchronize against a blocked UI thread. Apple's [view-backed element guidance](https://developer.apple.com/documentation/accessibility/integrating-accessibility-into-your-app) makes the tree/focus experiment material. |

**Integration decision:** retain these bridges as opt-in prototypes. The core's complete source range and bounded extraction policy are separate from OS contract completeness; neither an AOT build nor a direct vtable call establishes accessible editing. The smallest useful next product slice is an **OS-reachable, reversible registration** with stale-object invalidation and no document-copy mirror, followed by actual reader/IME acceptance on both architectures. The long-line `GetText(-1)`/`StringForRange:` tension remains the release gate described above.
