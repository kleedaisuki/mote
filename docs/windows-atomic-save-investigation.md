# Windows atomic Save: intermittent `ReplaceFileW` removal failure

## Decision and observed boundary (2026-09-30)

An ordinary **win-x64 Native AOT** `mote <file>` run has produced a real, user-visible Save failure while the editor remained responsive. This is a product reliability issue to investigate, **not** a measured slow Save or a proven general failure rate. The original target bytes remained intact and the editor remained dirty. We have **not** captured the thrown exception's `HResult`, a file-system event trace, or the process holding any conflicting handle; root cause remains unknown. Do not replace atomic Save with an unchecked in-place write or silently retry over a changed target.

The fixed executable was `mote.exe` SHA-256 `73cd0392852bd87ce43fa6085a9ba23e31178db55d1ceb247fd2be4515ef578b`, 6,175,232 bytes, Windows 10.0.26200; see [`benchmarks/NativeStartup/README.md`](../benchmarks/NativeStartup/README.md) for the exact 1 MiB ordinary startup protocol. The selected append-only raw row is `.cache/native-startup/ordinary-windows.jsonl` line 25, UTC `2026-09-30T10:17:47.3997613Z`, `ordinal=4`, `diagnostic_trace=true`. Four preceding fresh-process, unique-path rows using the **same executable hash** saved exactly; this fifth run reached a bound 21-character input island, acknowledged selection and `WM_CHAR`, and showed a dirty title, but did not complete the Save. An earlier selected unique-path batch passed 5/5 at 1 MiB and 3/3 at 100 MiB. The failing run retained the original 1,048,576-byte target, displayed a modal dialog containing `Save failed; the original file was retained. 无法删除要被替换的文件。`, and its main HWND answered the external responsiveness ping within 3 s. The benchmark's `>30 s` Save timeout was the modal blocking completion, **not evidence that `File.Replace` itself spent 30 s**. Foreground ownership at source binding belonged to another process, so none of this proves physical-key responsiveness.

The localized message is exactly the local Windows text of `Win32Exception(1175)`. The official [`ReplaceFileW` contract](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew) and [system error table](https://learn.microsoft.com/en-us/windows/win32/debug/system-error-codes--1000-1299-) call 1175 (`0x497`) `ERROR_UNABLE_TO_REMOVE_REPLACED`: the replaced file could not be deleted and the replaced/replacement files retain their original names. **This is a strong message-to-code inference, not a captured `IOException.HResult`.** The observed original target is consistent with the documented state. No evidence yet distinguishes an external scanner/indexer/sync process, a short-lived handle in mote, file-system filter behavior, access-control state, or another cause.

## Source-path analysis and ownership

`Document.SaveCoreAsync` in `src/Mote.Engine/Document.cs` captures the snapshot, expected file stamp and SHA-256, rejects an unexpected Save As overwrite, writes a unique temp in the target directory and flushes it to disk, then calls `CommitTempAsync`. The existing-target branch reopens the target for a SHA-256 plus stamp check immediately before `File.Replace(tempPath, path, null, ignoreMetadataErrors: false)`. The `VerifyOriginalContentAsync` `await using` read stream is disposed on return before `File.Replace`; the temp fingerprint read stream in `WriteTempAsync` is also disposed on return. `Document.OpenAsync` likewise scopes its read stream before return. Source inspection therefore found **no intentionally persistent engine handle** on the target or temp, though it cannot rule out a runtime, native UI, or external handle without tracing. Opening and verification use `FileShare.ReadWrite` (not Delete), so an overlapping read during replacement would matter; there is no observed overlap yet.

The engine serializes saves with `_saveGate`, so two simultaneous `SaveAsync` calls on the **same Document** should not race. The stamp/hash check is an important but non-atomic external-change guard; a different process can still change the path between final verification and replacement, as `src/Mote.Engine/README.md` already states. On failure, `SaveCoreAsync` executes `finally { if (File.Exists(tempPath)) File.Delete(tempPath); }`. For 1175 the Win32 contract says both names remain, so this cleanup normally deletes the staged new snapshot. The document remains dirty and the old target survives, but if the process later dies before a successful Save, the staged bytes are no longer a recovery artifact. A prospective fix should consider recovery semantics without making temp-file retention or overwriting into an unbounded leak/silent data-loss path.

Existing tests cover correct normal save, pre-cancellation preserving the original, Save As approval, and hash/stamp external conflict (`tests/Mote.Tests/EngineTests.cs`, `ReviewRegressionTests.cs`). The current `Held_target_reports_replace_phase_without_losing_original` test also covers a Windows no-Delete-sharing target handle, expecting `0x80070020`, phase `Replace`, unchanged bytes, dirty state, and temp cleanup. They do **not** cover Windows `ReplaceFileW` 1175 or OS-filter timing. The UI at `NativeEditorController.cs` catches the failure rather than falsely marking the document saved; its preservation wording is correct for the observed incident, but is not a guarantee for every possible replacement error (see the safety contract below).

## Disposable Windows probe: share/attribute controls

Run the tracked [`tests/SaveReplaceShareProbe.ps1`](../tests/SaveReplaceShareProbe.ps1) from the repository root with `pwsh -NoProfile -File tests/SaveReplaceShareProbe.ps1`. It creates unique synthetic target/replacement pairs only below root `.temp/save-replace-probe/`, optionally holds one `FileStream` with the table's share mode, calls `File.Replace`, and reports the inner managed exception/HResult and fixture bytes before closing the stream. It never reads a user document or recursively cleans a directory. The first exploratory run's raw output remains locally in ignored `.cache/windows-save-replace/probe-results.json`. On this Windows 10.0.26200 machine with .NET SDK 10.0.400 / PowerShell 7, one run observed:

| Case | Outcome | Target after failure |
| --- | --- | --- |
| No held stream | success | replacement bytes |
| Target open for read with `FileShare.ReadWrite` (no Delete) | `IOException`, `0x80070020` sharing violation | original bytes |
| Target open for read with `FileShare.ReadWrite | Delete` | success | replacement bytes |
| Temp open for read with `FileShare.Read` (no write/delete) | `IOException`, `0x80070020` sharing violation | original bytes |
| Target read-only attribute | `UnauthorizedAccessException`, `0x80070005` access denied | original bytes |

These controls show that **simple pre-existing** no-Delete handles or read-only attribute do not recreate the exact reported 1175 on this machine. They do **not** exonerate transient handles: `ReplaceFileW` is a multi-step operation, and a file-system filter or concurrent opener could interfere after an earlier step. Microsoft's API documentation says it requests `DELETE` on the replaced file, opens the replacement with broad rights and no sharing mode, and must delete/rename as part of replacement; `FileShare.Delete` specifically governs subsequent delete access ([`FileShare` contract](https://learn.microsoft.com/en-us/dotnet/api/system.io.fileshare)). The 1175 text identifies the failing **operation class**, not who prevented it. `ignoreMetadataErrors: true` would only relax metadata/ACL merge errors and is not a supported cure for a failed removal; changing it risks metadata loss without explaining this observation.

## Next discriminating experiment; no speculative retry

1. In a disposable, opt-in AOT diagnostic build, capture the **content-free** `IOException.HResult` and `GetType().FullName` at `File.Replace`, plus a phase ID (`stamp check`, `temp flush/hash`, `final target hash`, `replace`, `cleanup`). Record whether both paths exist, target/temp byte lengths, target `FileAttributes`, stamp, and a non-content file identifier immediately before/after replacement. Do not log file contents, actual user paths, or hashes to default telemetry. The diagnostic should not delay the hot save path in normal builds.
2. With the exact same executable and unique test paths, run controlled cases with a separate helper holding the target for each `FileShare` mode and closing it at precisely measured offsets. Correlate any 1175 with a Windows file-system trace such as Microsoft [Process Monitor](https://learn.microsoft.com/en-us/sysinternals/downloads/procmon) or ETW, with filtering and path redaction. First decide whether the error is a deterministic sharing contract, a post-open race, or machine-specific filter behavior. Reproduction under a clean hosted Windows runner versus a local machine with endpoint security would be discriminating; neither alone proves a universal root cause.
3. Only after phase/error evidence, evaluate a bounded recovery design. Any retry must re-verify stamp **and SHA-256 immediately before each attempt** and never reinterpret a conflict as permission to overwrite. Keep a same-directory staged file available under a bounded, discoverable recovery policy if final replacement failed; avoid claiming crash durability or ACL preservation the platform cannot guarantee. Test original-bytes preservation, dirty state, external same-size/restored-time edits, read-only target, no-Delete handles, cleanup failures, and Save As approval. A UI action to explicitly retry/recover is safer than indefinite automatic retries.

The strongest current conclusion is narrow: a real one-file ordinary path can fail at Windows replacement after successful editing, while correctly preserving the old file. The exact Win32 1175 cause and incidence are still open. The next useful evidence is the **actual managed HResult and file-system event sequence**, not another latency percentile or a broad retry loop.

## Opt-in content-free Save failure trace

The native Save catch now calls `MoteTelemetry.RecordSaveFailure` before showing
the unchanged error UI. With `MOTE_TRACE=1` (and no tracing otherwise), a
filesystem failure writes one `save.failure.<phase>` record with the original
signed numeric `hresult`. The phase is mapped through a fixed allowlist from
the engine's `Mote.Engine.SavePhase` exception annotation; arbitrary phase
strings become `save.failure.unknown`. The trace does not serialize exception
messages, paths, file contents, hashes, or arbitrary `Exception.Data` values.
It adds no synchronous trace I/O, retry, or Save state transition. A healthy sink is required;
bounded queue loss can still drop this record, so absence is not evidence of
Save success. An opt-in trace can capture a future failure's managed HResult and
phase; it does **not** retroactively establish the earlier 1175 inference.

## Evidence refinement and ranked hypotheses (2026-10-01)

This follow-up inspected source at HEAD `7bc42a6a0e995a15c3dfe81cf7a198951dd52de8`, the existing raw row and retained synthetic artifacts; it did not rerun the ordinary launch or share-control experiments. No production or workflow change is proposed as a root-cause fix.

### What the retained evidence can actually answer

- The original failure batch remains in `.temp/native-startup/22cba43cb823445e9fb696425a9fadc3/`. Its `ordinary-1-0.md` through `ordinary-1-3.md` each have 1,048,577 bytes and SHA-256 `2d12a1cbc6df198198d7b6de8c38a3e3f3bd8ffaf3bb73025effa9026c1d75f0`; `ordinary-1-4.md` has 1,048,576 bytes and SHA-256 `69f4396b7a4d42b022627414f8711cc4b62292f35fbd415b34daa201fac08aea`. These are synthetic fixture fingerprints, not permission to collect user hashes.
- All five retained `home/traces/mote-trace-*-000001.jsonl` files in that batch are **zero bytes**. There is no hidden historical HResult to extract from them. The old row lacks `child_process_id`, so trace-to-PID pairing cannot be reconstructed from that schema either.
- The current ordinary driver kills its own process in `finally`, even on success, and normally removes its isolated scratch/home directory. `-KeepFailureArtifacts` retains only failing-batch artifacts, not successful traces. The current sink uses a 64 KiB buffered `FileStream`, flushes on rotation/orderly shutdown, and does not flush each record (`JsonlTraceSink.WriteLoopAsync`). `Program` drains tracing only on normal shutdown. Forced termination can therefore lose a small session's entire buffered trace; waiting for a live trace file to become nonempty is not a reliable substitute for orderly shutdown. This is source-based explanation consistent with the empty files, not proof of the precise historical sink state.
- The hosted Windows structured-text pilot in `.github/workflows/ci.yml` invokes `-ReadinessOnly`, disables diagnostic tracing, and explicitly requires null edit/Save fields and unchanged fixture hashes. It never calls Save. Its passing status, or a green overall build, cannot close this incident. The existing external-fixture adapter is intentionally readiness-only and cannot be repurposed into a Save diagnostic by merely adding tracing.

The upstream [.NET 10 Windows implementation](https://raw.githubusercontent.com/dotnet/runtime/v10.0.0/src/libraries/System.Private.CoreLib/src/System/IO/FileSystem.Windows.cs) forwards `File.Replace` to the Win32 replacement API and translates the captured last P/Invoke error; there is no managed retry in that method. This inspected tag is a mechanism reference, not a claim that the old AOT binary used precisely that runtime servicing revision. Capture the actual SDK/runtime pack for a new build. If Win32 1175 is captured through the usual HRESULT translation, its numeric value is `0x80070497` / `-2147023721`; do not infer Win32 codes from arbitrary HRESULT low bits without checking the facility.

### Ranking: investigation priority, not numerical likelihood

| Priority | Hypothesis | Evidence for / against | Discriminating observation |
| --- | --- | --- | --- |
| 1 | File-system/filter-level removal interference or a target object state that permits initial access but prevents removal | Fits the inferred removal-stage 1175 and intermittence; no filter, stack, object-state or PID evidence is captured. Scanner/indexer/sync labels are possibilities, not identified culprits. | Actual `save.failure.replace` code plus file-system operation/result sequence and, when available, stack/filter attribution. Compare the same AOT hash on local and hosted Windows without disabling protection. |
| 2 | Ordinary application or observer handle overlap, including an unexpected mote handle lifetime | Windows handles without Delete sharing cause real Save failure; existing controls and engine test report **32**, not 1175. Open/verification streams are scoped and disposed before replacement; the observer polls metadata and hashes only after completed Save. No intentional persistent target stream is found. | Trace successful/failed CreateFile and CloseFile operations for target/temp, PID and share/access fields; establish an actual overlapping handle, not just a process with a suggestive name. |
| 3 | ACL, attributes, parent-directory permissions, or path/object changes near replacement | Replace needs more than permission to create a temp; metadata merging and delete permissions matter. A static read-only fixture produces **5**, and same synthetic directory succeeds in preceding runs. Dynamic changes and special object states remain untested. | Record fixture-only attributes, parent/target ACL and volume/reparse classification before/after; correlate changes with operation failures. Prefer this only if codes/results point here. |
| 4 | Native AOT/runtime-specific handle disposal or error propagation issue | Only the AOT ordinary incident is observed, but no controlled JIT/AOT comparison or native-error discrepancy exists. Shared upstream implementation provides no positive evidence of an AOT bug. | If a fresh incident is captured, run an engine-only reproducer with identical fixture protocol/runtime version in JIT and AOT; add direct Win32 control only if needed. Do not lead with a broad runtime matrix. |

There is an important constraint on the tempting "a reader opened just after replacement started" story: [CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew) checks sharing compatibility in both directions, while [ReplaceFileW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew) obtains Delete access on the replaced object. Once that handle exists, an ordinary new reader that omits Delete sharing should itself fail to open against it. A pre-existing incompatible reader should prevent the replacement's initial open. Therefore a transient-reader offset sweep is useful for locating **32** and handle timing, but is not by itself a supported mechanism for **1175**. A filter, special object state, path transition, or undocumented internal lifetime would require its own evidence. Public API docs do not expose the exact internal operation sequence.

### Narrow hosted diagnostic: proposed execution contract

The next deliverable should be a separate bounded Save-diagnostic driver, not a latency benchmark change or a speculative product retry. It can reuse the existing Win32 source/selection/edit command protocol, but must repair the evidence lifecycle described above before relying on traces. This section is a proposal; no hosted diagnostic has been run as part of this follow-up.

1. **One ordinary scope.** Fresh checkout, one pinned win-x64 Native AOT executable, one 1 MiB generated Markdown fixture per child, isolated repo-local `MOTE_HOME`, `MOTE_TRACE=1`. Use at most five fresh children, stop on the first Save failure, cap each child at 45 seconds and the whole batch at five minutes. Do not mix in grid, structured-file, physical-key, readiness-only or latency assertions. A timeout before verified editing is an infrastructure/capability failure, not a replacement result.
2. **Pin provenance.** Manifest captures HEAD, executable SHA/size, OS build, runner image version, SDK and runtime-pack version, local filesystem type, a random run ID, PID/start time, fixture size and expected synthetic digest. All generated files live below `.temp/windows-save-diagnostic/<run-id>/`; finalized artifacts live below `.cache/windows-save-diagnostic/<run-id>/`. Reject reparse ancestors and unexpected ownership. Do not change Defender, indexing or sync configuration; a hosted runner is a comparison environment, not assumed scanner-free.
3. **Observe without creating the interference.** Before Save, finish and close all fixture digest/identity reads. Between Save post and its outcome, poll only bounded HWND/title and non-opening metadata; no target/temp content reads or held file-ID handle. On a completed Save or a failure dialog, stop mutation and then obtain exact synthetic-byte outcome. Record target existence, length, expected-original match, expected-new match, dirty title, modal class, responsiveness, and phase/HResult if available. Missing target or neither digest match is a separate high-severity state, never reported as "original retained".
4. **Flush and keep both controls and failures.** Dismiss only the failure modal owned by the recorded child PID, then close that child normally. A dirty-close prompt may discard only this explicitly owned synthetic document; it must not initiate a second Save. Allow bounded orderly exit/drain and require a parsable terminal `mote.session` record to label trace capture complete. Copy the fixture manifest, all successful and failing traces, row, and exit outcome to the run artifact **before** cleanup. If normal exit cannot be completed, record `trace_capture=incomplete-forced-exit`, copy what exists, then kill only the owned child. Zero records or no failure event cannot be scored as a successful Save.
5. **Positive tracing control before interpreting absence.** In a separately identified synthetic control, a helper holds target read access with `ReadWrite` sharing and no Delete, acknowledges "held" before Save, and stays held through the observed failure. Expect target-original/dirty and `save.failure.replace` with `0x80070020`; release before orderly close. This is an end-to-end trace/safety control, **not** a recreation of the old 1175. The already completed basic share probe need not be rerun merely to rediscover this contract.
6. **Filesystem capture is the conditional next layer.** If ordinary failure recurs with actual replacement code, capture a bounded Microsoft [Process Monitor](https://learn.microsoft.com/en-us/sysinternals/downloads/procmon) session (or reviewed ETW collector) including all PIDs for the unique synthetic directory, not only mote: otherwise the contender is filtered out. Start before launch; stop/export on failure; preserve operation, result, access/share mode, PID/thread and relative target/temp role, plus stack when available. Keep raw system traces private because paths, process command lines and stacks can reveal host information. Export a sanitized summary; hash/version-pin any downloaded collector and keep its files inside the repo cache. If the runner cannot load the collector, report missing capability; do not substitute a causal claim from the managed HResult alone.

First useful decision: does a new ordinary failure emit **Replace/1175**, **Replace/32**, another phase/code, or no complete trace? All-success results are only a bounded non-reproduction; report `0/N` for that specific executable/environment, not a reliability rate. If it is 1175 again, the next concrete discriminating test is the same exact-hash ordinary protocol on a fresh hosted Windows runner and the original local machine with filtered file-system capture. If it is 32, identify the actual incompatible handle before changing sharing modes.

### Safety contract for a later fix or diagnostic

- **Do not universalize the original-preserved message.** Win32 documents 1175 retaining both original names; 1176 with no backup can leave the replaced target absent and the replacement under its original temp name; 1177 can leave the old object under a different name. The present `finally` may then delete the only staged replacement. This is a documented possible state, **not an observed mote data-loss incident**. A future fix must classify commit outcomes and recovery artifacts before cleanup and user-facing claims.
- **Preserve the primary failure.** Current cleanup exceptions replace a pending commit exception in `finally`; `save.failure.cleanup` can hide an earlier replacement error. A diagnostic observing Cleanup must not conclude replacement succeeded or never failed. A later recovery design should retain primary plus secondary bounded error codes without serializing arbitrary exception details.
- **Separate commit from post-commit bookkeeping.** `SavedStamp` fails after replacement; dirty state alone does not mean the disk still has old bytes. Verify the actual synthetic disk outcome rather than trusting modal wording or dirty state. Do not automatically repeat a commit whose outcome is unknown.
- **Keep external-change protection.** No in-place write fallback, delete-then-move, blanket `ignoreMetadataErrors`, or generic retry loop. Any permitted retry must recheck stamp and SHA immediately before that attempt; the existing check-to-replace race remains explicitly non-atomic. User-approved Save As overwrite remains an external contract.
- **Bound recovery, do not erase it blindly.** On uncertain/failed replacement, avoid deleting a potentially unique new snapshot until its role is established. Any future retention policy needs explicit ownership, quotas/expiry, discoverability, privacy and recovery UX; changing cleanup alone is not an adequate fix.
- **Do not equate atomic visibility with crash durability.** The engine flushes staged content, but the Win32 API's write-through replacement flag is unsupported. Research on application crash consistency shows why update protocols must be tested against their real platform's persistence properties ([Pillai et al., OSDI 2014](https://www.usenix.org/conference/osdi14/technical-sessions/presentation/pillai)). That study concerns Linux filesystems and does not establish this Windows cause. Its transferable lesson is to keep return-code failure, concurrent visibility, post-commit bookkeeping and power-loss guarantees separate. Crash testing is a later scope, not a prerequisite for this narrowly discriminating live-error capture.
