# Windows atomic Save: intermittent `ReplaceFileW` removal failure

## Decision and observed boundary (2026-09-30)

An ordinary **win-x64 Native AOT** `mote <file>` run has produced a real, user-visible Save failure while the editor remained responsive. This is a product reliability issue to investigate, **not** a measured slow Save or a proven general failure rate. The original target bytes remained intact and the editor remained dirty. We have **not** captured the thrown exception's `HResult`, a file-system event trace, or the process holding any conflicting handle; root cause remains unknown. Do not replace atomic Save with an unchecked in-place write or silently retry over a changed target.

The fixed executable was `mote.exe` SHA-256 `73cd0392852bd87ce43fa6085a9ba23e31178db55d1ceb247fd2be4515ef578b`, 6,175,232 bytes, Windows 10.0.26200; see [`benchmarks/NativeStartup/README.md`](../benchmarks/NativeStartup/README.md) for the exact 1 MiB ordinary startup protocol. The selected append-only raw row is `.cache/native-startup/ordinary-windows.jsonl` line 25, UTC `2026-09-30T10:17:47.3997613Z`, `ordinal=4`, `diagnostic_trace=true`. Four preceding fresh-process, unique-path rows using the **same executable hash** saved exactly; this fifth run reached a bound 21-character input island, acknowledged selection and `WM_CHAR`, and showed a dirty title, but did not complete the Save. An earlier selected unique-path batch passed 5/5 at 1 MiB and 3/3 at 100 MiB. The failing run retained the original 1,048,576-byte target, displayed a modal dialog containing `Save failed; the original file was retained. 无法删除要被替换的文件。`, and its main HWND answered the external responsiveness ping within 3 s. The benchmark's `>30 s` Save timeout was the modal blocking completion, **not evidence that `File.Replace` itself spent 30 s**. Foreground ownership at source binding belonged to another process, so none of this proves physical-key responsiveness.

The localized message is exactly the local Windows text of `Win32Exception(1175)`. The official [`ReplaceFileW` contract](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew) and [system error table](https://learn.microsoft.com/en-us/windows/win32/debug/system-error-codes--1000-1299-) call 1175 (`0x497`) `ERROR_UNABLE_TO_REMOVE_REPLACED`: the replaced file could not be deleted and the replaced/replacement files retain their original names. **This is a strong message-to-code inference, not a captured `IOException.HResult`.** The observed original target is consistent with the documented state. No evidence yet distinguishes an external scanner/indexer/sync process, a short-lived handle in mote, file-system filter behavior, access-control state, or another cause.

## Source-path analysis and ownership

`Document.SaveCoreAsync` in `src/Mote.Engine/Document.cs` captures the snapshot, expected file stamp and SHA-256, rejects an unexpected Save As overwrite, writes a unique temp in the target directory and flushes it to disk, then calls `CommitTempAsync`. The existing-target branch reopens the target for a SHA-256 plus stamp check immediately before `File.Replace(tempPath, path, null, ignoreMetadataErrors: false)`. The `VerifyOriginalContentAsync` `await using` read stream is disposed on return before `File.Replace`; the temp fingerprint read stream in `WriteTempAsync` is also disposed on return. `Document.OpenAsync` likewise scopes its read stream before return. Source inspection therefore found **no intentionally persistent engine handle** on the target or temp, though it cannot rule out a runtime, native UI, or external handle without tracing. Opening and verification use `FileShare.ReadWrite` (not Delete), so an overlapping read during replacement would matter; there is no observed overlap yet.

The engine serializes saves with `_saveGate`, so two simultaneous `SaveAsync` calls on the **same Document** should not race. The stamp/hash check is an important but non-atomic external-change guard; a different process can still change the path between final verification and replacement, as `src/Mote.Engine/README.md` already states. On failure, `SaveCoreAsync` executes `finally { if (File.Exists(tempPath)) File.Delete(tempPath); }`. For 1175 the Win32 contract says both names remain, so this cleanup normally deletes the staged new snapshot. The document remains dirty and the old target survives, but if the process later dies before a successful Save, the staged bytes are no longer a recovery artifact. A prospective fix should consider recovery semantics without making temp-file retention or overwriting into an unbounded leak/silent data-loss path.

Existing tests cover correct normal save, pre-cancellation preserving the original, Save As approval, and hash/stamp external conflict (`tests/Mote.Tests/EngineTests.cs`, `ReviewRegressionTests.cs`). They do **not** cover Windows `ReplaceFileW` 1175, third-party handle interference, or OS-filter timing. The UI at `NativeEditorController.cs` catches the failure and reports preservation rather than falsely marking the document saved.

## Disposable Windows probe: share/attribute controls

Run the tracked [`tests/SaveReplaceShareProbe.ps1`](../tests/SaveReplaceShareProbe.ps1) from the repository root with `pwsh -NoProfile -File tests/SaveReplaceShareProbe.ps1`. It creates unique synthetic target/replacement pairs only below root `.temp/save-replace-probe/`, optionally holds one `FileStream` with the table's share mode, calls `File.Replace`, and reports the inner managed exception/HResult and fixture bytes before closing the stream. It never reads a user document or recursively cleans a directory. The first exploratory run's raw output remains locally in ignored `.cache/windows-save-replace/probe-results.json`. On this Windows 10.0.26200 machine with .NET SDK 10.0.400 / PowerShell 7, one run observed:

| Case | Outcome | Target after failure |
| --- | --- | --- |
| No held stream | success | replacement bytes |
| Target open for read with `FileShare.ReadWrite` (no Delete) | `IOException`, `0x80070020` sharing violation | original bytes |
| Target open for read with `FileShare.ReadWrite | Delete` | success | replacement bytes |
| Temp open for read with `FileShare.Read` (no write/delete) | `IOException`, `0x80070020` sharing violation | original bytes |
| Target read-only attribute | `UnauthorizedAccessException`, `0x80070005` access denied | original bytes |

These controls show that **simple pre-existing** no-Delete handles or read-only attribute do not recreate the exact reported 1175 on this machine. They do **not** exonerate transient handles: `ReplaceFileW` is a multi-step operation, and a file-system filter or concurrent opener could interfere after an earlier step. Microsoft's API documentation says it requests `DELETE` on the replaced file, opens the replacement with broad rights and no sharing mode, and must delete/rename as part of replacement; `FileShare.Delete` specifically governs subsequent delete access ([`FileShare` contract](https://learn.microsoft.com/en-us/dotnet/api/system.io.fileshare)). The 1175 text identifies the failing **operation class**, not who prevented it. `ignoreMetadataErrors: true` would only relax metadata/ACL merge errors and is not a supported cure for a failed removal; changing it risks metadata loss without explaining this observation.

## Next discriminating experiment; no speculative retry

1. In a disposable, opt-in AOT diagnostic build, capture the **content-free** `IOException.HResult` and `GetType().FullName` at `File.Replace`, plus a phase ID (`stamp check`, `temp flush/hash`, `final target hash`, `replace`, `cleanup`). Record whether both paths exist, target/temp byte lengths, target `FileAttributes`, stamp, and a non-content file identifier immediately before/after replacement. Do not log file contents, actual user paths, or hashes to default telemetry. The diagnostic should not delay the hot save path in normal builds.
2. With the exact same executable and unique test paths, run controlled cases with a separate helper holding the target for each `FileShare` mode and closing it at precisely measured offsets. Correlate any 1175 with a Windows file-system trace such as Microsoft [Process Monitor](https://learn.microsoft.com/en-us/sysinternals/downloads/procmon) or ETW, with filtering and path redaction. First decide whether the error is a deterministic sharing contract, a post-open race, or machine-specific filter behavior. Reproduction under a clean hosted Windows runner versus a local machine with endpoint security would be discriminating; neither alone proves a universal root cause.
3. Only after phase/error evidence, evaluate a bounded recovery design. Any retry must re-verify stamp **and SHA-256 immediately before each attempt** and never reinterpret a conflict as permission to overwrite. Keep a same-directory staged file available under a bounded, discoverable recovery policy if final replacement failed; avoid claiming crash durability or ACL preservation the platform cannot guarantee. Test original-bytes preservation, dirty state, external same-size/restored-time edits, read-only target, no-Delete handles, cleanup failures, and Save As approval. A UI action to explicitly retry/recover is safer than indefinite automatic retries.

The strongest current conclusion is narrow: a real one-file ordinary path can fail at Windows replacement after successful editing, while correctly preserving the old file. The exact Win32 1175 cause and incidence are still open. The next useful evidence is the **actual managed HResult and file-system event sequence**, not another latency percentile or a broad retry loop.

## Opt-in content-free Save failure trace

The native Save catch now calls `MoteTelemetry.RecordSaveFailure` before showing
the unchanged error UI. With `MOTE_TRACE=1` (and no tracing otherwise), a
filesystem failure writes one `save.failure.<phase>` record with the original
signed numeric `hresult`. The phase is mapped through a fixed allowlist from
the engine's `Mote.Engine.SavePhase` exception annotation; arbitrary phase
strings become `save.failure.unknown`. The trace does not serialize exception
messages, paths, file contents, hashes, or arbitrary `Exception.Data` values.
It adds no synchronous trace I/O, retry, or Save state transition. A healthy sink is required;
bounded queue loss can still drop this record, so absence is not evidence of
Save success. An opt-in trace can capture a future failure's managed HResult and
phase; it does **not** retroactively establish the earlier 1175 inference.
