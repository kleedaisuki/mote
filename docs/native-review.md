# Native shell review (2026-09-29)

Scope: `src/Mote.Native/**` controller, text projection, Windows RichEdit adapter, macOS AppKit adapter, and their engine save interaction. This is an independent source review, not certification of interactive IME, screen-reader, or packaged macOS distribution behavior. Historical defect locations below describe the pre-fix implementation; use current symbols rather than the old line numbers when navigating the code.

## Defects found during review and current disposition

### P2 — Untitled Save could not replace an existing selected target — **fixed and regression-tested**

**Historical defect:** In `src/Mote.Native/NativeEditorController.cs`, `StartSave`, the Save command opened a file picker for an untitled document, but the existing-target branch was gated by `saveAs`. Pressing **Save** on an untitled document and selecting an existing target therefore called `Document.SaveAsync(path)` rather than `SaveOverAsync`; Engine correctly rejected that call with “explicit overwrite approval required.” The document remained safe but the ordinary Save workflow failed.

**Current fix and evidence:** `StartSave` now tracks `pickerWasUsed` and routes any picker-selected existing *different* target through `FileOverwriteToken.CaptureAsync`, `ConfirmOverwriteAsync`, and `SaveOverAsync`, regardless of whether the user initiated Save or Save As. The same-path flow and external-change check remain. Validation added a fake-shell regression covering denial (target preserved, document still dirty) and later approval (save succeeds); the focused native/navigation/CSV suite passed **20/20**, and the frozen-tree Windows Release suite passed **171/171** ([validation record](../tests/VALIDATION.md)).

### P0 — Mixed-newline edit could silently delete a logical line break — **corrected in current working tree**

**Historical defect:** In `src/Mote.Native/NativeTextProjection.cs`, `Difference`, the source/display mapping handled each isolated line ending, but the resulting `TextChange` was not closed under re-projection at the *seams* between retained source and replacement text.

**Exact repro:** Source `"\ra\n"` projects to RichEdit display `"\r\na\r\n"`. Delete only the `a` in the native control, yielding `"\r\n\r\n"` (two logical line breaks). `Difference` yields a change whose application produces source `"\r\n"`; projecting that source yields only `"\r\n"` (one logical line break). The adjacent original CR and LF merge into one CRLF after deletion. Thus the editor immediately hides one newline and Save persists data different from what the user just edited. This is not an exotic invalid CRLF cursor operation; deletion of `a` uses ordinary boundaries 2–3 in the displayed text.

**Evidence:** `.temp/native_projection_exhaustive.py` enumerated valid CRLF-boundary edits for source strings up to length four and found this case. `NativeControllerTests` now includes the exact seam regression. After the fix, **5,000 seeded random edits** and exhaustive short combinations of CR, LF, CRLF, ordinary characters and surrogate pairs passed the source/display roundtrip invariant ([validation record](../tests/VALIDATION.md)). Interactive RichEdit behavior remains unverified.

**Design invariant:** The projected source after applying any accepted native edit must equal the edited native display; otherwise the edit must not silently commit. The current fix implements this contract, and its common-path validation is now a streaming comparator rather than another full-page allocation. Its edit-to-paint latency still needs measurement on target hardware.

### P1 — Windows semantic colors and selection used the wrong newline coordinate space — **code fix present; interactive validation pending**

**Historical defect:** `src/Mote.Native/Windows/WindowsEditorShell.cs` requests `EM_GETTEXTEX` with `GT_USECRLF`, so the managed display has two UTF-16 units per line break. RichEdit 2+ stores paragraph breaks as one CR internally, and `EM_EXSETSEL` addresses its internal positions. The earlier shell sent managed display offsets directly to `EM_EXSETSEL` via `SetSelection`; `SetDocument`, semantic styling and preview styling were all affected.

**Trigger/impact:** For `"a\r\nb"`, a token span at display offset 3 (the `b`) is selected at internal position 3 rather than internal position 2. Tokens after newlines are colored at the wrong place or not at all. When `SetDocument` must replace native text, restoring the old internal caret against the new display length also becomes unreliable. Preview styling has the same offset drift. Microsoft documents that `GT_USECRLF` translates each CR to CR/LF, whereas `GT_RAWTEXT` preserves position alignment with text in memory; [GETTEXTEX reference](https://learn.microsoft.com/en-us/windows/win32/api/richedit/ns-richedit-gettextex). Microsoft also documents RichEdit 2+ single-CR paragraph markers; [About Rich Edit Controls](https://learn.microsoft.com/en-us/windows/win32/controls/about-rich-edit-controls).

**Current fix:** The native owner added `Windows/RichEditOffsetMap.cs`; `GetSelection`/`SetSelection` convert between native single-CR and CRLF-display positions, and preview text/spans receive a corresponding projection. `tests/Mote.Tests/NativeReviewTests.cs` checks multiline token offsets, all native caret positions across representative strings, and preview span composition (filtered run **7/7**). Windows semantic styling now imports one escaped RTF page after input-idle coalescing, rather than issuing a selection/format call for every token. An isolated real-control 128 KiB/4,096-span probe measured **16.7 ms** ASCII multiline, **50.0 ms** one long line and **57.6 ms** mixed Unicode for RTF import including selection/scroll restoration ([performance record](native-richtext-performance.md)); the current production page is smaller, and these are not product p95 or IME/accessibility validation.

## Material release gaps (not newly introduced defects)

- `NativeEditorController.ScheduleAnalysis` explicitly disables global diagnostics and structure preview for JSON/TOML/YAML over 2 Mi UTF-16 units; `Format` rejects all formats above that threshold. Markdown/CSV/plain text receive only viewport-relative analysis on large files. This contradicts the stated complete semantic-analysis ambition; it is an acknowledged functional limit, not an accidental stale-result bug. The public release promise needs either a bounded/incremental semantic design or a clearly accepted limitation.
- The large-file UI uses a **64 Ki UTF-16 page with 8 Ki edit slack** and manual `PreviousPage`/`NextPage` navigation rather than continuous scroll, whole-document selection or offscreen accessible navigation. The status acknowledges whole-document selection is unavailable. This is a product/accessibility gate, not necessarily a quick local patch; `docs/single-binary-feasibility.md` already records the virtualized-control plan. Focused page-end typing/paste regressions passed after the page/slack change ([validation record](../tests/VALIDATION.md)).
- macOS `NSTextView` and Windows RichEdit are reasonable system-native IME/accessibility starting points, but no source-level inspection proves real CJK composition or screen-reader behavior. Avoid claiming these are validated until interactive target-OS tests pass. In particular, the macOS callback currently forwards every `textDidChange:` to the engine; verify Save, undo, format and page replacement during marked-text composition.

## Scope and limits

The document save path captures an immutable snapshot under a gate and marks edits made during save as modified; the reviewed controller also rejects document replacement while `_saving`, so I found no demonstrated save-vs-open use-after-dispose in the current flow. The controller's analysis result has serial, document-identity and snapshot-version checks, so I found no demonstrated stale-analysis publication path. Telemetry record types are numeric/enumerated and do not expose a document path/content field; no direct telemetry privacy defect was identified here. These are source observations, not exhaustive concurrency or privacy verification.
