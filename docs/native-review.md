# Native shell review (2026-09-29)

Scope: `src/Mote.Native/**` controller, text projection, Windows RichEdit adapter, macOS AppKit adapter, and their engine save interaction. This is an independent source review, not certification of interactive IME, screen-reader, or packaged macOS distribution behavior. Historical defect locations below describe the pre-fix implementation; use current symbols rather than the old line numbers when navigating the code.

## Defects found during review and current disposition

### P1 conditional — `NSApplication.stop:` may not exit a non-event-triggered close — **wake-event fix present; hosted macOS gate**

**Pre-fix risk:** Changing `WindowWillClose` from `terminate:` to `stop:` lets `MacEditorShell.Run` return to managed probe assertions and telemetry shutdown. Ordinary Close/Custom Quit from a window/menu `NSEvent` pass through `WindowShouldClose` (IME settlement, saving/dirty veto) and should stop after the event. But GUI smoke and `MacNativeWorkflowProbe.Workflow.Tick` initiate `shell.Close()` from a posted main-thread selector, not necessarily a current `NSEvent`. [Apple's `stop:` contract](https://developer.apple.com/documentation/appkit/nsapplication/stop%28_%3A%29) explicitly says a timer/run-loop observer call will not stop the run loop because no event is posted. The initial `stop:`-only patch therefore risked hanging those probes. Separately, native Dock/OS Quit originally reached `applicationShouldTerminate:` and could take AppKit's `terminate:` path, which Apple says does not return to cleanup code in `main`; that bypassed managed post-run telemetry ([Apple termination contract](https://developer.apple.com/documentation/appkit/nsapplication/terminate%28_%3A%29)).

**Current fix and gate:** The macOS shell now pairs `stop:` with a posted `NSApplicationDefined` event (`NSEvent.otherEventWithType:...`, `postEvent:atStart:`) to wake a run loop whose close originated from a selector rather than an input event. Custom Quit still goes through `performClose:` and the dirty/IME veto. External Dock/OS Quit now consults the same closing contract, closes the window, and returns `NSTerminateCancel` so AppKit does not call `exit` before managed cleanup. A source review checked the Objective-C ABI signature (pointer-sized event type/flags/`NSInteger`, two-double `NSPoint`, `double` timestamp, `short` subtype, BOOL for `atStart:`) against [Apple's `otherEventWithType:` contract](https://developer.apple.com/documentation/appkit/nsevent/otherevent%28with%3Alocation%3Amodifierflags%3Atimestamp%3Awindownumber%3Acontext%3Asubtype%3Adata1%3Adata2%3A%29). No source-level blocker was found, but only `--smoke-gui` and the end-to-end Mac workflow under timeout on **both** architectures can establish that the actual AOT ABI/runloop path exits correctly.

### P0 — Windows Cut could delete text after clipboard failure — **code fix and controller regression present**

**Historical trigger and path:** `src/Mote.Native/Windows/WindowsEditorShell.cs`, `SetClipboardText`, reported `GlobalAlloc`, `GlobalLock`, `OpenClipboard`, `EmptyClipboard`, or `SetClipboardData` failure via `ShowError` and returned normally. `src/Mote.Native/NativeEditorController.cs`, `CopyOrCut`, treated normal return as clipboard success and immediately applied `new TextChange(start, length, "")` for Cut. Holding the clipboard open elsewhere made `OpenClipboard` fail: the user saw an error, yet Ctrl+X still deleted text without copying it.

**Current fix and limit:** The Windows adapter now throws on all observed allocation, lock, open, empty, set and close failures; the controller's existing catch leaves the document unchanged. A fake-shell regression injects clipboard rejection for Copy and Cut and checks unchanged document/disk; the focused controller/incremental suite passed **62/62** ([validation record](../tests/VALIDATION.md)). This tests the controller contract, not a real busy-clipboard failure in the Win32 adapter. macOS `SetClipboardText` already throws when `setString:forType:` fails.

### P1 — Older asynchronous Copy could overwrite the clipboard after a newer Cut — **fixed and regression-tested**

**Historical trigger and path:** `NativeEditorController.CopyOrCut` started each selection materialization with independent `Task.Run` and posted the completion to the UI thread without a clipboard-operation identity. Copy a very large selection A, then select a small range B and Cut it while A is still being materialized: the Cut callback could place B on the clipboard and remove it from the document, then the older Copy callback could overwrite the clipboard with A.

**Current fix and evidence:** The controller now increments `_clipboardSerial` for each Copy/Cut and on document replacement, discarding any superseded completion before clipboard transfer. It keeps the document-version/selection check for Cut. A controlled fake-shell test delivers Copy(A) and Cut(B) completions in reverse order and verifies B remains on the clipboard and only B is removed; the focused suite passed **62/62** ([validation record](../tests/VALIDATION.md)).

### P2 — A slow Find could overwrite a newer user selection — **fixed and regression-tested**

**Historical trigger and path:** `NativeEditorController.StartFind` captured `startAnchor/startActive` but its posted completion checked only find serial, document identity and snapshot version. `SelectionChanged` did not cancel or invalidate an in-flight find. Searching a large document while the user clicked elsewhere could publish the old search result after the newer caret action and move the viewport unexpectedly.

**Current fix and evidence:** Explicit selection changes and page/line navigation call `InvalidateFind`, which cancels the token, increments the serial and clears the stale search status. A fake-shell test releases a delayed search after a newer user selection and verifies the caret remains there; included in the **62/62** focused suite ([validation record](../tests/VALIDATION.md)).

### P1 conditional — macOS marked text could be applied to the wrong document after New/Open — **code guard present; interactive IME gate**

**Historical conditional path:** `MacEditorShell.TextDidChange` defers `TextChanged` while `NSTextView.hasMarkedText` is true, so provisional CJK input lives only in the native view. Without a guard, New or asynchronous Open completion could replace the controller document while `SetDocument` deferred replacing that old native view. On composition end, `CommitComposition` could then raise `TextChanged` with **old view text** against the **new document's projection**, dirtying or corrupting the newly opened file. Close could miss a dirty prompt, and Save could capture the pre-composition snapshot. This path depends on AppKit event ordering and was not reproduced on a macOS IME.

**Current guard and remaining gate:** AppKit command handlers now call `CommitMarkedTextBeforeCommand`, which asks the text view to `unmarkText` and commits before New, Save, page/selection commands, close or Quit; failure vetoes the command. The shared controller also calls `INativeEditorShell.CommitPendingText` at asynchronous **Open, Format, Cut and Find completions** before changing the engine or projected selection, then rechecks document identity/version so a newly committed edit invalidates the stale result. This covers a fresh composition started while background work runs. Successful Save As updates file-policy identity independently of composition settlement, so a failed unmark cannot leave a `.txt` file renamed to `.json` under the old format policy. Apple documents [`NSTextInputClient.unmarkText`](https://developer.apple.com/documentation/appkit/nstextinputclient/unmarktext%28%29) as accepting marked text as normal input. These are source-level guards, not interactive macOS IME validation. Chinese/Japanese composition during Save, slow Open, Format/Cut/Find completion, New, close and Quit remains a release gate.

### P2 — Untitled Save could not replace an existing selected target — **fixed and regression-tested**

**Historical defect:** In `src/Mote.Native/NativeEditorController.cs`, `StartSave`, the Save command opened a file picker for an untitled document, but the existing-target branch was gated by `saveAs`. Pressing **Save** on an untitled document and selecting an existing target therefore called `Document.SaveAsync(path)` rather than `SaveOverAsync`; Engine correctly rejected that call with “explicit overwrite approval required.” The document remained safe but the ordinary Save workflow failed.

**Current fix and evidence:** `StartSave` now tracks `pickerWasUsed` and routes any picker-selected existing *different* target through `FileOverwriteToken.CaptureAsync`, `ConfirmOverwriteAsync`, and `SaveOverAsync`, regardless of whether the user initiated Save or Save As. The same-path flow and external-change check remain. Validation added a fake-shell regression covering denial (target preserved, document still dirty) and later approval (save succeeds); the focused native/navigation/CSV suite passed **20/20**, and the frozen-tree Windows Release suite passed **171/171** ([validation record](../tests/VALIDATION.md)).

### P0 — Mixed-newline edit could silently delete a logical line break — **corrected in current working tree**

**Historical defect:** In `src/Mote.Native/NativeTextProjection.cs`, `Difference`, the source/display mapping handled each isolated line ending, but the resulting `TextChange` was not closed under re-projection at the *seams* between retained source and replacement text.

**Exact repro:** Source `"\ra\n"` projects to RichEdit display `"\r\na\r\n"`. Delete only the `a` in the native control, yielding `"\r\n\r\n"` (two logical line breaks). `Difference` yields a change whose application produces source `"\r\n"`; projecting that source yields only `"\r\n"` (one logical line break). The adjacent original CR and LF merge into one CRLF after deletion. Thus the editor immediately hides one newline and Save persists data different from what the user just edited. This is not an exotic invalid CRLF cursor operation; deletion of `a` uses ordinary boundaries 2–3 in the displayed text.

**Evidence:** `.temp/native_projection_exhaustive.py` enumerated valid CRLF-boundary edits for source strings up to length four and found this case. `NativeControllerTests` now includes the exact seam regression. After the fix, **5,000 seeded random edits** and exhaustive short combinations of CR, LF, CRLF, ordinary characters and surrogate pairs passed the source/display roundtrip invariant ([validation record](../tests/VALIDATION.md)). Interactive RichEdit behavior remains unverified.

**Design invariant:** The projected source after applying any accepted native edit must equal the edited native display; otherwise the edit must not silently commit. The current fix implements this contract, and its common-path validation is now a streaming comparator rather than another full-page allocation. Its edit-to-paint latency still needs measurement on target hardware.

### P1 — Windows semantic colors and selection used the wrong newline coordinate space — **code fix present; interactive validation pending**

**Historical defect:** `src/Mote.Native/Windows/WindowsEditorShell.cs` requests `EM_GETTEXTEX` with `GT_USECRLF`, so the managed display has two UTF-16 units per line break. RichEdit 2+ stores paragraph breaks as one CR internally, and `EM_EXSETSEL` addresses its internal positions. The earlier shell sent managed display offsets directly to `EM_EXSETSEL` via `SetSelection`; `SetDocument`, semantic styling and preview styling were all affected.

**Trigger/impact:** For `"a\r\nb"`, a token span at display offset 3 (the `b`) is selected at internal position 3 rather than internal position 2. Tokens after newlines are colored at the wrong place or not at all. When `SetDocument` must replace native text, restoring the old internal caret against the new display length also becomes unreliable. Preview styling has the same offset drift. Microsoft documents that `GT_USECRLF` translates each CR to CR/LF, whereas `GT_RAWTEXT` preserves position alignment with text in memory; [GETTEXTEX reference](https://learn.microsoft.com/en-us/windows/win32/api/richedit/ns-richedit-gettextex). Microsoft also documents RichEdit 2+ single-CR paragraph markers; [About Rich Edit Controls](https://learn.microsoft.com/en-us/windows/win32/controls/about-rich-edit-controls).

**Current fix:** The native owner added `Windows/RichEditOffsetMap.cs`; `GetSelection`/`SetSelection` convert between native single-CR and CRLF-display positions, and preview text/spans receive a corresponding projection. `tests/Mote.Tests/NativeReviewTests.cs` checks multiline token offsets, all native caret positions across representative strings, and preview span composition (filtered run **7/7**). Windows semantic styling now imports one escaped RTF page after input-idle coalescing, rather than issuing a selection/format call for every token. An isolated real-control 128 KiB/4,096-span probe measured **16.7 ms** ASCII multiline, **50.0 ms** one long line and **57.6 ms** mixed Unicode for RTF import including selection/scroll restoration ([performance record](native-richtext-performance.md)); the current production page is smaller, and these are not product p95 or IME/accessibility validation.

## Material release gaps (not newly introduced defects)

- All six formats now offer per-document analysis sessions, but `NativeEditorController.ScheduleSessionAnalysis` requests only **visible** scope beyond 2 Mi UTF-16 units. Plain text and CSV may still assert exact whole-document facts; Markdown, JSON, TOML and YAML can return `Provisional`/covered-region results rather than complete global validation in this path. `SessionDiagnosticSummary` labels these as globally unknown, and complete results use an exact total diagnostic count. The release ambition of complete semantics for large structured files therefore remains unmet despite the truthful status; `Format` also rejects documents above the same threshold. A bounded global-analysis scheduling policy is needed before claiming full large-file semantics.
- The large-file UI uses a **64 Ki UTF-16 page with 8 Ki edit slack** and manual `PreviousPage`/`NextPage` navigation rather than continuous scroll or offscreen accessible navigation. Global Select All, Copy, Cut, Find and Go To Line now operate in engine coordinates; the native control still exposes only one page to screen readers, and a global Copy/Cut materializes the selected text into one string before placing it on the OS clipboard. This is a product/accessibility and memory gate, not necessarily a quick local patch; `docs/single-binary-feasibility.md` records the virtualized-control plan. Focused page-end typing/paste regressions passed after the page/slack change ([validation record](../tests/VALIDATION.md)).
- macOS `NSTextView` and Windows RichEdit are reasonable system-native IME/accessibility starting points, but no source-level inspection proves real CJK composition or screen-reader behavior. Avoid claiming these are validated until interactive target-OS tests pass. The macOS callback now withholds marked-text changes from the engine until composition ends; the conditional document-identity risk above must be resolved or disproved by interactive tests.

### Continuous viewport and opportunistic Full-analysis audit (2026-09-29)

Scope: `src/Mote.Native/Viewport/**`, `NativeIdleFullAnalysis.cs`, and the corresponding controller/session-driver/entry-point diff. I found **no demonstrated correctness defect** in the frozen model/scheduler wave. `ContinuousViewport` retains a global source anchor, asks the engine for indexed logical-line starts, excludes CR/LF/CRLF delimiters from bounded visible slices, and snaps slice boundaries away from UTF-16 surrogate seams. `SparseHeightIndex` stores only non-baseline row corrections and augments AVL nodes with prefix sums; its source↔pixel operations were compared with a flat oracle in the committed tests and a 10-million-line sparse case. This is a no-wrap logical-row model, not proof of grapheme shaping, wrapped-line geometry or a screen-reader-capable canvas ([viewport contract](../src/Mote.Native/Viewport/README.md)).

`NativeIdleFullAnalysis` debounces one optional Full request per stable version, cancels on edit/navigation, serializes through the document's format driver, and leaves a policy's `Provisional` result labeled as globally unknown. The controller checks document, driver, version and viewport identity again before publishing; a Full result cannot silently replace newer visible analysis. The updated diagnostic summary separates exact document-wide counts from errors actually intersecting the displayed page, including zero-width EOF errors. Focused viewport/idle tests and the verifier's new native suite passed **12/12** for this slice. The GC-based budget is explicitly **advisory**, not an OOM guarantee; JSON `Visible` may itself scan a 100 MiB source to certify global semantics, and canceled Full work shares a serialized parser lane with visible work. Measure actual allocation, cancellation latency and edit-to-visible presentation on 1/10/100 MiB workloads before claiming responsive large-file semantics. The new `Program` canvas flags statically call OS system libraries and do not add shipped companion files; final per-RID Native AOT inventory gates remain the strict-one-binary proof.

### Mac read-only on-screen canvas review (2026-09-29)

**P2 pointer/paint defect found and corrected in the working tree:** `MacOnScreenCanvasSurface.HitSource` initially treated `SourceLength == 0` as a missing `FirstOrDefault` row, but an intermediate blank logical line is a valid zero-length slice. A click on that row therefore fell back to the final visible row and wrong global UTF-16 offset. `HitSource` now tracks whether a row was found separately and returns a found blank row's own `SourceStart`. `DrawSelection` now paints a trailing selected delimiter marker for LF/CRLF, including blank rows. The on-screen probe adds intermediate empty LF/CRLF pointer checks and a selected-newline PNG. Hosted macOS arm64/x64 execution and visual inspection are still pending; the added probe path is source-level regression coverage, not a measured frame result.

The remaining observed ABI/ownership path is coherent at source level: `drawRect:` takes a by-value 32-byte NSRect, pointer events take Objective-C object pointers, `locationInWindow`/`convertPoint:fromView:` return 16-byte points, and the bitmap capture calls retain their NSWindow/NSView/CF/CoreText/CG resources through use. `CTFontCopyPostScriptName` is released, `CTLine` and attributed strings are released after paint/hit-test, and the screenshot `NSBitmapImageRep`/PNG data live within the AppKit autorelease pool. An unused 32-byte `SendRect` helper, which would need [`objc_msgSend_stret` on x86_64](https://developer.apple.com/documentation/objectivec/objc_msgsend_stret), was removed before use. The on-screen probe still needs both macOS Native AOT RIDs and visual PNG inspection; it does not test physical compositor presentation, IME, horizontal trackpad scrolling, discontiguous RTL selection or accessibility.

### Frozen on-screen canvas follow-up (2026-09-29)

I found **no new demonstrated source blocker** in the frozen Windows and additive Mac on-screen probe wave. In `WindowsOnScreenCanvasWindow`, an empty visible row is distinguished from a missing row and maps to its own `SourceStart`; source CR/LF/CRLF delimiters are excluded from the shaped slice but receive a selected trailing-cell fill, including on zero-length rows. `WM_PAINT` calls `BeginPaint`, ensures and binds a top-down 32-bpp DIB, completes Direct2D `EndDraw`, then `BitBlt`s that DIB to the window before `EndPaint`. Wheel, selection and rebind paths invalidate the window; each PNG capture calls `UpdateWindow` before copying the DIB bytes. The Windows probe checks CRLF-only selection, intermediate blank-row selection, Unicode point round-trips, a cross-64-KiB drag and a remote bounded long-line slice. The source caps each shaped text fragment at 16 Ki UTF-16 units, and ordinary COM/GDI teardown has matching `Release`, deselection, `DeleteObject` and `DeleteDC`. Painter and geometry use the same theme font family, size and no-wrap policy; foreground, background and selected foreground/background come from the active theme policy. No companion runtime dependency was introduced in this path. Local **win-x64 Native AOT** one-executable and three-theme large-fixture execution was reported by the platform owner; a supplementary numbered-line fixture showed visibly different before/after row ordinals ([Windows evidence](../src/Mote.Native/Windows/Canvas/README.md)). Windows Arm64 **offscreen geometry** has passed in hosted CI, but the new on-screen Direct2D/DIB path and interactive performance remain unverified there.

The Mac probe now calls `Display()` and captures separate numbered-row images **before and after** wheel movement, then selected, remote-long-line and newline cases. `CapturePng` redraws the same view into an AppKit bitmap after the visible draw and excludes that recapture from `ScreenDrawCount`; the outer autorelease pool keeps the bitmap and PNG objects alive until writing completes. The additional captures do not change the previously reviewed CoreText/CoreGraphics ownership path. Their ordering supports visual comparison of source row ordinals but is not evidence of physical compositor presentation. Both macOS AOT RIDs and hosted visual inspection remain pending.

**Conditional product integration guard, not a current probe failure:** Windows DIB size follows arbitrary `WM_SIZE` dimensions and `Capture` then allocates another `width * height * 4` array plus PNG compression buffers. The current fixed-size probe uses only a few MiB; a future resizable product canvas on an 8K/high-DPI display could make backing-store memory compete with 100-MiB document and parser allocations. Before replacing RichEdit, cap/reuse the raster buffers and measure resize/maximize allocation and paint latency rather than treating the fixed probe as a large-window guarantee. This is distinct from the already documented bidi, IME and accessibility release gaps.

### Hosted Mac foreground regression and source correction (2026-09-29)

**P1 visual defect observed in hosted run 36557417180 — corrected and target-host verified:** Mac dark-theme glyphs were black against a dark background, and high-contrast glyphs were black against black, despite `Draw` setting the themed `CGContext` fill. Apple documents that an attributed string without an explicit foreground defaults to black and CoreText overrides the context; setting [`kCTForegroundColorFromContextAttributeName`](https://developer.apple.com/documentation/coretext/kctforegroundcolorfromcontextattributename) to `kCFBooleanTrue` makes CoreText use the context fill instead. The correction resolves the exported CFString and CFBoolean pointer constants, applies the attribute over each nonempty bounded line in `WithLine`, and does not release those borrowed framework constants. Normal glyph drawing sets `EditorForeground`; selected-glyph redraw clips and sets `SelectionForeground`. The verifier's dependency-free `InspectCanvasPng.py` locates the first selected-row band and checks separate normal/selected glyph contrast and theme surfaces. It rejected the old hosted Mac dark/high-contrast images; a mutated Windows light selected-foreground image also fails while its original passes. [Hosted runs 36558583763](https://github.com/kleedaisuki/mote/actions/runs/36558583763), [36559175652](https://github.com/kleedaisuki/mote/actions/runs/36559175652) and the first blocking [36559682956](https://github.com/kleedaisuki/mote/actions/runs/36559682956) passed the read-only on-screen diagnostic on all four published AOT RIDs and all three themes. Both Mac RIDs reported dark-theme **487 normal / 366 selected** bright ASCII pixels and high-contrast **551 / 369**, versus zero before the fix; PNGs were also visually inspected. This closes the specific black-on-dark regression, not physical compositor timing, general Unicode shaping, interactive IME or accessibility ([validation record](../tests/VALIDATION.md)).

### Earlier document/session lifecycle conclusions

The document save path captures an immutable snapshot under a gate and marks edits made during save as modified; the reviewed controller also rejects document replacement while `_saving`, so I found no demonstrated save-vs-open use-after-dispose in the current flow. The format-session driver serializes calls, records a bounded ordered edit chain, rebuilds on a gap and defers disposal until in-flight analysis exits; the controller filters publication by analysis serial, document identity, session-driver identity and snapshot version. I found no demonstrated stale-semantic publication path in this integration. Telemetry record types are numeric/enumerated and do not expose a document path/content field; no direct telemetry privacy defect was identified here. These are source observations, not exhaustive concurrency or privacy verification. Focused native/session tests and the subsequent serialized Windows Release suite (**214/214**) passed. The macOS close-path change after that checkpoint still requires the hosted two-architecture workflow gate described above.

### Experimental interactive canvas/input-island review (in progress, 2026-09-29)

Scope is the explicitly opt-in `--canvas-experimental` path, not the default RichEdit/NSTextView editor. The controller validates document generation, immutable snapshot version, binding nonce and exact global selected span before its sole `Document.Apply`; the native islands keep one bounded caret-local source slice. The following are source-level findings against the frozen first interactive slice; platform owners are addressing them, and no hosted real-IME conclusion follows yet.

1. **P1 — Windows global Delete/Backspace could be a native no-op and fail to delete selected document text; source correction and HWND probes passed.** In the first frozen version, `WindowsRichEditIsland.Bind` / `SetNativeSelection` clamped a global selection to the one-line host. Select `[0,2)` in source `"a\n\n"` with active caret at offset 2, the start of an empty line: the host contained `""` and selection `[0,0)`. Delete/Backspace made no RichEdit change or `EN_CHANGE`, leaving the global source unchanged. The same early null-difference return lost a wider global selection's replacement when the native selected substring was replaced by identical text. The Windows island now routes global Delete/Backspace as an absolute transaction before RichEdit's local no-op and tags confirmed printable `WM_CHAR` replacements so a same-text local result still replaces the global selected span. The owner reports real-HWND probes covering eight LF/CRLF × selection-direction/delete cases plus four same-text cases passed. A later narrow IMM `GCS_RESULTSTR` confirmation handles same-text result-string replacement; a synthetic canceled composition with no result restores native-only changes and emits no engine edit. This is not yet a real IME/TSF pass.
2. **P1 — macOS large plain-text paste was rejected rather than bridged to the source document; direct path and persistent-root Undo now have repeated target-host passes.** The first frozen `MacTextInputIsland.PastePlain` rejected a paste that would make bounded NSTextView exceed 16 Ki. The corrected path keeps the native host cap but emits one absolute generation/version/nonce-tagged `TextChange`, using the global selection when present. A temporary controller preflight then rejected edits whose inserted-plus-removed UTF-16 byte cost exceeded 32 MiB to avoid immediately losing Undo; this was a *historical intermediate safety guard*, not the current product cap. Engine commit `7597b0f` switched Undo to retained persistent document roots and the controller removed that 32 MiB check. [Hosted runs 36566797297](https://github.com/kleedaisuki/mote/actions/runs/36566797297) and [36567450134](https://github.com/kleedaisuki/mote/actions/runs/36567450134) passed the published in-process AppKit probe on both osx-x64 and osx-arm64: 40 Ki mixed rich/plain paste, streamed exact 50 Mi-code-unit plain paste with ≤16 Ki native host, Undo→Redo→Undo, repeated-selection replacement, Save As/reopen to exact BOMless `Zac`, and unchanged original-file hash. The second run uploaded per-stage current working set and elapsed time; reported `PeakWorkingSet64=0` on Mac is **unavailable**, not a real peak. External keyboard/IME and p95 latency remain separate gates.
3. **P1 — macOS Save/Open/Close could be vetoed after a global selection with no edit; no-edit guard added.** Previously `CommitPendingText` called `CommitFinal` unconditionally, and a null local difference returned only if global selection was collapsed. After Select All without typing, `_replacementRangeBeforeEdit` was null and `CommitFinal` threw, so `MacEditorShell.CommitPendingText` vetoed the command. The island now records whether a native change callback or composition actually occurred and returns on an untouched host. It still allows an observed same-text ordinary replacement to replace a wider global selection; hosted AppKit command tests remain decisive.
4. **P2 conditional — macOS resize during marked text could separate the native candidate host from its canvas row; same-host move added.** The first frozen `Draw` updated `_height` on NSView resize but `PlaceHost` returned while composing. The current resize path moves the existing bottom-origin `NSScrollView` without replacing `NSTextView` text or selection and defers a controller viewport resize until composition settles. Candidate coordinates still require real Pinyin/Japanese tests; this was a geometry risk, not a demonstrated source mutation.
5. **P1 conditional — final composition semantics remain unproven on both OSes.** Windows now treats an IMM `GCS_RESULTSTR` or printable `WM_CHAR` as confirmation and discards native-only differences after an unconfirmed cancel. However [RichEdit `EN_STARTCOMPOSITION`](https://learn.microsoft.com/en-us/windows/win32/controls/en-startcomposition) and [`EN_ENDCOMPOSITION`](https://learn.microsoft.com/en-us/windows/win32/controls/en-endcomposition) also cover TSF; a TSF commit arriving through these notifications without an IMM result string or `WM_CHAR` could be classified as cancel and dropped. On macOS, `CommitFinal` returns on a null local difference after any composition; a confirmed candidate identical to the bounded local text but intended to replace a wider global selection would likewise not mutate the engine. These are conditional input-loss paths derived from source and OS contracts, not reproduced target-IME failures. ### Windows opt-in UIA fragment foreground-focus correction (2026-09-29)

**No new source-level blocker found in the narrow focus patch.** `UiaFragmentRootObject.InputHasFocus` now requires the input HWND's owner thread to own the current foreground window *and* `GetGUIThreadInfo(ownerThread).Focus` to equal the input HWND. Querying the HWND's owner thread rather than the COM callback thread is necessary, while the foreground requirement avoids claiming global UIA focus merely because a background editor retains thread-local focus. `GetForegroundWindow` returns an HWND-sized pointer, `GetWindowThreadProcessId` returns a `DWORD`, and the existing `GUITHREADINFO` layout is pointer-sized on supported Windows RIDs. `SetFocus` still refuses to dispatch to a different GUI thread and reports failure rather than pretending focus moved. The opt-in fragment is selected only with both canvas and `--uia-fragment-experimental`; the default RichEdit/AX path is unchanged. The added unit checks cover the pure same-thread/different-thread focus decision and a real message-only HWND's inability to own the foreground, but they do not reproduce a foreground switch on a real top-level editor. Two foreground reads bracket the GUI-thread query; a concurrent user focus switch can still make any sampled focus claim momentarily stale, so the pending hosted ARM64 external UIA rerun remains the behavioral gate, not a claim of atomic focus state.

**P1 numeric UIA property defect found by the hosted ARM diagnostic; correction reviewed, target-host rerun pending.** The initial fragment returned dynamic focus under property `30009`, which is **IsKeyboardFocusable**, not **HasKeyboardFocus** (`30008`). Thus a foreground logical document could falsely report that it was focusable only while focused, while its actual focus property fell back to a default. The corrected Pane/root reports `30008=false`, `30009=false`, `30016=true` (control), `30017=false` (not content); its Document child reports dynamic `30008`, `30009=true`, `30016=true`, `30017=true`. These identifiers and `VT_BOOL` semantics match [Microsoft's UIA property table](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-automation-element-propids); `30003` Pane/Document control types, `30005` Name, and `30011` AutomationId are otherwise unchanged. The generated-COM vtable test now queries both IDs and the false-focus state, and the owner reports focused AX **25/25** plus Native Release build clean. It does not test the true-focus state or whether a UIA `CacheRequest` coalesces/exposes the RichEdit host differently on ARM64; fresh and cached external-client tree/focus observations are still the discriminating gate. This patch remains behind the two explicit experimental flags, so it does not change default AX behavior.

### Mac ARM64 Objective-C font-call ABI correction (2026-09-29)

**Confirmed opt-in crash path; narrow ABI correction target-host verified.** [CI 36590047135](https://github.com/kleedaisuki/mote/actions/runs/36590047135) reproduced a blank `--canvas-experimental --smoke-gui` ARM64 `SIGSEGV` with LLDB stack `objc_msgSend` ← `CFStringHasPrefix` ← `+[NSFont fontWithName:size:]` ← Mote `Send_10` ← `MacTextInputIsland.SetTheme` ([validation record](../tests/VALIDATION.md)).
