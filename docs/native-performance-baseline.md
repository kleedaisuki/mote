# Native performance baseline and evidence boundaries (2026-09-29)

## Status and decision

The repository has a **scheduled/manual, non-gating** benchmark path in `.github/workflows/benchmarks.yml`. It publishes a process-isolated **Native AOT** engine benchmark and the native editor on Windows x64 and macOS arm64, then uploads raw JSONL rather than failing on a timing threshold. [Hosted run `36549790750`](https://github.com/kleedaisuki/mote/actions/runs/36549790750) passed **all four jobs** and uploaded both engine and both startup artifact sets; the environment-specific baseline below is computed from those files. An [earlier run `36549385420`](https://github.com/kleedaisuki/mote/actions/runs/36549385420) uploaded both engine sets, while both startup scripts produced JSON and then the workflow wrapper falsely failed on `$LASTEXITCODE -ne 0` (`Native startup measurement failed ()` in the log), preventing their uploads. The redundant wrapper check was removed before the successful run. None of these numbers is a release performance SLA or a cross-OS speed comparison.

This deliberately measures two different contracts:

| Instrument | What it actually measures | What it does **not** measure |
| --- | --- | --- |
| `tests/Mote.Benchmarks` Native AOT executable | `Document.OpenAsync` wall time after a synthetic file exists; sequential end/start/middle engine edits; optional 1 MiB Markdown analysis; process peak working set | Native GUI projection, parse-to-presentation, actual keystroke latency, first editable frame or paint |
| `tests/Measure-NativeStartup.ps1` with Native AOT `mote --smoke-gui` | Parent-observed process launch through GUI smoke **exit**, sampled working-set lower bound, telemetry initialization/write on vs off | Cold disk-cache miss, open-file-to-editable, physical first paint, IME, edit-to-paint, exact lifetime peak RSS |

The separation matters. A fast engine edit is not proof that the UI remains smooth: [the large-file UI probe](large-file-ui-evaluation.md) found that a standalone rope edit and an attached GUI edit can differ by orders of magnitude. Likewise, `--smoke-gui` emits its ready marker after the native window is shown and immediately closes; timing its entire process lifetime is **not** a first-frame measurement.

## Reproducible methodology

The engine benchmark generates deterministic ASCII files under repository `.temp/benchmarks/`, then excludes generation from `OpenMs`. `--open-edit` uses a line-bearing Markdown-like pattern; `--long-line` uses one unbroken `a` line. The requested size is exactly 1, 10 or 100 MiB of ASCII bytes, equivalent to that many UTF-16 code units before edits. Each invocation is a new process. After open, it records three one-character-location insertions (each inserts seven ASCII characters) **sequentially**: near end first, near start second, middle third. The retained `EditMs` field aliases the original first/end edit for JSON consumers; schema version 2 added named edit fields and `OriginalLengthUtf16`, while version 3 marks unavailable peak/private counters with `null`. Do **not** infer that one position is intrinsically faster from those three timings: order and first-edit initialization are confounded. The weekly/manual hosted workflow repeats each size/shape combination three times, plus three 1 MiB Markdown full-analysis runs. It does not attempt a 100 MiB full semantic parse as a startup/edit proxy.

The benchmark records `PeakWorkingSetBytes` from the running process and after-open/after-edit working set. On Windows these are process working-set counters. On hosted macOS arm64 Native AOT, **all 21** `PeakWorkingSetBytes` and `PrivateBytesAfterEdits` values in run `36549790750` were zero even though `WorkingSetAfterEditsBytes` was positive; zero means those two counters were **unavailable**, not zero memory. A narrow benchmark harness correction now writes `null` for non-positive peak/private counters (schema version 3). The older schema-version-2 macOS artifact retains zeros and must be interpreted as unavailable; the **point-in-time** `WorkingSetAfterEditsBytes` is reported separately below and is not a peak. A row carries OS, architecture, runtime version and logical processor count. JSON serialization is source-generated so the same harness works under Native AOT. Microsoft describes [Native AOT](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/) as ahead-of-time native compilation without runtime JIT; benchmarking a JIT harness would conflate a different runtime regime with the shipped native executable.

The schema-3 correction was validated independently in [hosted run `36550663893`](https://github.com/kleedaisuki/mote/actions/runs/36550663893), which passed all four jobs: all 21 macOS engine rows have `PeakWorkingSetBytes: null` and `PrivateBytesAfterEdits: null`, while all 21 have a positive `WorkingSetAfterEditsBytes`. This confirms the representation of unavailable counters, not a newly established macOS memory peak; the baseline statistics below remain those of run `36549790750`.

The startup script takes one **first invocation** after publish, then ten warm telemetry-off/on pairs in alternating order. "Cold" remains the old JSON field name for compatibility, but `cold_definition` explicitly says the OS file cache was **not evicted**. It launches the GUI-subsystem executable with `Start-Process`, waits for exit, verifies the exact `mote-native-gui-ready` marker, and times from just before process creation through observed exit. During life it polls `PeakWorkingSet64`; a **positive** `observed_peak_working_set_bytes` is a sampled **lower bound**, not an exact lifetime peak. On macOS in run `36549790750`, the property remained zero despite **28–130 polls per process**; all 21 startup samples correctly serialize this as `null` (unavailable), **not zero resident memory**. Earlier run-`36549385420` logs containing zero must likewise be interpreted as unavailable. Child stdout, stderr, temporary `MOTE_HOME`, and opt-in JSONL traces stay under `.temp/benchmarks/`; per-run and aggregate results stay under `.cache/benchmarks/`. The script checks the resolved scratch directory before recursive cleanup. `MOTE_TRACE=1` is applied only to the telemetry-on child; the successful hosted run generated about 2.95 KiB of trace data per platform. That is still a startup-smoke overhead comparison, not tracing overhead while typing.

Hosted runners are fresh VMs and their labels, images, and available CPU/memory can change; [GitHub documents the hosted-runner model](https://docs.github.com/en/actions/reference/runners/github-hosted-runners) and [runner-image labels](https://github.com/actions/runner-images). The workflow pins `windows-2025` / `win-x64` and `macos-26` / `osx-arm64` instead of cross-comparing unlabelled `-latest` changes, but pinning the image generation does **not** pin physical hardware or background load. [Kalibera and Jones, ISMM 2013](https://kar.kent.ac.uk/33611/45/p63-kaliber.pdf) explain why nested repetitions and uncertainty, rather than a lone best run, matter for performance studies. Three engine process repetitions and ten startup pairs are a useful baseline, **not** sufficient for an automatic p95 latency SLA across heterogeneous runners. Keep the uploaded raw samples and compare changes within the same RID/image family and similar workload/commit context.

### Mac GUI-smoke gap: a phase-localization investigation, not a platform verdict

The second successful [hosted run `36550663893`](https://github.com/kleedaisuki/mote/actions/runs/36550663893) supplies another ten **telemetry-off warm** smoke samples per OS. This table uses the conventional average-of-two-middle-values median and median absolute deviation (MAD), calculated from each artifact's `warm_samples_ms`: `median = (sorted[4] + sorted[5])/2`, then `MAD = median(abs(sample − median))`. It is intentionally separate from the nearest-rank summary fields above. A local scratch calculation lives under `.temp/benchmarks/startup-variance.ps1`; the formula and uploaded samples, not that ignored scratch file, are the reproducible record.

| Run | RID | Warm off median | MAD | Observed min–max |
| --- | --- | ---: | ---: | ---: |
| `36549790750` | `win-x64` | 74.8 ms | 1.8 ms | 69.2–83.9 ms |
| `36549790750` | `osx-arm64` | 363.7 ms | 30.3 ms | 304.8–915.3 ms |
| `36550663893` | `win-x64` | 83.9 ms | 5.0 ms | 78.4–98.1 ms |
| `36550663893` | `osx-arm64` | 252.1 ms | 32.7 ms | 175.6–448.0 ms |

The macOS median moved **−111.6 ms (−30.7%)** between these two runs; Windows moved **+9.1 ms (+12.2%)**. The macOS within-run off-sample max/min ratio was **3.00** and **2.55**, respectively, versus **1.21** and **1.25** on Windows. Telemetry-on medians also fell on macOS (362.1 to 258.6 ms), so telemetry does not explain the large run-level shift. These are *observed hosted-run spreads*, not a statistical estimate of runner hardware variance: the runs used different VMs **and different executable hashes/commits**, and the process-lifetime metric includes PowerShell launch, AppKit setup, intentional immediate close, and shutdown. The macOS/Windows median ratio changed from about **4.9× to 3.0×**; neither ratio is an intrinsic OS or editor-rendering comparison. There are only two VM instances per OS, so do not derive a cross-platform regression target from them.

The current `--smoke-gui` path is especially easy to overinterpret. `Program.Main` resolves theme and constructs `NativeEditorController`, then `MacEditorShell.Run` calls `NSApplicationLoad`, creates the window/menu, calls `makeKeyAndOrderFront:`, and **posts** `Shown` before entering `[NSApplication run]`. `Program` prints the ready marker in that callback and posts `Close`; a first text-view draw is neither required nor observed. Thus even a fast `Shown` callback would not prove a usable or painted editor, and a slow smoke exit might be a slow close/run-loop wake rather than a slow launch. Apple's [`NSView.displayIfNeeded`](https://developer.apple.com/documentation/appkit/nsview/displayifneeded%28%29) documentation distinguishes invoking view drawing from merely invalidating it; [`NSWindow.windowDidExpose`](https://developer.apple.com/documentation/appkit/nswindowdelegate/windowdidexpose%28_%3A%29) signals exposure, not a verified pixel on a display. **None** of these callbacks alone is physical presentation.

#### Hypotheses and cheapest discriminating tests

| Candidate source of the gap | Discriminating observation | Interpretation if confirmed |
| --- | --- | --- |
| Process launch / dynamic loading / PowerShell wrapper | Interleave the *same published binary's* `--check-runtime` and `--smoke-gui` under the same parent launcher; compare polling-on with polling-off. On macOS, inspect a few launches with Apple's [Instruments App Launch / Time Profiler guidance](https://developer.apple.com/documentation/xcode/reducing-your-app-s-launch-time). | A large pre-`Main` or parent-to-child-entry component is not AppKit view or text rendering. Do not optimize the document engine for it. |
| AppKit first use and native view construction | Opt-in phase timestamps around `PrefersDark` (which itself calls `NSApplicationLoad` / `sharedApplication`), shell setup, `CreateWindow`, `CreateMenu`, projection, `makeKeyAndOrderFront:`, and entering the run loop. | A dominant AppKit phase points to a concrete construction path for profiling; a tiny phase rules out the easy “AppKit startup” story. |
| Posted `Shown` delivery, close, or teardown | Timestamp posted-callback entry, close request, run-loop return, telemetry shutdown and last managed line; compare a probe that remains open until one actual draw callback with existing immediate-close smoke. | A large ready-to-exit interval means today's metric penalizes teardown and may close before first draw. |
| Actual first draw or edit-to-paint | Keep a real file-open window alive; record projection-complete, key/first-responder state, first visible-window draw callback, then an injected text input and the draw of the resulting revision. Use a separate external screen observer for pixel visibility. | This finally separates usable editor, drawing submission and observed pixels. Existing headless edit timings cannot substitute for it. |

The smallest AOT-safe code instrumentation is an **opt-in, fixed-size array of phase IDs and `Stopwatch.GetTimestamp()` values**, captured at those boundaries and serialized *once at shutdown* to a repository-local JSONL file. Timestamp collection must not allocate, call `Console`, or synchronously write inside AppKit paint/input callbacks; include a monotonic sequence/revision ID so the first post-edit draw can be matched to its edit. Child phase **durations** share one clock; do not subtract a child timestamp from a parent `Start-Process` timestamp unless the clocks are explicitly synchronized. Retain the parent process-start-to-exit measurement separately, then compare phase sums and the unaccounted launch/observer remainder. Microsoft's [`Stopwatch.GetTimestamp`](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.stopwatch.gettimestamp) supplies the timer API. Native AOT supports [EventPipe only when explicitly enabled](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/diagnostics), so adding EventSource/EventPipe merely to answer this initial question would be more invasive than the timestamp buffer. If a phase remains large, correlate it with Apple [signposts in Instruments](https://developer.apple.com/documentation/os/recording-performance-data) and native CPU/thread-state profiling rather than assuming the cause from wall time alone.

For **first editable**, require both a projected document and an active native first responder, then send an input through the AppKit event path and verify a resulting engine revision; a direct `ProbeInsertAtEnd` call is useful for a lower-level path but bypasses physical input dispatch. For **first draw**, record the first *visible* view draw callback (not `displayIfNeeded` invoked only to make a test pass). A draw callback measures CPU-side rendering, **not** compositor presentation. On a permissioned local Mac, an independent [ScreenCaptureKit](https://developer.apple.com/documentation/screencapturekit) observer can timestamp the first captured frame containing a distinctive marker and the first changed frame after an edit; account for capture-frame interval and pipeline delay, and do not label that timestamp exact photon time. Screen-recording permission and a visible desktop make this a local validation, not an assumed hosted-runner capability. The current on-screen Canvas probe already counts visible `drawRect:` callbacks, but it is a read-only surface and does not establish the `NSTextView` editing path's latency.

**Target experiment:** keep a fixed SHA-256 Native AOT executable per platform and fixed runner image, use telemetry **off** for the primary path, alternate control and GUI cases, and collect at least 30 warm processes on each of at least three independent hosted VM instances. Record OS/image, CPU count, executable hash, timer overhead, phase deltas, median/MAD and raw samples; reserve one first invocation per VM as a separate, *not cache-cold*, category. Run with and without the parent's 2 ms memory-poll loop to bound observer overhead. Repeat any apparent phase difference on a stable local Mac under Instruments before changing production architecture. Then, with a real Markdown file and separately with a 100 MiB/long-line file, measure open-to-first-editable and edit-to-first-draw; local external pixels can bound draw-to-visible. Only a repeatable, phase-localized bottleneck should motivate an optimization, and no CI timing gate is warranted yet.

### Reproducible 100 MiB Markdown completeness benchmark

The standalone `benchmarks/Mote.MarkdownBenchmarks` project isolates the new large-Markdown semantic-session contract from the earlier engine/JSON harness. It publishes as Native AOT on Windows x64 and macOS arm64. Each invocation writes **exactly 104,857,600 ASCII bytes** to a repository-local `.temp/benchmarks/` file using a 64 KiB buffer, then excludes file generation from `Document.OpenAsync` and analysis timings. It appends one source-generated-JSON row to `.cache/benchmarks/markdown-large.jsonl`; the temporary source file is removed. The four modes are deliberately *different semantic cases*, not interchangeable timing samples:

| Mode | Deterministic source | Required analysis contract |
| --- | --- | --- |
| `markdown-flat` | 12,800 blank-separated, 8,190-character `alpha...` paragraphs (8,192 bytes per block) | Uncached `Full` is `Complete`, covers the entire 100 MiB, and reports exact zero diagnostics; one character replaced at UTF-16 offset 64 stays `Complete` after one `VersionedEdit`. |
| `markdown-dense` | Repeated `alpha\n\n` paragraphs, far beyond the flat block-count admission budget | `Full` and near-start edited `Full` are `Provisional`, with unknown total diagnostic count; fast rejection is **not** complete parsing. |
| `markdown-complex` | Repeated heading/inline link, list item and fenced JSON | Same honest `Provisional` outcome; independent flat-block certification is unsafe for this syntax. |
| `markdown-cancel` | Same sparse flat source as `markdown-flat` | A 5 ms *requested* timer cancellation interrupts the uncached scan; a second `Full` on the same session recovers `Complete`. Record the timer's **actual** request time and the request-to-observed-cancellation interval separately. |

All session calls are synchronous on one measured thread. `GC.GetAllocatedBytesForCurrentThread` is **cumulative transient analyzer allocation**, not retained heap; allocation excludes source generation and file open, but includes the session call and projection. A forced GC occurs after open and before the measured analysis. Process working-set samples are taken after open, analysis, edit and cancellation recovery; a positive `PeakWorkingSet64` is a **whole-process lifetime** peak including the engine document, not an analyzer-only RSS increment. As with the preceding engine benchmark, a zero OS peak counter is serialized as `null` (unavailable), and positive macOS point-in-time `WorkingSet64` must **not** be labeled a peak. The edit's engine `ApplyMs` and session `EditAnalyzeMs` are distinct; neither includes native UI projection or paint. For cancellation, the timer may fire later than its requested 5 ms under scheduling/GC load, so response latency must be assessed from the recorded actual request timestamp, not `InitialAnalyzeMs − 5`.

A **single local Windows x64 Native AOT sanity run** (Windows 10.0.26200, .NET 10.0.11, 20 logical processors, warm cache) passed all four contracts: flat uncached certification 559 ms / 638,971,432 allocated bytes / 229.4 MiB process peak; flat edit analysis 0.024 ms / 67,928 bytes; dense and complex Full returned `Provisional` in 1.18 and 0.98 ms. The cancellation timer actually fired at 13.63 ms, the exception followed 0.034 ms later, and the same session recertified in 555 ms. These are **one-shot functionality and order-of-magnitude checks**, not a p50, p95, or cross-platform performance claim. In particular, the ~609 MiB transient allocation of a complete flat certification is a real GC/energy cost despite modest retained RSS; its practical significance requires hosted repetition and, eventually, user-file distributions.

All six cancellation rows observed `OperationCanceledException` and subsequently recovered `Complete` in the **same session**. The requested 5 ms timer was actually delivered after **10.17–23.82 ms** on the hosted VMs; the sub-0.1 ms measured reaction applies *after that request* and does not promise a 5 ms user-visible cancellation bound. The harness does **not** record whole-process start-to-exit wall time: `OpenMs` excludes fixture creation, `InitialAnalyzeMs` is the first uncached session call (or time to cancellation), and neither is a GUI first editable frame or physical paint. Do not add phase medians and call the result process startup. A future process-lifetime field would require a new schema and equivalent hosted rerun, not an inference from GitHub step duration.

`Benchmarks` now has a focused `workflow_dispatch` choice `suite=markdown`. It runs three process-isolated repetitions of all four modes **on the same VM and same published binary per RID**, rotating mode order, and uploads the 12 raw JSONL rows per platform without a timing gate. `suite=engine` and `suite=startup` retain their previous manual workloads; default `suite=all` and the weekly schedule run all suites. On a push, a small path-classification job selects only the suites whose source areas changed: `benchmarks/Mote.MarkdownBenchmarks/**` selects Markdown, `tests/Mote.Benchmarks/**` selects existing engine/JSON, and `tests/Measure-NativeStartup.ps1` selects startup. A workflow-only change conservatively selects all; a workflow change accompanying only Markdown source selects Markdown alone. This prevents a Markdown-only push from repeating the already measured 100 MiB JSON guard. The useful hosted comparison is **within one RID/VM** across modes and across same-RID repeated runs; it is not a macOS-vs-Windows speed contest. Three repetitions make nearest-rank p95 equal the sample maximum, so preserve raw points and do not invent a tail SLA.

### Opt-in interactive canvas: external GUI evidence and unresolved scroll gap

`benchmarks/NativeCanvasGui/` now contains an **external-process** diagnostic for the experimental continuous canvas, separate from both the headless engine benchmark and the read-only on-screen canvas screenshots. Its fixtures are synthetic and byte-exact: 100 MiB of 64-byte CRLF rows with repeating visible ordinals, and 50 MiB of one ASCII line. It creates and removes them only under repository `.temp/`; compact JSONL stays under `.cache/benchmarks/`. The [harness README](../benchmarks/NativeCanvasGui/README.md) gives the commands and observation contract. The Windows probe discovers the exact child PID's native canvas and **focused, visible bounded RichEdit island**, sends one `WM_CHAR`, checks the dirty marker, saves, and proves via a streaming hash that exactly one `X` was inserted before every original byte. Its 100 MiB case sends the real canvas `WM_VSCROLL/SB_BOTTOM` and observes scrollbar movement. A cross-process child-control length must use `WM_GETTEXTLENGTH`, not `GetWindowTextLengthW`: [Microsoft documents that `GetWindowText` does not retrieve another process's control text](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getwindowtexta). This distinction caused and then resolved the first local harness false failure.

The smallest local Win x64 Native AOT probe used `.cache/canvas-large-undo/publish-win-x64/mote.exe`, SHA-256 `AD31D5B4FAC5C649F4882E9C99446A3F03923FB0596C6F954A05F98C71A2E776`, **not a newly published binary from the current Native working tree**. A combined successful one-shot run on Windows 10.0.26200 / .NET 10.0.11 reported:

| Synthetic file | Parent start → externally focused host | Native `WM_CHAR` → dirty title | Edit → exact Save | Host UTF-16 units before / after | OS memory observation | Scroll observation |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| 100 MiB many-line | 623.6 ms | 17.4 ms | 677.5 ms | 62 / 63 | Whole-process peak 282.6 MiB | `SB_BOTTOM` raised normalized vertical position to 999,978 in 11.4 ms |
| 50 MiB single-line | 455.2 ms | 11.1 ms | 266.1 ms | 16,384 / 16,384 | Whole-process peak 185.4 MiB | One wheel message was processed without expanding the host; no positive horizontal-scroll result |

These timings include the PowerShell launcher, 20 ms polling, window activation, OS dispatch, and Save I/O; they are **not** process-internal open-to-first-editable timestamps, keystroke latency distributions, first drawing, or physical paint. The document's exact disk bytes after Save establish that the small edit reached the engine; a dirty title alone would not. The unchanged 16,384-unit long-line host is a useful bounded-memory check, **not** evidence that its remote 50 MiB content was horizontally reachable. One intermediate local long-line host-bind attempt timed out despite later passing; its cause was not localized, so the harness now records the last window/host state on a bounded timeout. A fresh Native AOT build and repeated runs on the target host are needed before treating these numbers as a product baseline.

The interactive canvas currently has **no user-facing horizontal scroll path**: `ContinuousViewport.SetHorizontalOffset` has no caller, and the Windows island handles wheel/vertical scroll but not horizontal wheel or a horizontal scrollbar. A read-only test's direct `Reveal` of a remote long-line slice is *not* equivalent to user navigation. Therefore the requested long-line horizontal-scroll gate is **unsupported**, not passed. It needs an explicit Native owner decision and implementation before a performance number could be meaningful. A one-logical-line file also cannot demonstrate positive vertical movement; the many-line case is the vertical test.

The companion `Measure-MacCanvasGui.ps1` is deliberately a **non-gating capability probe** for hosted macOS arm64. It launches `--canvas-experimental`, uses exact-PID System Events/AX focus, sends one external `X` and Command-S, applies the full byte oracle, and tentatively compares [`AXVisibleCharacterRange`](https://developer.apple.com/documentation/appkit/nsaccessibilityprotocol/accessibilityvisiblecharacterrange%28%29) before/after View → Next Page. An AX range change would be a source-viewport clue, not a rendered-pixel proof; the new custom canvas AX hierarchy and TCC permissions have **not** yet been target-tested. The custom AX element can expose the global source length while hiding the native input `NSTextView`, so its `AXNumberOfCharacters` cannot certify the host's 16 KiB limit. The script does not read `AXValue` or claim that bounded-host property from AX. Prior default-editor external keyboard success and separate in-process AppKit clipboard success do not transfer automatically to this combined experimental path. Its AppleScript/AX timing includes compilation and automation startup, so comparing its raw "open-to-AX-focus" value directly with Windows' Win32 polling would be invalid.

#### 50 MiB Mac canvas paste/Redo: a fluency signal, not an isolated phase time

The separate in-process AppKit clipboard probe's [hosted run `36567450134`](https://github.com/kleedaisuki/mote/actions/runs/36567450134) passed exact 40 KiB/50 MiB paste, Undo/Redo, bounded host and saved/reopened bytes on macOS arm64 and x64. Its milestone file reports the following **single-run** intervals and point-in-time working sets; the OS peak counter was zero/unavailable throughout both runs:

| Hosted RID | Stage 4→5 (50 MiB paste through next validated state) | Point resident after stage 5 | Stage 6→7 (Redo through next validated state) | Point resident after stage 7 |
| --- | ---: | ---: | ---: | ---: |
| macOS arm64 | 1,029 ms | 605.1 MiB | 649 ms | 808.4 MiB |
| macOS x64 | 4,089 ms | 555.9 MiB | 2,661 ms | 660.5 MiB |

These intervals **include probe work**: stage 4 constructs a new 50 MiB managed string before paste; stages 5 and 7 each run `MatchesHuge` over all 50 MiB before recording; every subsequent state is scheduled with a 60 ms delay. Consequently, the table is an upper bound on combined fixture construction/native transaction/whole-document oracle/scheduling, **not** isolated paste or Engine Redo latency. It is still consequential: one cannot claim 50 MiB interaction is "instant" on the hosted x64 path, and the point resident sets are substantial on both hosts. Because architecture, runner hardware and possibly translation differ, this single comparison does not identify a CPU-architecture cause or a memory peak.

The next discriminating experiment is **phase-localized on the same binary and host**, not a speculative rewrite. Ask the Native/Engine owners to add opt-in, fixed-buffer monotonic timestamps at (1) fixture/clipboard construction outside the user transaction, (2) AppKit input dispatch and native text extraction, (3) Engine root Apply/Undo/Redo, (4) legacy `Changed` payload construction and subscriber delivery, (5) controller viewport/input-window projection, (6) AppKit rebind/layout/draw callback, and (7) independent `MatchesHuge` oracle completion. Record `GC.CollectionCount` and allocation deltas around synchronous phases, plus positive point RSS; never log source text. Repeat several process-isolated pairs per RID, keep verification scans **outside** the latency interval, and compare fresh 50 MiB paste versus Redo in both directions. If the main thread remains blocked in one phase, use Apple's [Instruments Time Profiler and thread-state trace](https://developer.apple.com/documentation/xcode/reducing-your-app-s-launch-time), with native AOT symbols, to distinguish CPU work, allocation/GC and waiting. A draw callback would still be render submission, not physical presentation. No CI latency gate or "fast on Intel" claim is justified by the present milestone data.

#### ChangedRange migration: small-typing external GUI check

The later `ChangedRange` migration makes the native controller the sole range-only Engine change subscriber, avoiding giant legacy inserted-text materialization for that subscriber. It still copies the one inserted character for bounded format-session work. To check whether this changes ordinary typing, the Windows harness ran **three fresh processes per binary per file size**, each with **20 one-character edits** at source start, 300 ms spacing, and a further 200 ms after the last edit for the 80 ms semantic debounce. It used 1, 10, and 100 MiB repeating CRLF fixtures, verified every saved byte, and required exactly 20 product `document.edit_to_presentation` trace records per process. All **18 processes, 360/360 edits and 360/360 trace records passed**. This is an external focused-native-host input workflow, not a synthetic Engine call.

The old cached AOT executable has SHA-256 `AD31D5B4FAC5C649F4882E9C99446A3F03923FB0596C6F954A05F98C71A2E776`; the fresh range-enabled AOT executable has SHA-256 `13299F53F5D34F934DD7C5D9D896938071132D70D14215596B3E81DDB2F85B0E`. The latter was published from the Native owner's frozen local source before its `e6add4e` commit, including contemporaneous default-off AX draft code. The former predates other canvas fixes as well as the range migration, so this is **not a single-change causal A/B**. Both were run interleaved on one Windows 10.0.26200 x64 development machine with warm fixture caches; .NET 10.0.11 is the PowerShell observer runtime, not a measured Native AOT runtime field. The table reports the **median of three per-process nearest-rank summaries**, followed by their min–max range in parentheses; its 20-edit p95 is only the observed 19th of 20 samples, not a tail SLA.

| File | Old trace p50, ms | New trace p50, ms | Old trace p95, ms | New trace p95, ms | Old/new whole-process peak, median MiB |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 MiB | 95.0 (93.1–99.1) | 93.0 (92.9–105.8) | 109.9 (107.4–110.4) | 106.0 (102.4–107.4) | 85.4 / 86.0 |
| 10 MiB | 93.8 (92.7–106.0) | 94.7 (92.4–106.4) | 102.3 (97.1–107.8) | 107.6 (107.0–109.8) | 104.0 / 106.4 |

The new 100 MiB process-median p50 is ~9.7 ms higher, yet its three-process range overlaps the old range and the new process minimum is **faster** than the old median. No convincing monotonic size-scaled typing regression follows from these noisy, few-process samples. Native synchronous `WM_CHAR` acknowledgement had per-process p50s of 2.4–3.9 ms across all cells; this is a message-return bound, **not** edit-to-render. The traced `document.edit_to_presentation` interval includes the fixed 80 ms analysis debounce and ends at semantic publication, **not AppKit/Win32 draw or physical display**. It is therefore insensitive to a small `After.GetText(1)` cost and cannot prove zero added allocation. The product Native AOT build does not expose EventPipe GC counters; **GC pauses were not measured**, rather than assumed absent.
