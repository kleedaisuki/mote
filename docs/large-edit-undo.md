# Large-edit undo: a silent data-loss boundary

**Status (2026-09-29): root-based Engine implementation passed independent targeted review and tests; cross-platform low-memory/native UI validation remains. Earlier measurements below include the pre-fix behavior for comparison.** Scope is one document in the Engine and the opt-in native canvas's direct, large plain-text paste. This is not a proposal for a project/workspace subsystem. Related local context: [`src/Mote.Engine/README.md`](../src/Mote.Engine/README.md), [`docs/native-review.md`](native-review.md), [`docs/virtual-editor-design.md`](virtual-editor-design.md), and `Document.Apply` / `TrimHistory` in [`src/Mote.Engine/Document.cs`](../src/Mote.Engine/Document.cs).

## Finding and reproducible evidence

**Pre-fix failure:** `HistoryEntry.Cost` counted two bytes per inserted and removed UTF-16 code unit. `Apply` committed the edit, pushed its history entry, and only **then** called `TrimHistory`. The 32 MiB / 512-entry policy repeatedly removed the oldest entry while over budget. If one operation alone exceeded 32 MiB, it eventually removed **that operation too**, as well as all earlier undo history. The edit succeeded with no warning; `CanUndo` became false. This affected large **deletion/replacement**, not just paste. It violated an ordinary editor user's expectation that the last operation is reversible. The native canvas's 50 MiB ASCII paste costs about **100 MiB** under UTF-16 accounting.

Reproduction files are project-local and intentionally ignored by Git: `.temp/undo-probe.ps1` and `.temp/UndoMemoryProbe/`. Run `pwsh -File .temp/undo-probe.ps1` and `dotnet run --project .temp/UndoMemoryProbe/UndoMemoryProbe.csproj -c Release -- 16777216` (replace the last number with `52428800` for the 50 Mi-character case). The essential behavioral reproduction, independent of those temporary files, is:

```csharp
using var document = new Document();
document.Apply(new TextChange(0, 0, "seed"));
document.Apply(new TextChange(4, 0, new string('x', 50 * 1024 * 1024)));
// Current behavior: this committed edit and all prior history are gone.
Console.WriteLine($"CanUndo={document.CanUndo}, Undo={document.Undo()}"); // false, false
```

Environment: Windows 10.0.26200 x64, .NET SDK 10.0.400 / runtime 10.0.11, PowerShell 7.6.5, 31.7 GiB physical RAM; 2026-09-29. Timings are one-run local probes, **not** cross-platform latency targets.

| Edit | Accounted history data | Apply time, PowerShell probe | Undo after commit | Interpretation |
|---|---:|---:|---|---|
| Insert 16,777,212 ASCII chars after `seed` | 32 MiB less 8 bytes | 518–573 ms | Yes; prior `seed` edit survives at exact total budget | Near boundary |
| Insert 16,777,216 ASCII chars after `seed` | 32 MiB | 507–541 ms | Yes; earlier `seed` edit is trimmed | Latest operation retained at exact budget |
| Insert 52,428,800 ASCII chars after `seed` | 100 MiB | 1,563–1,816 ms | **No; all history removed** | 50 Mi-character paste is irreversible |
| Delete 52,428,800 chars | 100 MiB | 27 ms | **No; document becomes empty** | A single Delete can be irreversible too |

The optimized .NET memory probe with forced collections reports, for 16 Mi characters (32 MiB text), **64.1 MiB** retained after paste while history is present versus **32.1 MiB** after disposing the document's history while retaining its after-snapshot. For deletion, holding a pre-delete snapshot plus the current inverse string also retains **64.1 MiB**, versus **32.1 MiB** for the root alone. At 50 Mi characters the current entry is trimmed, so only about **100.4 MiB** is retained in those scenarios. This is evidence that storing a second contiguous inverse/redo string materially duplicates rope content *when history is kept*, not proof that every root-based history pattern will halve peak process memory. The `Document`/GC lifetime and native clipboard can add other allocations.

### Bounded root-history prototype (2026-09-29)

`.temp/RootUndoPrototype/` links the **actual current** `RopeNode`, `TextSnapshot`, and `TextChange` source into a separate .NET 10 Release console. Its experimental `RootDocument` stores before/after rope roots, source lengths, and state-neutral edit coordinates, not inserted/deleted strings. Undo/redo switches roots and materializes the legacy `TextChange.InsertText` only when emitting a corresponding event-shaped payload. An oversized action is protected while newest; later ordinary edits count toward the 32 MiB soft budget and can eventually evict it to keep history a bounded contiguous suffix. The 512-entry cap remains. Run `dotnet run --project .temp/RootUndoPrototype/RootUndoPrototype.csproj -c Release` (the temporary source is ignored by Git; these steps and design are recorded here for re-creation).

| Prototype workload | Apply | Undo | Redo | Forced-GC retained heap before undo | Result |
|---|---:|---:|---:|---:|---|
| Insert 50 Mi ASCII chars into `seed` | 67 ms | <1 ms | 24 ms | 100.7 MiB | Undoable; after Redo + one small edit, Undo small then giant returns to `seed` |
| Delete 50 Mi chars | <1 ms | 21 ms | not timed | 100.7 MiB | Undo restores all 52,428,800 chars; Redo succeeds |
| Append 10,000 one-character edits to 1 Mi-char document | 77 ms total | not timed | — | not measured | 512-entry limit retained; final text verified at tail |

These are *single-run microbenchmarks* on a 31.7 GiB Windows machine, not an 8 GiB Mac release verdict. In particular, 50 Mi deletion's old root intrinsically keeps ~100 MiB alive if Undo is available, and legacy event payload materialization still allocates ~100 MiB transiently at Undo. The prototype does not yet model locking, event queues, save state, or native UI, so production integration must test those contracts independently. It does demonstrate that the existing rope representation can retain the newest giant action **without an additional full-string copy at rest** and without a disk journal.

### Engine patch checkpoint

The focused `Mote.Engine/Document.cs` patch now stores before/after roots and lengths in `HistoryEntry`, reconstructs the legacy `Changed.Change.InsertText` only when Undo/Redo emits it, protects an oversized action while newest, and uses checked `long` cost arithmetic. `Document.Apply` and all public signatures remain unchanged. Current local evidence: Engine Release build **0 warnings / 0 errors**; independent validator's new root-history tests **8/8** and existing Engine tests **30/30** passed; independent review found no text/event data corruption and ran a **50-seed × 500-action** Apply/Undo/Redo oracle covering exact text and prior-coordinate event replacements. The project-local memory probe rebuilt against the patched Engine reports **50 Mi-character insertion and deletion both `CanUndo=true`** and approximately **100.4 MiB** forced-GC retained heap for each, unchanged when history is disposed but one corresponding immutable snapshot remains. A production `Document` probe of 10,000 one-character tail edits took **73 ms total** and retained 512 undo steps on this Windows host. These single-run figures support the intended *no duplicate full string at rest* claim for these cases. They do not establish 8 GiB Mac peak memory, GC pauses, or Native UI latency; those remain release measurements.

The reviewer additionally constructed this deliberate boundary: paste 20 Mi characters (nominal 40 MiB), then append three 8 Mi-character chunks (16 MiB each). The post-paste ordinary suffix eventually exceeds 32 MiB, so the older giant paste is evicted; only the newest ordinary suffix remains Undo-accessible. This is **intended bounded linear history**, not a promise to protect a giant action forever. Removing only an intermediate ordinary edit would create an invalid history gap; allowing unlimited post-giant overrun could consume unbounded RAM. A regression test captures this exact policy boundary.

**Secondary pre-fix arithmetic defect:** `HistoryEntry.Cost => (long)(Change.InsertText.Length + Removed.Length) * sizeof(char)` widened *after* `int` addition. A zero-allocation arithmetic probe using two 1,200,000,000-code-unit lengths yields **−3,789,934,592** for that expression instead of **4,800,000,000** bytes. Such a real edit would require exceptional memory, but the accounting invariant was broken. The reviewed patch now uses `checked(((long)insertLength + deleteLength) * sizeof(char))`. This is separate from the 50 MiB reproducible case.

## External signals, with scope limits

| Signal | What it supports | What it does **not** establish |
|---|---|---|
| [GNU Emacs undo manual](https://www.gnu.org/software/emacs/manual/html_node/emacs/Undo.html) | Uses soft/strong/outer byte limits; specifically tries to preserve the most recent command and **warns** when even that must be discarded. Mote's silent loss of the newest command is not a necessary consequence of bounded history. | Emacs's exact limits are not suitable defaults for Mote's .NET rope, native UI, or 50 MiB paste. |
| [Microsoft Rich Edit `EM_SETUNDOLIMIT`](https://learn.microsoft.com/en-us/windows/win32/controls/em-setundolimit) | Production native controls bound action count and explicitly tie higher limits to memory. | A count limit alone cannot prevent one huge edit from exhausting memory; Mote's Engine is the source of truth, not the input island. |
| [Neovim undo persistence](https://neovim.io/doc/user/undo/) and [options](https://neovim.io/doc/user/options/) | Disk undo is an established *opt-in* feature; Neovim checks the edited file's content hash before restoring an undo file and documents that undo files are not automatically deleted. | Disk persistence is not needed merely to make one in-session paste undoable; it has cleanup/privacy obligations. |
| [Xi text engine design](https://xi-editor.io/xi-editor/docs/crdt-details.html) and [Boehm et al., “Ropes: An Alternative to Strings,” 1995](https://doi.org/10.1002/spe.4380251203) | Immutable/shared text structure can support version navigation without copying full strings. Mote already has the prerequisite persistent rope. | Xi's CRDT/revision model is more complex than a single-user document and should not be transplanted wholesale. |
| [Rossmy et al., CHI 2023, “Point of no Undo”](https://doi.org/10.1145/3544548.3581433) | Recent HCI work treats irreversibility as a *deliberate and salient* interaction choice; it reinforces that silent irreversibility is qualitatively different from an explicitly communicated destructive action. | It does not evaluate large text-editor pastes or prove that a warning is sufficient UX here. |
| [Pietron et al., *Software and Systems Modeling*, 2025](https://doi.org/10.1007/s10270-024-01214-9) | For operation-based histories, snapshot placement trades restore latency against memory; adaptive policy can outperform fixed-distance caching in their evaluated model editor. | Their collaborative graphical-model workloads and numbers cannot be carried directly into Mote's rope editor. This is a research direction for later history tiers, not an implementation prescription. |

## Options and recommendation

| Option | Correctness and user experience | Memory/latency | Engineering and privacy cost | Judgment |
|---|---|---|---|---|
| **A. Additive preflight + explicit confirmation** | Before a user-facing edit, estimate the actual retention policy in `long`; if an action will become non-undoable, warn with Cancel as default. Preserve the public `Document.Apply` behavior for existing callers. | No extra retained memory; warning interrupts exceptional operations. | Smallest transitional safety gate; two-phase UI checks race concurrent edits unless bound to version/generation/selection. | **Fallback only** if the reviewed root-history design or low-memory platform tests cannot guarantee latest-action undo. The old blanket `>32 MiB` warning is obsolete once root retention ships. |
| **B. Adaptive in-memory latest-entry allowance** | Preserve newest large edit above soft 32 MiB, trim older ones first, and warn/reject only beyond a tested outer limit (e.g., 128 MiB; *candidate*, not measured policy). A 50 MiB ASCII insertion then remains undoable. | Current string-based history plausibly retains ~100 MiB extra input string on top of ~100 MiB rope, plus transient allocations. Low-memory devices and replacements/deletions need profiling. | Modest code change, but arbitrary outer limit remains and memory pressure can cause OOM. Preserve `Apply` compatibility; expose status if an edit is still not undoable. | Useful bridge only after 8 GiB Mac/Windows stress results; not sufficient alone for arbitrary large edits. |
| **C. Root-based in-memory history** | Store immutable `before`/`after` rope roots and state IDs instead of `InsertText`/`Removed` copies; undo/redo switch roots (new public versions) rather than copying a giant string. Preserve the newest giant action, then trim only a contiguous suffix under later edits. | Large insertion's after-root is already the live document; huge deletion retains the old root rather than building a duplicate contiguous deleted string. Full-document replacements still intrinsically retain both versions. | Best fit to existing rope. Current patch retains nominal edit-size accounting for ordinary history, not a true unique-leaf-byte quota. Legacy `Changed.Change.InsertText` still materializes one giant string transiently on Undo/Redo; an additive length-only delta is a later optimization. | **Implemented in Engine; oversized action can be evicted by enough subsequent edits. Cross-platform low-memory measurements remain.** |
| **D. Disk-backed undo journal under configurable `~/.mote`** | Can bound RAM and support long history/session recovery if a record is durably written before admitting an edit. Failed/full journal writes must fail the edit or fall back to a still-undoable memory mode—never silently continue. | Adds O(edit bytes) disk write/read and potential Undo latency; possible async prewrite but commit must not outrun protection. | Highest complexity: format/version/checksum, file identity, recovery, quota/GC, Windows ACL and Unix `0600`, symlink/path safety, multi-process coordination, encryption/secure deletion expectations. Journal can retain sensitive deleted text after original file is saved or removed. | **Defer** until root-based history is benchmarked; opt-in if ever introduced. Separate “in-session undo” from “crash recovery.” |

### Transitional gate, only if platform validation finds a hard memory limit

The root-history patch makes a 50 MiB paste/delete undoable in Engine, so a blanket “larger than 32 MiB is irreversible” warning would now be false and should **not** be shipped. If an 8 GiB Mac or another supported configuration shows unacceptable peak memory, choose a measured per-operation admission threshold and add an engine-visible estimate/status rather than assuming the 32 MiB ordinary-history budget is a hard operation limit.

1. Gate every user-originating path consistently if a true hard limit is introduced, including macOS/Windows direct paste, selection deletion, format/rewrite, and Replace All. The opt-in canvas choke point is `NativeEditorController.CanvasEdited`, which validates generation/version/binding nonce and calls `_document.Apply(change)`; Mac and Windows direct paste both route through it. Never silently truncate or partially apply clipboard content.
2. If an operation genuinely cannot remain undoable, offer a precise warning with **Cancel as default** and an explicit “Continue without Undo” action; preserve the document and clipboard on Cancel. Bind any modal confirmation to document generation, snapshot version, exact selection and binding nonce, and revalidate after the prompt. An additive Engine admission method could make the version check atomic. **Do not change public `Apply` to reject edits by default** without a deliberate compatibility migration.
3. After an explicitly irreversible action, expose status/accessibility feedback and accurately disable Undo. Do not imply Save is equivalent to Undo. None of this substitutes for retaining the latest action when technically feasible.

### Next discriminating investigation

Run production root-history implementation through (a) 50 MiB ASCII insertion, (b) 50 MiB deletion, (c) replace-all of a 100 MiB file, and (d) 10,000 small edits. Measure P95 edit/undo latency, peak private bytes and GC pause, retained unique leaf bytes after history pruning, event payload allocation, and `IsModified`/saved-state restoration on **Windows and 8 GiB macOS**. Existing Windows unit tests cover behavior, not native presentation or low-memory pressure. An acceptable design must keep the latest user action undoable without a UI-thread pause that materially exceeds the existing canvas interaction budget; only if it cannot should the explicit admission gate or bounded optional disk tier be considered.

## 50 MiB Redo notification cost and additive event design

**Source audit (2026-09-29).** Root-backed history removed full-string retention, but `Document.Redo` still unconditionally runs `restored.GetText(Start, InsertLength)` **inside the document lock**, before it knows whether any subscriber needs `DocumentChangedEventArgs.Change.InsertText`. `RopeNode.Slice` uses a `StringBuilder(length)` and then `ToString()`. A local project-only probe (`.temp/UndoMemoryProbe/`, Windows x64, Release Engine/runtime 10.0.11) measured one 50 Mi-code-unit Redo at **200.0 MiB thread allocation / 41 ms**, with **zero `Changed` subscribers**. This is two full UTF-16-sized temporary allocations; the time is a single-run machine-specific observation, while the allocation is a direct API-path mechanism. Undo of a 50 Mi deletion has the same construction. No copy remains in history at rest, but transient allocation and a long held lock can induce GC and UI latency.

The native product's Engine `Changed` subscriber is `NativeEditorController.DocumentChanged`. It invokes `NativeFormatSessionDriver.Record`, `NativeNavigationModel.ApplyChange`, and `CanvasInteraction` → `ContinuousViewport.ApplyEdit`. Navigation and viewport only need **inserted length**, not inserted characters. The session driver stores small `TextChange` payloads for incremental parser reuse, but discards one insertion greater than **1 Mi UTF-16 units** and rebuilds its format session from the authoritative snapshot on the next analysis. Thus a 50 Mi redo allocates and passes a giant legacy `InsertText` that these Native consumers do not use. The separate Avalonia desktop `Editor.Document.Changed` subscription is an Avalonia text-document event, **not** the Engine event. Tests and future embedders may still subscribe to Engine's public `Changed`; its exact payload must remain valid.

### Hosted Mac evidence is an aggregate, not Engine timing

[GitHub Actions run 36567450134](https://github.com/kleedaisuki/mote/actions/runs/36567450134) uploaded `mac-canvas-clipboard-metrics.txt` (local inspection copies under `.cache/ci-run-36567450134/`). The source `MacCanvasClipboardProbe.Workflow.Tick` creates a 50 Mi-character string *inside* stage 4, then invokes paste; stage 5 scans all 50 Mi characters with `MatchesHuge` before recording. Stage 6 invokes Redo; stage 7 again scans the entire document before recording. Each next stage has an additional scheduled **60 ms poll**. The following are **upper bounds for each operation plus validation/scheduling**, not paste/Redo latencies:

| Mac RID | Stage 4→5 (string construction + paste + full scan + poll) | Stage 6→7 (Redo + full scan + poll) | Working-set change stage 6→7 |
|---|---:|---:|---:|
| osx-arm64 | 1,029 ms | 649 ms | +~202 MiB |
| osx-x64 | 4,089 ms | 2,661 ms | +~202 MiB |

The working-set increase is *consistent with* the measured 200 MiB Redo allocation, but not proof of causation: other AppKit/controller work and GC occur in the interval. The artifact reports `PeakWorkingSet64=0` on Mac, so **true peak memory is unavailable**. No allocation, GC-pause, Engine-phase, or actual pixel-present trace was recorded. In particular, removing the legacy Redo copy would not by itself explain or cure the 4.1 s x64 paste interval, which includes multiple unrelated full-document operations.

### Additive, compatibility-preserving contract

**Engine implementation now exists; Native migration is still separate.** `TextChangeRange(Start, DeleteLength, InsertLength)` uses UTF-16 code units; `DocumentChangedRangeEventArgs(Before, After, Change)` exposes immutable snapshots and the range; `Document.ChangedRange` is the new event. Its source text is `After.GetText(Start, InsertLength)` *only when a consumer explicitly requests it*. The existing public `Document.Changed` event, `DocumentChangedEventArgs`, and `TextChange` payload remain exact for subscribers. Both event kinds use **one ordered mutation queue**, not independent queues that could invert versions under concurrent or reentrant edits. For each mutation Engine delivers `ChangedRange` first, then legacy `Changed`, with the same immutable Before/After versions; a reentrant edit queues behind both callbacks for its parent mutation. A queue record retains snapshots and lengths, not a giant string when no legacy subscriber exists. Engine constructs `Changed.Change.InsertText` only if `Changed` has a handler; when `Apply` already has a `TextChange` and a legacy handler is present, it reuses that value. A handler added during queue delay still receives exact content reconstructed from `After`. A handler failure cannot strand later versions or prevent the other event kind from being delivered.

Engine Release build passed with zero warnings/errors. New focused tests **7/7** and affected existing Engine/root-history tests **38/38** passed on Windows, covering exact payloads, deterministic dual-event and concurrent/reentrant order, handler failure, late legacy subscription, reentrant Save/Undo, and 50 Mi range-only Redo allocation. A single-run Release Engine probe on Windows .NET 10.0.11 measured:

| 50 Mi-character Redo observer mode | Calling-thread allocation | Wall time | Payload result |
|---|---:|---:|---|
| No `Changed` subscriber | ~0.0 MiB | <1 ms | Root switch only |
| `ChangedRange` subscriber only | ~0.0 MiB | <1 ms | Exact `InsertLength=52,428,800` |
| Legacy `Changed` subscriber | **200.0 MiB** | 41 ms | Exact 52,428,800-character `InsertText` |

This verifies the Engine allocation hypothesis and deliberate legacy compatibility on this host. It is **not** evidence that Mac UI Redo is now fast: the Native controller currently remains subscribed to legacy `Changed`, so its production runtime still takes the 200 MiB branch until it migrates. The full hosted Mac stage intervals also still contain the probe's scan/poll and AppKit work.

Native migration is separate from this Engine addition: switch `NativeEditorController` to `ChangedRange`; navigation/viewport transform anchors from `InsertLength`; `NativeFormatSessionDriver.Record` first checks its one-Mi-unit budget, then reads small inserted text from `After` only when retaining that incremental edit. It must not retain whole before/after snapshots in its queued edit list; a giant edit records a version gap and triggers its existing authoritative rebuild. The controller's own `CanvasEdited` still has the original user input `TextChange` for caret positioning. With Native as a range-only subscriber, 50 Mi Redo should switch rope roots without allocating a full inserted string. A legacy subscriber intentionally preserves the old cost and exact content. This changes no `Apply`, `Undo`, `Redo`, `Changed`, dirty-state, save, or format-policy contract.

### Discriminating measurement before claiming a speedup

1. **Engine-only, same 50 Mi document:** warmed repeated Undo/Redo under (A) current no-listener baseline, (B) new no-listener Engine, (C) new range-only listener, and (D) new legacy `Changed` listener. Record per-operation `Stopwatch` p50/p95, `GC.GetAllocatedBytesForCurrentThread`, collection counts/pause evidence, and peak process memory. Expected result: B/C eliminate roughly **200 MiB** from each giant Redo; D still emits exact 50 Mi `Change.InsertText`. Assert event version ordering and payload equality, including concurrent/reentrant handlers.
2. **Native controller/AppKit:** timestamp payload construction, clipboard-to-managed conversion, Engine validation/rope replace, root switch, event dispatch, format-session record, navigation/viewport update, `ShowCanvasDocument` frame and input binding, draw submission, and the `MatchesHuge` scan **separately**. Exclude the probe's 60 ms poll and full-file validation from operation latency, then validate bytes outside the timed interval. Trace GC and actual present separately from a model callback.
3. **Cross-platform comparison:** run at least repeated warmed samples on osx-arm64, osx-x64 and win-x64 with the same Native AOT build/fixture, including a lower-memory Mac. A stage aggregate improvement without matching Engine allocation reduction and unchanged content/selection/IME behavior is insufficient attribution. If Redo still costs seconds after eliminating the 200 MiB copy, investigate AppKit input rebinding, grapheme/window selection, frame layout and validation scans rather than assuming the Engine was the only bottleneck.

**Documentation correction for a later Engine docs-only patch:** `TextChange.cs` currently says a change may split a surrogate pair. Raw UTF-16 offsets can name such a boundary, but committed `Document.Apply` rejects it via `ValidateBoundary`; the existing XML remark misdescribes the Document contract. Do not conflate this wording fix with the notification API migration.
