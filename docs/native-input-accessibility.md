# Native input and accessibility acceptance plan

Status: source audit, OS-documentation synthesis, and local Windows experimental-canvas acceptance, 2026-09-29. **Real Microsoft Pinyin candidate, Insert, Cancel, same-text replacement, and 50 Mi remote-pan commit have passed on particular hashed Windows x64 AOT artifacts below; this does not establish other IMEs, macOS real IME, Narrator, or VoiceOver.** Scope is the strict one-on-disk-binary `Mote.Native` shell on Windows and macOS; OS-provided RichEdit, AppKit, accessibility, and input libraries do not add shipped sidecars.

## Decision in one paragraph

Keep native RichEdit/NSTextView as the **input-composition host**, because replacing them with a hand-written text-input stack would add substantial IME and assistive-technology risk. Treat the engine snapshot as canonical **only after committed input** and keep the native marked/undetermined composition on its page until completion or cancellation. Separately, do not mistake a global selection model for whole-document accessibility: a native control containing only a 64 Ki-unit page can normally expose only that page to UI Automation (UIA) or macOS accessibility clients. Product-grade large-file access needs an engine-backed, virtualized document accessibility provider or a different engine-backed view; until it is demonstrated, do not assert that offscreen text is screen-reader navigable. This distinction follows the [Microsoft UIA text model](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-ui-automation-textpattern-overview) and [Apple accessibility guidance](https://developer.apple.com/documentation/accessibility/integrating-accessibility-into-your-app), but the page-only conclusion is a **source-code inference**, not a measured provider result.

## Composition contract to implement and measure

1. Represent input as `Idle -> Composing -> Commit-or-Cancel -> Idle` at the **shell/controller boundary**. `Composing` means marked/undetermined text belongs to the native control, not yet to the engine snapshot. Keep any composition-local string and selection out of Save, diagnostics, formatting, global copy/cut, page rebase, and semantic restyling until resolved. If OS behavior forces incremental engine edits, record them as one reversible composition transaction and make Save/undo semantics explicit; never silently persist provisional candidates.
2. Begin/end signals must be platform-specific and observed. On macOS, sample `hasMarkedText`/`markedRange` after input callbacks and before any page replacement; on transition to unmarked, reconcile the final native page exactly once. On Windows, record `WM_IME_*`, `EN_CHANGE`, and RichEdit `EN_ENDCOMPOSITION` ordering and query language/edit options; only then choose the robust commit trigger for IMM and TSF. Do not disable IMEs or text services to simplify this.
3. Queue engine-initiated page replacement, formatting, theme/font changes, whole-page RTF import, navigation, and close/open requests during composition. On commit/cancel, reconcile text, preserve the global source selection, then apply queued operations against the new snapshot version. Save and close should either finish/cancel composition through the OS and wait for acknowledgement, or fail visibly without changing the file; never save an ambiguous intermediate view.
4. Assert an invariant at every transition: projecting the committed engine page equals the native page after composition (modulo the documented CR/LF projection), and Save/reopen reproduces exact Unicode scalar sequence, newline spelling, and encoding. The platform shells must not turn one candidate into multiple engine edits or duplicate text on confirmation.

This is an implementation direction, **not** a claim that one event-ordering recipe is already validated. RichEdit defaults and specific IMEs differ; probe before hard-coding the state machine.

### Opt-in Windows canvas input island (2026-09-29 follow-up)

The current strict AOT binary built locally as `.cache/ime-canvas-aot/mote.exe` accepts `--canvas-experimental`; the existing PowerShell probe now locates its *nested* `MoteInteractiveCanvas → RICHEDIT50W` input island rather than the hidden default editor, and supports `-CanvasExperimental -Scenario Insert|Cancel|SameText`. ### Cold first-key loss: injected Alt transition, not a proven Mote key handler defect

On 2026-09-30 I retested the preserved 50 MiB synthetic fixture and SHA-256-identical final-source executable above. The repo-local probe `.temp/cold-pinyin/probe.ps1` adds per-key native RichEdit prefix, foreground/focus, and Shift/Ctrl/Alt/Win/Caps guards; `.temp/cold-pinyin/run-cold.ps1` forces a disposable English-to-Chinese taskbar-mode transition and restores the observed entry mode. It sends no Save, checks the fixture hash on Cancel, and records only this generated fixture. The original probe sends a synthetic Alt key tap after switching taskbar mode to grant `SetForegroundWindow`; the controlled variant omits **only that post-toggle Alt tap**. This distinction matters because [Microsoft says `SendInput` reports events inserted into the input stream, not delivery to a particular window](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput).

The decisive traced failure had mote foreground and the physical RichEdit HWND focused before and after every injected key; all guarded modifiers were clear. `SendInput` accepted the `n` down/up pair, but **neither `WM_KEYDOWN` nor `WM_SYSKEYDOWN` for that first key appeared in Mote's `GetMessage` loop or RichEdit subclass**. A `WM_KEYUP` for `n` did appear, with no document binding/rebinding in that interval. Immediately beforehand, RichEdit spent **2.265 s** inside `DefSubclassProc` for `WM_SYSKEYUP`; passing traced trials did not have that late system-key release in the injection interval and did receive ordinary first-key `WM_KEYDOWN` followed by IME composition. Microsoft documents system-key messages as part of Alt/menu handling, with [different `WM_SYSKEYDOWN` and character semantics](https://learn.microsoft.com/en-us/windows/win32/inputdev/about-keyboard-input). The inserted Alt tap is the most specific demonstrated correlate; whether the missing key was consumed by the OS input queue, TSF/Pinyin during activation, or a transient focus transfer **within** the down/up pair remains unresolved. Stable focus snapshots on either side of an 85 ms key interval cannot exclude such a transfer. The 3/27 versus 0/19 trial difference is suggestive, not a statistical guarantee that removing Alt alone cures every first-key issue.

**Decision:** do not add a speculative Mote key replay, a synthetic extra keystroke, or a focus delay to production. No delivered first-key message was shown to be swallowed by Mote, and replay could duplicate real text or break IME composition. The temporary trace **was removed** from production source after the experiment; the disposable probe remains under `.temp` for reproduction. A fresh Native Release build after removal had zero warnings and zero errors. The developer taskbar indicator was then restored from Chinese to **English and independently reread as English twice**; no language/profile setting was changed. A physical-keyboard cold-start test and, if it fails, an OS-level TSF/focus event trace are still needed before declaring first-keystroke reliability. The original synthetic-Alt helper should not be used as an acceptance oracle without its mode/focus and per-key evidence.

The next architectural experiment is a **physical-keyboard and accessibility event-order trace**, not a rewrite: on each OS, log timestamped input/composition/selection and command events for one real conversion and one cancellation, with text omitted or replaced by length/hash. Store probes under repository `.temp/` and never enable them in user telemetry by default. The Windows injected-key trace above does not replace this independent physical-key test. The unmodified opt-in Windows UIA bridge retains a duplicate focused RichEdit `Document`; the newer **separately opted-in fragment** removes that duplicate in external client inventory while preserving the Pinyin flows above. The tree probe and input probe were separate processes, so query full-document ranges, focused element, selection and spoken caret **during** active candidate use before considering default enablement. On macOS, hosted [two-RID external Swift AX source-range checks](https://github.com/kleedaisuki/mote/actions/runs/36572346343) and [external close-lifecycle checks](https://github.com/kleedaisuki/mote/actions/runs/36576635105) have narrow passes; **real macOS IME interaction and VoiceOver speech remain unverified**. Microsoft's `TextPattern` models document ranges, while `TextEditPattern` separately models active composition; a one-node tree alone does not establish either complete editable text semantics or candidate speech. [TextPattern](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-ui-automation-textpattern-overview), [TextEditPattern](https://learn.microsoft.com/en-us/windows/win32/winauto/textedit-control-pattern).
