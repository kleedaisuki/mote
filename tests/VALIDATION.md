# Validation strategy

## Contract and scope

The editor's public workflow is **open one file, inspect its structural analysis, edit, undo/redo, and save**. Validation should derive expectations from that workflow and from each text format's published syntax rather than copying implementation output. Engine offsets and format spans are UTF-16 code-unit offsets; this is intentionally observable because the desktop text control also uses UTF-16 positions.

The suite should distinguish three layers:

1. Engine: immutable snapshots, line lookup, edits, undo/redo, file identity, persistence, encoding, and cancellation.
2. Policies: parse trees, spans, diagnostics, formatting, rendering, and selection by file extension for Markdown, TOML, JSON, YAML, CSV, and plain text.
3. Integration: an opened file's policy remains coherent after edits; stale or canceled analysis cannot replace analysis of newer text; save/reopen retains content and relevant file metadata.

## High-information cases

| Area | Expected behavior | Why it discriminates |
| --- | --- | --- |
| Snapshot isolation | Earlier snapshots retain prior text after edit, undo, redo, and document disposal. | Detects mutable backing storage leaking across versions. |
| UTF-16 offsets | Edit and spans around an astral Unicode scalar use two UTF-16 units. | Separates code-unit contracts from scalar/grapheme indexing. |
| Line index | CR, LF, and CRLF are breaks; terminal delimiter yields a final empty line. | Exposes off-by-one and newline-normalization mistakes, including chunk boundaries. |
| Save/reopen | UTF-8 BOM/no BOM, UTF-16 BOM, and CRLF survive an unmodified open/save cycle. | File fidelity matters more than internal normalization. |
| JSON | Nested object/array parse; malformed input and duplicate object keys diagnosed. | Distinguishes structural parsing from lexical highlighting. |
| TOML | Tables and key/value pairs form structure; duplicate keys diagnosed. | Tests scope-aware semantics, not just tokenization. |
| YAML | Nested mappings/sequences form structure; duplicate mapping keys diagnosed. | Tests indentation-sensitive semantics. |
| CSV | Quoted commas/newlines/escaped quotes parse as cells; inconsistent columns diagnosed. | Tests records rather than lines. |
| Markdown | Headings, lists, links, and fenced code have structure; a fence ending at EOF is valid CommonMark. | Exercises block and inline semantics without inventing an error. |
| Plain text | Arbitrary text remains editable with no format diagnostics. | Protects fallback behavior. |
| Large file | Edit near the end of a multi-megabyte document preserves nearby and distant text. | Checks correctness without imposing an arbitrary timing threshold on CI. |

YAML duplicate-key cases are based on [YAML 1.2.2 §3.2.1.3 Node Comparison](https://yaml.org/spec/1.2.2/#3213-node-comparison): scalar equality uses tag and canonical value, sequence equality is positional, and mapping equality ignores pair order. Thus `0xB` and `11` are duplicate integer keys, equal sequence/mapping keys are duplicates, and quoted `"11"` differs from numeric `11`. Self-referential alias equality is implementation-defined; the test requires safe bounded behavior rather than guessing an equality result.

For implicit tags, [YAML 1.2.2 §10.3.2 Core Schema Tag Resolution](https://yaml.org/spec/1.2.2/#1032-tag-resolution) does not include underscore-separated integers or signed hexadecimal in its integer regular expression. Therefore `1_000` versus `1000`, and `-0xB` versus `-11`, are not duplicate keys under the untagged Core schema even if a parser library accepts those spellings as extensions.

A differential local probe by the format-policy team used `ruamel.yaml 0.19.1` (`typ='rt'`, `pure=True`, `allow_duplicate_keys=False`; script in ignored `.temp/yamlkeyprobe.py`). It rejected numeric-equivalent and equal-sequence keys and accepted distinct quoted/numeric keys, but accepted equal mapping keys with reordered pairs. That negative result is why mapping-key expectations follow the specification rather than blindly copying this library's behavior.

## Execution and interpretation

Run local unit/integration tests on Windows and in GitHub Actions on Windows and macOS. Run Native AOT publishing on native-architecture runners because cross-architecture AOT toolchains are platform-dependent. Collect performance measurements separately from correctness gates; CI timing thresholds on shared runners are not evidence of a regression. Report tested commands, environment, expected versus observed results, and untested paths. Never call a compile-only job a runtime test or infer macOS behavior from a Windows run.

The Native AOT matrix uses `windows-latest`/`win-x64`, `windows-11-arm`/`win-arm64`, `macos-15-intel`/`osx-x64`, and `macos-latest`/`osx-arm64`. The Windows ARM64 runner choice follows GitHub's [hosted runner label documentation](https://docs.github.com/en/actions/reference/runners/github-hosted-runners) and avoids assuming Windows x64 can cross-link an ARM64 Native AOT binary. The release-target project is now `src/Mote.Native`, not the legacy Avalonia desktop. Each native job will run `--check-runtime` (expected `mote-native-ready`) and `--smoke-gui` (expected `mote-native-gui-ready`) using a process-waited invocation. macOS additionally asks Launch Services to `open -W -a` the standalone executable, testing embedded application metadata rather than a `.app` bundle. A GUI smoke is a real OS-window startup/close probe, but not proof of physical paint or keyboard/mouse interaction. A hosted runner without an active GUI session may fail for environmental reasons, which must be diagnosed rather than misreported as an editor defect.

Routine CI does **not** build or upload the exploratory `.app`/portable ZIP packages because the user requires literal one-binary delivery. The scripts under `packaging/` remain diagnostic fallback tools, not a release path. macOS CI inspects the raw executable's linked libraries with `otool -L`; signing, notarization, Gatekeeper behavior, and trust prompts are unverified.

Strict single-binary delivery is a separate **gating assertion** at the end of each `Mote.Native` AOT job. The job publishes with symbols/documentation disabled, inventories **all** resulting files, uploads JSON inventory, and fails unless the executable is the only file. A passing `PublishAot` step alone is not proof of single-binary delivery. The legacy Avalonia win-x64 publish did fail this contract: `Mote.Desktop.exe` (`26,863,616` bytes) was accompanied by `av_libglesv2.dll` (`5,394,096` bytes), `libHarfBuzzSharp.dll` (`1,816,088` bytes), and `libSkiaSharp.dll` (`11,628,896` bytes), excluding PDB/XML debugging files. This is evidence for the architecture pivot, not a finding about the native shell; the latter's four-target one-file result is recorded in the hosted checkpoints below.

For repeatable, non-gating performance evidence, run `dotnet run --project tests/Mote.Benchmarks -c Release -- 32` (size in MiB). It generates a deterministic Markdown file under `.temp/benchmarks`, measures file open, one tail edit, whole-file analysis, and peak process working set, then appends environment-tagged JSONL to `.cache/benchmarks/results.jsonl`. These numbers are workload and machine specific; compare like-for-like runs rather than treating them as product-wide guarantees. The harness does not measure GUI startup or rendered-frame latency.

`Benchmarks` GitHub Actions runs weekly or manually on hosted Windows/macOS. Its non-gating workloads are 1 MiB Markdown open/edit/analyze, 100 MiB Markdown open/edit (analysis intentionally omitted), and a 32 MiB single-line open/edit. It uploads the JSONL measurements as artifacts. No regression threshold is asserted on shared runners; the workflow has not itself been observed in GitHub Actions from this checkout.

The same workflow separately publishes the native shell on representative win-x64 and osx-arm64 runners, then runs `tests/Measure-NativeStartup.ps1`: one cold process and ten warm `--smoke-gui` processes, recording nearest-rank p50/p95 plus all samples. The metric is **process start to orderly GUI-smoke exit**, including OS process startup and test close delay; it is **not first paint** or edit latency. A local three-warm-run harness check on the stable pre-latest win-x64 single-file publish yielded cold `82.2601` ms, warm p50 `71.1769` ms, warm p95 `74.8685` ms (samples `69.7886`, `71.1769`, `74.8685` ms). These are not acceptance thresholds, not a ten-run estimate, and not current-source performance. Raw local JSONL is under ignored `.cache/benchmarks/native-startup.jsonl`.
